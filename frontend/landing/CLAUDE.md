# CLAUDE.md — 이 폴더에서 일할 때의 규칙

`paperboat/` 는 GPU 파동 시뮬레이션 위를 항해하는 향 탐색 프로토타입이다.
구조와 함정은 `README.md` 에 정리돼 있다. **먼저 README 를 읽는다.**

⭐⭐ **2026-09-15 부터 원본은 팀 프론트의 `frontend/landing/`(이 폴더)이다** — paperboat 저장소는 v0.63.0 에서 멈췄다.
거기서 덮어쓰지도, 거기로 되돌려 복사하지도 않는다.
네 갈래 워크트리(A 바다·배 렌더 · B 부표·향수 고르기 · C 연출·화면 UI·항해 · D 앱 연결)로 나눠 작업하는 동안은
**`docs/워크트리-분할.md` 를 먼저 읽는다** — 갈래 브랜치에서는 `CHANGELOG.md` · 이 파일 · `window.PB` 줄을 안 고치고 `docs/분할/<갈래>.md` 에 적는다.

⚠⚠ **develop 에는 개발 패널이 없다** (2026-09-17 · 사용자 : *"최종 develop 에 올릴 때는 노출 안 되게 삭제"*).
`perf` · `tweaks` · `viewbar` · `campanel` · `compare` · `freecam` · `probes` · `framegrab` 모듈과 `main.js` 의 자리 · `PB.solo` · H 키가 빠졌다.
아래에서 이 패널로 재고 보는 방법(HUD · 검증 보기 조작 바 · 자유 시점 · `PB.solo`)은 **엔진 작업 브랜치 기준**이다 — develop 에서 엔진을 고칠 때는 그 브랜치에서 작업하고 옮긴다.

**무엇을 어떤 순서로 만들 것인가는 `docs/작업계획.md` 에 있다.** 2026-08-31 기능명세 개정으로
돛단배(MAP-21)·향해 일지(MAP-24)·YES/NO 탐색 제안(MAP-12)이 정식 P1 요구사항이 됐다.
작업을 시작하기 전에 그 문서의 1장(코드와 스펙의 충돌)과 2장(작업 순서)을 읽는다.

## 먼저

- `npm run dev` 로 띄우고 실제 화면을 본다. 이 프로젝트는 정지 스크린샷으로 판정할 수 없다 —
  파도, 일렁임, 반짝임, 부력은 시간이 흘러야 드러난다. 최소 10초는 보고 판단한다.
- 좌상단 계측 HUD(`perf.js`, 개발 빌드 전용)를 같이 본다. **⚠ 창이 화면에 안 떠 있으면
  `document.hidden` 이 false 여도 브라우저가 rAF 를 안 돌린다** — GPU·rAF·게이트 간격이 전부
  수천 ms 로 뜬다. 시간 기반 값을 인용하기 전에 창이 실제로 보이는지부터 확인한다.
  드로우콜·정점 수는 영향을 안 받으므로 그쪽은 언제 읽어도 된다.
- ⭐⭐⭐ **화면을 볼 때는 개발 UI 를 닫는다 — `PB.solo(true)`** (2026-09-12 저녁 사용자 지시 :
  *"앞으로 너가 웹화면을 체크하며 테스트나 프레임을 확인할때 무조건 개발자용 패널, 파라미터 조절,
  원본 차이 패널은 닫고 보셈"*). 계측 HUD · 개발 바 · 파라미터 · 카메라 패널 · 원본 비교 **다섯**을
  한 번에 숨긴다. 되돌리기는 `PB.solo(false)` 또는 **H 키** (campanel 의 [화면만] 버튼과 같은 것).
  ⚠⚠ **서비스 UI 는 절대 닫지 않는다** — 미니맵 · 검색바 · 말풍선 카드 · 부표 이름표 · DRIFT 바,
  그리고 **앞으로 붙는 UI 전부**. 사용자 : *"서비스에 들어갈 미니맵, 앞으로 추가할 ui는 절대
  닫으면 안되는걸 명심하셈"*. `solo` 는 개발 패널 다섯만 고르므로 새 UI 를 붙여도 그대로 남는다 —
  ⚠ 새 **개발** 패널을 만들면 `campanel.addSoloTarget(el)` 로 등록한다 (compare.js 가 그렇게 한다).
  ⚠⚠⚠ **DOM 을 직접 숨기지 않는다** (`el.style.display='none'`). 실측 2026-09-12 : HUD 를 그렇게
  가렸더니 ResizeObserver 가 0 크기를 읽고 **캔버스가 1×1 로 죽었다.** 화면이 배경색만 남아
  **물리 발산과 똑같이 보인다** — 엉뚱한 데를 뒤지게 된다. `PB.onResize()` 로도 안 돌아와 리로드했다.
  `solo` 는 원래 display 를 기억했다가 돌려주고, 캔버스를 품은 컨테이너를 애초에 안 건드린다.
- ⭐⭐ **테스트 창은 1920×1080 이다** — ⏸ **2026-09-13 부터 보류 : 이 노트북은 pane 제 크기(1440)로 한다 (이 항목 끝)** (2026-09-12, 사용자 : *"테스트는 앞으로 1920 에 맞춰서
  진행할거임 md 에 적어서 비율 잘 맞도록하고"*). **화면 px 로 적힌 값은 창 폭에 따라 상대적으로
  달라 보인다** — 선 굵기(`focusLinkW`), 부표 이름표 글자 크기, 고르기 흩기 간격(px)이 그렇다.
  같은 3.6px 이 1920 에서는 또렷하고 2560 에서는 실처럼 얇다. 실제로 09-12 에 2560 창에서 본
  2.4px 을 *"안 보인다"* 고 판정할 뻔했다 — 창이 달랐던 것이다.
  ⚠ 값을 정할 때도, 화면으로 판정할 때도 **1920×1080 에서** 본다. 다른 크기에서 본 굵기·간격은
  인용하지 않는다 (인용할 때는 그 창 크기를 같이 적는다).
  ⚠ 반응형 단계는 `index.html` 의 **폭 1280 · 1024 · 760 / 높이 700 · 560** 이라
  1920 은 단계 밖의 **기준값**이다 — 1920 에서 고른 값이 그 아래 단계의 출발점이 된다.
  ⚠ 브라우저 도구로 볼 때는 `resize_window` 로 1920×1080 을 **매 턴 다시** 잡는다 (턴이 끝나면 풀린다).
  `innerWidth` 와 `LineMaterial.resolution` 이 둘 다 1920 인지 확인하고 시작한다.
  ⏸ **2026-09-13 : 이 노트북에서는 일단 pane 제 크기(1440 폭)로 진행한다** — 사용자 : *"그럼 일단 노트북 세팅 값인 1440 으로
  진행하자 지금 비율정하는건 크게 의미없을듯"*. 시연 PC 화면이 아직 정해지지 않아 1920 에 맞추기를 미뤘다 —
  위 1920 규약은 시연 화면이 정해지면 다시 본다. 그동안 `resize_window` 로 크기를 잡지 않는다.
  ⚠ 이 노트북은 브라우저 기준 화면 **1440×900 · 배율 2** 다 (09-13 실측 : pane 1440×780 · 캔버스 2880×1560).
  미디어 쿼리 문턱(폭 1280 · 높이 700)보다 커서 **반응형 단계는 1920 과 같다** — 달라지는 것은 px 값이 화면에서 차지하는
  몫과 3D 화면 비율(1.85 vs 1.78)이다. 1920 에서 잰 수치(CHANGELOG v0.51 · v0.52 의 선 길이 · 자리 등)와 견줄 때는
  창 크기가 다르다는 것을 같이 말한다.
  ⚠ 1920 으로 돌아가면 : `resize_window` 로 잡은 크기는 **턴이 끝나면 앱이 푼다** (Viewport 메뉴로 붙잡히는 것은 Mobile ·
  Tablet 뿐 — 도구 안내 기준). 이 노트북에서 1920 을 에뮬레이트하면 캔버스가 3840×2160 이 되고 pane 에는 축소되어 보인다.
  사용자가 턴 사이에도 1920 으로 보려면 Chrome 개발자 도구의 기기 모드(Ctrl+Shift+M) 1920×1080.
- 물리 수치를 바꿀 때는 바꾼 값과 이유를 말하고 진행한다. `sim.c`, `sim.step`, `sim.damping`,
  스펀지 계수는 사용자 확인 없이 바꾸지 않는다. 발산하면 화면이 하얗게 날아간다.

## 지켜야 하는 불변식

0. **시뮬 텍스처의 네 채널은 x = 높이, y = 속도, z = 항적, w = 거품이다.**
   ⚠ **z 와 w 는 이 바다에서 기억을 갖는 유일한 층이다.** 나머지 표현(마루 색·백색·반짝임·
   반사)은 전부 '현재 파도 상태의 순수 함수'라, 아름다운 무늬로는 보여도 장소로는 안 읽힌다.
   새 표현을 넣을 때 "이건 기억이 필요한가"를 먼저 묻는다.
   ⚠ 거품 채널이 보는 너울의 시각·위상은 `water.js` 와 글자 그대로 같아야 한다
   (`uTimeQ` / `uSwellOff`). 어긋나면 거품이 마루가 아닌 자리에 남는다.

0-1. **배와 파도는 같은 시계를 쓴다 — 속도는 `월드/초` 가 아니라 `위상속도의 몇 배`로 적는다**
   (2026-09-06, `ocean-clock.js`). ⚠⚠ **`waveSpeed` 는 속도 손잡이가 아니라 길이 단위의 선언이다.**
   `BANDS` 의 ω = 0.62·√(g·k) 에서 0.62 는 배율이 아니다 — 심해 중력파의 월드 각속도가
   √(g·k/ℓ) 이므로 `0.62·ws = 1/√ℓ`, 즉 **ℓ = 1/(0.62·ws)² m/월드**다.
   `ws` 를 내리면 파도가 느려지는 게 아니라 **바다가 커진다** (ws 0.48 → 1월드 11.29m → 배 28m).
   `ws = 1.0` 이 정확히 물리 분산관계이고 그때 1월드 = 2.60m · 배 **13.01m** 다
   (⚠ 2026-09-07 정정 : 여기 오래 적혀 있던 6.45m 는 `lengthW` 2.48 시절 값이다).
   ⚠ 그래서 **월드/초를 손으로 적으면 `ws` 를 건드릴 때마다 그 값만 조용히 옛 축척에 남는다.**
   실제로 그랬다 — 배의 지상속도가 `driftSpeed + s×9.0` 이라 순항 `v/cp = 6.27` 이었다
   (배가 자기 앞 파도를 6배 추월). 화면 흐름의 89.7%가 파도가 아니라 내가 달린 것이었고,
   그게 *"보이는 느낌과 움직이는 흐름의 이질감"* 의 정체다.

## 하지 않는 것

- **`Reflector` / `Water.js` 를 넣지 않는다.** 씬을 프레임당 한 번 더 그리므로 정점이 2배가 된다.
  거울 카메라와 렌더타깃을 쓰는 방식도 마찬가지로 쓰지 않는다 — 한 번 넣어 봤다가 걷어냈다.
  ⚠⚠ **화면 좌표로 반사를 되읽으면 안 된다.** 그러면 반사가 화면에 못 박히고 물이 그 밑으로
  흘러가서, 파도 높이와 **무관한 도장**이 된다. 높이로 읽히게 만든 다른 층(마루 색·백색·명암)을
  정면으로 방해한다. 되읽는 좌표를 기울기로 미는 것도 소용없다 — 도장을 문지를 뿐이다.
  ⚠ **배가 물에 비치는 것은 광선으로 푼다** (`water.js` 의 `uBoatPos` 블록). 이 면의 실제
  법선으로 시선을 튕겨 그 광선이 배를 향할 때만 색을 얹는다. 그래서 배 쪽으로 기울어진 면에만
  뜨고, 마루 뒷면과 골에서는 끊긴다 — **파도가 반사를 만들지, 반사가 파도 위에 얹히지 않는다.**
  비용은 실측 0.024ms 다. 텍스처도 추가 렌더도 없다.
  ⚠⚠ **공중의 향수 부표가 물에 비치는 것은 렌더타깃 없이 푼다** (2026-09-03). 부표는
  위치·반지름·색을 전부 아는 **구**라서, 이 면의 법선으로 튕긴 광선이 그 구를 지나는지만
  보면 된다 (광선-구 교차). 화면 좌표를 안 읽으므로 '도장'이 될 여지가 구조적으로 없다.
  상이 부서지는 것도 공짜다 — 반사 광선이 이미 파면 기울기로 흔들려 있다.
  ⚠ **진짜 반지름으로만 재면 화면의 0.05% 라 안 보인다.** 세기를 6배 올려도 면적이 안 는다.
  ⚠ **그렇다고 사방으로 똑같이 넓히면 둥근 얼룩**이 되고 안개로 읽힌다. 물에 비친 상은
  **보는 쪽으로 길게 끌리므로** 허용 오차를 세로로 크게·가로로 조금 키운다 (`markReflSpread`).

  22 이상은 색면이다.
  ⚠⚠ 그것만으로는 상이 보는 쪽으로 끝없이 끌려 **어디가 그 부표의 자리인지 안 읽힌다.**
  부표의 **수직 발밑에서 잰 거리로 제곱 감쇠**를 곱해 못 박는다 (`markReflFall`).
  실측 (세기 0.6, 총 32개) : 감쇠 2 → 1.45% · 3 → 2.23% · 4 → 2.85% · 6 → 3.55% · 9 → 4.48%.
  확정 : 세기 0.45 · 폭 8 · 감쇠 3.
  ⚠ 비용은 측정 잡음 아래다 (1280×720, 구 6개, −0.09ms). 다만 **가까운 여섯 개만** 싣는다 —
  프래그먼트마다 도는 루프라 개수가 곧 비용이다. 배열 크기는 `MARK_REFL_MAX` 에서 생성한다.

(실측 : 최대 프레임시간 0.5ms → 150~235ms). 누른 뒤 HUD 의 GPU·rAF 를 같이 본다.

90도 어긋난 채 세 커밋을 갔다. 새 층을 넣으면 검증 보기부터 만든다.

## ⚠⚠ `hash2` 는 `[0,1]` 이 아니라 `[−0.5, +0.5]` 를 돌려준다

`water.js` 의 `hash2()` 는 끝에 `- 0.5` 가 붙어 있다. 네 점을 보간하면 분포가 가운데로
몰려 **전형값이 ±0.17** 이다 (최댓값 ±0.5 는 접힘 판정용이지 전형값이 아니다).

2026-09-06 에 이걸로 **한 층이 통째로 죽었다.** 새 노이즈 마스크의 문턱을 `[0,1]` 인 줄 알고
0.44 로 잡았는데 신호가 한 번도 그 위로 안 갔고, 같은 층의 법선 흩기에서 `−0.5` 를 또 빼서
법선이 상수만큼 한쪽으로 밀렸다. **화면 점유 0.00%.** 셰이더는 정상 컴파일됐고 콘솔도
조용했다 — 픽셀로 재고서야 나왔다.

- 문턱을 걸려면 먼저 펴라 : `clamp(n * 2.9 + 0.5, 0.0, 1.0)` 이면 문턱 0.5 가 면적의 절반이다.
- 법선·변위에 더할 때는 **그대로 더한다.** 이미 0 중심이다.
- 세기의 기준은 기존 `glitter` 의 실효값 **0.19** (`glitter 0.55 × 0.35`)다. 그 10배를 주면
  법선이 흩어져 하프벡터에 아예 안 맞고, 정반사 지수가 30만 돼도 결과가 0 이 된다.

## ⚠ 게이트를 곱으로 쌓지 않는다 — 셋이면 몇 레벨로 죽는다

높이·뭉침·앞뒤면처럼 1 미만인 게이트를 곱하면 실효가 곱으로 줄어든다. v0.11 의 '거품 게이트'가
화면 최대차 **3레벨**로 죽었던 것이 이것이고, v0.12.1 의 반짝임 거품도 같은 자리에 빠졌다.

- **각 게이트가 실제로 1 에 닿는지** 먼저 확인한다. 높이 게이트의 상단을 `h` 의 p90(0.793)
  위에 두면 그 층은 **한 번도 최대 세기로 안 그려진다** (불변식 13 과 같은 실패다).
- 마스크는 **좁은 창**으로 거의 이진이 되게 한다. 넓게 두면 패치가 아니라 회색 감쇠기다.
- 방향만 주고 싶은 게이트는 `mix(1 - amt, 1.0, gate)` 로 **바닥을 깐다.** 앞뒤면이 그 예다.

## rAF 가 안 도는 환경에서 검증하기 — 프레임을 직접 펌프한다

창이 실제로 화면에 안 보이면 브라우저가 rAF 를 아예 안 준다 (실측 : 2초에 **0프레임**,
`sim.qT` 증가 0). 그러면 파도·부력·발산처럼 **시간이 흘러야 드러나는 것**을 하나도 못 본다.

`tick()` 이 매 프레임 **자기 자신을 다시 등록**하는 성질을 이용해 콜백을 가로챈다.

```js
// ① rAF 를 큐잉 버전으로 바꾼다
window.__pump = { cbs: [], real: window.requestAnimationFrame.bind(window),
                  realCancel: window.cancelAnimationFrame.bind(window) };
window.requestAnimationFrame = (cb) => { window.__pump.cbs.push(cb); return 1; };
window.cancelAnimationFrame = () => {};

// ② 스크린샷 한 장으로 부트스트랩한다.
//    ⚠ 이게 핵심이다 — 스크린샷은 강제 페인트를 일으켜 **이미 진짜 rAF 에 걸려 있던**
//    콜백 하나를 실행시킨다. 그 tick 이 패치된 rAF 에 재등록하면서 큐에 들어온다.
//    (이 한 걸음이 없으면 큐가 영원히 비어 있다)

// ③ 이제 내가 돌린다
for (let i = 0; i < n; i++) {
  const cbs = window.__pump.cbs.splice(0);
  for (const cb of cbs) cb(performance.now());
  await new Promise(r => setTimeout(r, 16));     // setTimeout 은 창이 가려져도 돈다
}

// ④ ⚠⚠ **반드시 원복한다.** 안 되돌리면 사용자가 창을 띄워도 앱이 얼어 있다
window.requestAnimationFrame = window.__pump.real;
window.cancelAnimationFrame  = window.__pump.realCancel;
window.__pump.cbs.splice(0).forEach(cb => window.__pump.real(cb));
```

**긴 시간이 필요하면 시계를 합성한다.** `performance.now` 를 고정 증분으로 바꾸면
`THREE.Clock.getDelta()` 가 그 값을 읽으므로 벽시계 비용 없이 앱 시간을 민다 —
실측 : **30초를 3.1초에** 재현했다 (프레임당 1/60초 × 1800). 끝나면 같이 원복한다.

| 이 방법으로 되는 것 | 실측 예 |
|---|---|
| 누적 발산 (30초 방치) | 물 밝기 202.7~210.6 안정 · NaN 0 |
| 부력 | 배 y 0.082~0.432 로 파도를 탄다 |
| 선회 반경 | 30초 우선회에 `scroll.z` 진폭 7.3 ≈ 지름 2×3.8 |
| 층의 프레임간 코히런스 | 반짝임 거품이 더한 흔들림 −0.21 (= 안 끓는다) |

⚠⚠ **부트스트랩과 펌프를 같은 호출에 넣지 않는다.** 패치 직후에는 큐가 비어 있어 펌프가
아무것도 안 하고, 그러면 **리로드 직후의 얼어붙은 장면(t≈0)** 을 계속 재게 된다.
시뮬의 거품·항적 채널은 시간이 지나야 차오르므로 그 상태에서는 **점유가 0%** 로 나온다 —
2026-09-06 에 하마터면 "셰이더를 고쳐서 거품이 죽었다" 고 오진할 뻔했다.
**패치 → 스크린샷 → `window.__pump.cbs.length >= 1` 확인 → 그 다음에 펌프.**

⚠⚠ **펌프는 매 프레임 유니폼을 `PARAMS` 로 되돌린다.** `uni.uXxx.value` 를 직접 밀고 펌프를
돌리면 그 값이 즉시 사라져 스윕이 전부 같은 숫자로 나온다. 펌프와 같이 쓸 때는
**`PARAMS` 를 바꾸고 한 틱 민 뒤** 읽는다. (렌더만 할 때는 유니폼 직접 쓰기가 맞다.)

⭐ **시각 · 순서만 잴 때는 그리기를 끈다** (2026-09-13). 1920 에서 펌프 한 장이 0.25~0.45초라 170장이 브라우저 도구의
**45초 제한**에 걸렸다. `PB.renderer.render = function () {}` 로 두면 부표 · 선의 CPU 갱신은 그대로 돌고 한 장이 ms 대다
(원래 함수를 챙겨 두고 반드시 돌려놓는다). `performance.now` 를 1/60초씩 합성하면 앱 시각이 정확히 맞는다.
⚠ 되돌리는 코드는 **따로 한 번** 부른다 — 긴 펌프 끝에 붙여 두면 시간 초과로 멈췄을 때 시계가 멈춘 채 남는다.

⚠⚠ **되지 않는 것은 성능이다.** 패널이 합성을 안 하므로 GPU 타이밍이 무의미하다 —
`gl.finish()` 를 넣고도 프레임 0.4ms(= 2500fps)라는 값이 나왔다. HUD 의 `물 4.35ms`,
`블룸 3.05ms` 같은 수치는 **보이는 창에서만** 유효하다. 여기서 잰 ms 를 인용하지 않는다.

⚠ 그리고 **'느낌' 은 끝까지 판정할 수 없다.** 이 방법은 숫자를 주지 그림을 주지 않는다.
파도가 자연스러운지, 거품이 어색한지는 사람이 보이는 창에서 최소 10초를 봐야 한다.

## GPU 비용을 잴 때 — **타이머가 아니라 면적을 센다**

⚠⚠ **숨겨진 패널에서 GPU 타이머는 거짓말을 한다.** `EXT_disjoint_timer_query` 로 재면
**수면 셰이더를 통째로 꺼도 같은 ms** 가 나온다 (2026-09-06 실측 : 1.81ms 고정).
GPU 가 프래그먼트 작업을 실제로 안 하기 때문이다. 여기서 낸 ms 를 인용하지 않는다.

대신 **검증 보기 12 (비용 지도)** 로 *어느 층이 몇 픽셀에서 몇 번 도는가* 를 센다.
픽셀당 해시 수를 원색 **계단**으로 그린다 — 연속 램프는 되읽어 역산할 때 불안정하다.

실측 기준선 (2026-09-06, camDist 3.24) :

```
물이 화면의 73.1%              픽셀당 평균 해시 16.85
바닥 45.4% · +반짝임 거품 49.6% · +worley 5.0%
```

⚠⚠ **"비싸 보이는 층" 과 "비싼 층" 은 다르다.** worley 흰 거품은 해시 18회로 가장 무거워
보이지만 **물의 5% 에서만** 돌아 실제 몫이 작다. 진짜는 **물 전체에서 도는 바닥**이다.
비용은 `해시 × 면적` 이지 해시가 아니다 — 면적을 먼저 본다.

비용 스위치 : `glitterOct2` 0 · `microWarp` 0 · `sparkCull` ↑ · `foamCull` ↑ ·
좌상단 바의 **끄기** 줄 (전부 한 번에).

## 화면을 픽셀로 잴 때 — 기본 프레임버퍼에서 읽지 않는다

앱의 rAF 가 도는 동안 `gl.readPixels` 를 기본 프레임버퍼에 대고 부르면, 두 번 찍은
A/B 가 **같은 화면**으로 돌아온다 (실측 : dr−dg 범위가 [0,0]). 층을 껐다 켠 차이가
0 으로 나오므로 "이 층은 아무것도 안 한다" 는 잘못된 결론이 나온다.

렌더타깃에 그리고 `readRenderTargetPixels` 로 읽는다. 그러면 A/B 가 실제로 갈린다.
그리고 A/B 사이에 `step()` 을 넣지 않는다 — 파도가 흘러서 그 차이가 층의 몫보다 커진다
(같은 설정이 0.05% 와 0.26% 로 나왔다).

⚠ **파라미터를 훑을 때도 파도를 얼린다.** 설정 사이에 시뮬을 돌리면 스윕이 단조롭지 않게
나와서 엉뚱한 값을 고른다 — 실제로 치우침 스윕이 뒤죽박죽이라 두 번 잘못 짚었다.
얼린 뒤 스윕하니 단조로워졌다. 단, **한 장면만으로 정하지 않는다** (상태마다 비율이
달라진다). 얼린 스윕을 3~4 상태에서 반복해 평균 낸다.

## 배가 이상할 때 — 부력 프로브를 켠다

`PB.params.showProbes = true` (또는 패널의 '계측' 묶음). 개발 빌드 전용이다.

프로브 자리마다 **청록 원반**(배가 읽었다고 믿는 수면 높이)과 **세로 막대**(그 수면에서
선체 바닥까지의 간격)를 그린다. 막대가 붉으면 그 자리가 잠긴 것이다.

- 원반이 파면 위에 얹혀 있으면 정상이다. **물에 뜨거나 잠겨 보이면 CPU/GPU 가 갈라진 것**
  (불변식 2). 배는 GPU 수면을 안 보고 `swellCPU` + `sim.sampler()` 로 따로 계산한다.
  `gerstner` 를 CPU 쪽에 안 넘기는 실수가 이 증상으로 나타난다.
- 막대 길이가 프로브마다 다르면 배가 파도를 버티고 있는 것이다. **전부 같으면 파도에
  그대로 누운 것**이다 (`rightLimit` 이 안 먹는 상태).
