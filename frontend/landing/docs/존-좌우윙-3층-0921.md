### 1-2. 층의 성격 — 이름과 실제가 한 칸 어긋난다

화면으로 확인한 것 (빨강 바탕에 합성해서 봤다) :

| 원본 이름 | 코드 이름 | 실제 그림 |
|---|---|---|
| 맨앞 | `near` | **크게 확대된 한 줌.** 초점이 나가 있거나 대상이 몇 개뿐이다. **상자가 가장 작다** |
| 중앙 | `mid` | **가장 선명하다.** 주된 실루엣 |
| 맨뒤 | `far` | 넓게 퍼진 바닥 판. 작은 요소가 많고 **상자가 가장 크다** |

⚠ **선명도 순서가 `mid` > `far` > `near` 다** — 이름만 보면 거꾸로다 (라플라시안 실측 : mid 15~57 ·

⚠⚠ 그래서 **층을 가르는 잣대는 선명도가 아니라 상자 크기다** (§1-5-3).
⚠ `near` 의 상자가 작은 것은 **원고에서 실제로 작게 놓였다는 뜻이지 해상도가 모자란다는 뜻이 아니다**
  (1920 화면에서는 509px 이 그대로 509px 로 앉는다 — §3-2). 블러 이미지라 그보다 커져도 티가 안 난다.

### 1-3. 변환 — PNG → WebP + 알파

도구는 **ffmpeg 9.0.1 (libwebp)** 다. 이 노트북에 `cwebp` · `sharp` · Pillow 가 없다.

```
ffmpeg -i <src>.png \
  -c:v libwebp -lossless 0 -q:v 82 -compression_level 6 -preset picture -pix_fmt yuva420p \
  <out>.webp
```

- ⚠⚠⚠ **크기를 건드리지 않는다.** 원본 픽셀 수가 곧 1920×1080 원고 안에서의 배치 크기라
  (§3-2), 줄이는 순간 **구도 정보가 사라진다.**
  09-21 오전에는 §5 의 권장(근경 1536 · 중경 1280 · 원경 1024)을 따라 긴 변 1280 으로 줄였는데,
  사용자가 원고 캔버스를 알려 주면서 되돌렸다. 값을 잃는 대가에 비해 **얻는 것은 4.2MB → 4.0MB 뿐이었다.**
- `-pix_fmt yuva420p` 로 **알파를 살린다.** 확인 : 변환본을 단색 위에 합성해 봤을 때 테두리 띠·배경 잔상 없음.
- 색차는 420 서브샘플링이지만 **알파는 WebP 에서 전해상도**라 실루엣이 뭉개지지 않는다.

### 1-5-1. ⚠⚠ 우디 맨앞은 **좌·우가 같은 그림이라 오른쪽을 반전했다**

알파 경계 상자를 27장 전부 재 보니 **오른쪽 판인데 내용이 왼쪽 변에 붙은 것이 하나** 있었다 :

| | 상자 | 내용 | 여백 |
|---|---|---|---|
| `우디 왼쪽 맨앞` | 443×342 | x 0..437 | 왼 0 |
| `우디 오른쪽 맨앞` | 443×342 | x 0..437 | **왼 0** ← 오른쪽 판인데 왼쪽에 붙어 있다 |

단색 위에 나란히 합성해 보니 **같은 그림**이었다 (md5 는 다르지만 화면이 같다).
그대로 두면 오른쪽 아래 모서리에 **빈 자리**가 생기고 블러 덩어리가 화면 안쪽에 떠 있게 된다.

→ 변환할 때 `hflip` 을 한 번 먹였다. ⭐ 이건 §5 가 **원래 권한 방법**이다 —
  *"좌우는 같은 이미지를 반전해 쓴다 … 자연물이라 반전이 티나지 않는다."*
  더구나 이 판은 **초점이 나간 블러**라 반전이 보일 수가 없다.

```
ffmpeg -i "우디 오른쪽 맨앞.png" -vf hflip … woody-right-near.webp
```

⚠ 좌판 27장이 전부 왼쪽 변에, 우판 26장이 전부 오른쪽 변에 붙어 있다.
  (`fruity-left-far` 만 왼 18 · 오 3 인데, 내용이 상자를 거의 다 채우는 판이라 문제가 아니다.)

### 1-5-2. ⚠⚠ 프루티 오른쪽은 **맨앞·맨뒤 파일 이름이 서로 바뀌어 있었다**

2026-09-21 사용자 : *"파일 중 프루티 맨앞과 맨뒤가 바뀜 수정좀"*.

원본 이름 그대로 넣으면 `fruity-right-near` 가 1180×931 의 **선명한 넓은 판**, `fruity-right-far` 가
349×572 의 **블러 한 줌**이 된다 — 다른 여덟 향조와 정반대다. 단색 위에 합성해 눈으로 확인했다.

→ 변환할 때 **두 원본을 교차**시켰다 :

```
ffmpeg -i "프루티 오른쪽 맨뒤.png"  … fruity-right-near.webp
ffmpeg -i "프루티 오른쪽 맨앞.png"  … fruity-right-far.webp
```

⚠⚠ **원본을 다시 받으면 이 교차와 §1-5-1 의 `hflip` 을 같이 다시 먹인다.** 원본 PNG 는 저장소 밖
  (사용자 바탕화면)에 있어 스크립트를 커밋해 둘 곳이 없다 — **예외 둘은 이 문서가 유일한 기록이다.**

## 2. 등장 순서 — `phase.js` 의 트랙을 여섯으로

사용자 : *"왼쪽 2, 오른쪽 2, 왼쪽 3, 오른쪽 3, 왼쪽 1, 오른쪽 1 순서로 좌우에서 시작하면 됨"*
(1 = 맨앞 `near` · 2 = 중앙 `mid` · 3 = 맨뒤 `far`)

→ **중앙 → 맨뒤 → 맨앞**, 각 층 안에서 **왼쪽 먼저**.

### 2-1. ⚠⚠ 층 시차가 좌우 시차보다 **커야** 한다

지금 표는 좌우 시차가 0.22s 다 (2026-09-10 에 0.14 → 0.22 로 늘렸다 — `phase.js` 주석).
층 시차를 그보다 작게 잡으면 시작 시각이 `좌중(0) → 좌뒤(0.18) → 우중(0.22)` 로 **뒤섞여 요청한 순서가 깨진다.**

그래서 **좌우 0.18s · 층 0.30s** 로 다시 고른다. 시작 시각이 엄밀히 커진다 :

| 트랙 | 구간 | 커브 | 시작 |
|---|---|---|---:|
| `openLmid` | 0.00 → 1.10 | `outCubic` | 0.00 |
| `openRmid` | 0.18 → 1.28 | `outCubic` | 0.18 |
| `openLfar` | 0.30 → 1.40 | `outCubic` | 0.30 |
| `openRfar` | 0.48 → 1.58 | `outCubic` | 0.48 |
| `openLnear` | 0.60 → 1.70 | `outCubic` | 0.60 |
| `openRnear` | 0.78 → 1.88 | `outCubic` | 0.78 |

- 판 하나가 드는 시간은 **1.10s** 로 같다 (예전 좌 1.15 · 우 1.18 과 같은 급이다)
- 마지막 판이 **1.88s** 에 선다 — `look`(0 → 2.00)이 여전히 가장 늦으므로 **`ENTER_DUR` 은 2.00s 그대로다**
- 커브는 전부 `outCubic` 이다. ⚠ `outExpo` 로 바꾸지 않는다 — 2026-09-10 에 *"마지막 3% 를 남은 시간 내내 좁혀"* 가장자리에 틈이 보였다 (`phase.js` EASE 주석)

### 2-2. 퇴장은 여섯이 **같이** 나간다

`leave` 표는 손대지 않는다 — 여섯 트랙 모두 예전 `openL`/`openR` 과 같은 `[0.25, 1.20] inCubic` 이다.

⚠ §3 의 규율 그대로다 : *"들어온 순서의 역순이 아니다 — 역순으로 재생하면 되감기로 읽힌다.
  그래서 퇴장에는 좌우 시차가 없다 — **닫힐 때만 순서가 있다.**"*
  층 시차도 같은 이유로 안 넣는다. 나가는 3층은 어차피 서로 다른 속도로 미끄러지므로(§3-2 의 패럴랙스) 공간감은 유지된다.

## 3. `gate.js` — 한 층에서 세 층으로

### 3-1. 깊이가 공간감이다

§5 :

> 깊이가 다른 판이 **서로 다른 속도로 어긋나야** 그게 공간이 된다 — 그게 멀티플레인이다.

판은 `camBase`(패럴랙스로 밀기 **전**의 카메라 자리)에서 `fwd × dist` 에 선다.
카메라가 마우스로 `off` 만큼 밀리면 판이 화면에서 어긋나는 각은 **`off / dist`** 다 —
즉 **움직이는 양 ∝ 1/dist** 다. 그래서 손잡이를 거리가 아니라 **움직임(`gateMove*`)으로 적고**
거리를 `gateDist / gateMove` 로 역산한다. 정하고 싶은 것이 거리가 아니라 움직임이라서다.

### ⚠⚠⚠ 맨앞이 **가장 적게** 움직인다 — 교과서와 반대다

2026-09-21 사용자 지시 :
*"맨 앞에 배치되어있는 이미지는 거의 움직이면 안될듯함 **하단에 바다가 자꾸 삐져나와보임** ·
그 가중치 만큼 뒤로 갈수록 더 움직이면 될듯"*

까닭은 이 자산의 생김새다 — `near` 는 화면 **아래 모서리를 막는 판**이라, 그것이 움직이면
막고 있던 자리에서 바다가 드러난다. **물리적 원근보다 프레임이 안 새는 것이 먼저다.**

| 층 | `gateMove` | 거리 | 화면에서 |
|---|---:|---:|---|
| `near` | **0.15** | 107 | **거의 안 움직인다** — 아래 모서리를 붙잡는다 |
| `mid` | 0.50 | 32 | 기준 |
| `far` | **1.00** | 16 | 가장 많이 움직인다 |

⚠ 처음 고른 값은 `0.28 / 1.00 / 1.75` 였는데 같은 날 저녁에 사용자가 *"너무 심하게 이미지가 움직인다 …
  약간만 움직임 덜하게"* 라고 해서 **셋을 같은 비로 57% 까지 내렸다.** 층 사이 관계는 그대로다.

⚠ 그래서 `near` 가 카메라에서 **가장 멀리** 서는데 그리기는 **맨 앞**이다.
  깊이를 안 읽으므로(`depthTest:false`) 모순이 아니지만 헷갈리기 쉬워 코드에도 적어 뒀다.

⭐ **`dist` 를 바꿔도 화면에서의 크기는 안 변한다** — 판 폭을 `halfW = tan(fov/2)·dist·aspect` 에서 *화면 비율로* 내기 때문이다.
  정하는 것은 **시차와 기울기**뿐이다. (§5 가 말한 "층을 늘리려면 `SRC` 에 줄을 더하면 된다" 가 이 구조다.)

`renderOrder` 는 `near 22 · mid 21 · far 20` 이다 — ⚠ 깊이를 안 읽으므로 **순서가 곧 앞뒤다.**
수면 타이포(0)보다 뒤에 그린다 = 앞에 온다. 이 규약은 예전 그대로다.

기울기도 같은 비율을 탄다 — 마우스로 꺾이는 양 `gateTiltMouse` 에 `gateMove` 를 곱한다.
덜 움직이는 판이 덜 꺾이므로 시차와 방향이 맞는다. ⚠ **새 파라미터를 만들지 않는다** (움직임 하나에서 파생시킨다 — 불변식 2 와 같은 규율).

### 3-1-1. ⚠⚠ 색 — 시간대 색조를 **끈다**

2026-09-21 사용자 : *"오브젝트가 지금 그림자의 영향을 받고 있어서 매우 어둡게 표현되고있음 ·
원본의 색상을 그대로 표현되었으면"*.

**조명 탓이 아니다** — 판은 `MeshBasicMaterial` 이라 빛을 아예 안 받는다.
범인은 `CONFIG.times[].gateTint` 였다. 재질 색이 텍스처에 **곱해지는데** :

| 시간대 | `gateTint` | 텍스처가 눌리는 비율 (R / G / B) |
|---|---|---|
| 낮 | (없음) | 100% |
| 저녁 | `#9C8290` | **61% / 51% / 56%** |
| 밤 | `#394056` | **22% / 25% / 34%** |

그 색은 2026-09-11 에 **암석 한 장**에 맞춰 고른 값이다 (`config.js` 주석도 *"암석 — 역광에 선 보랏빛 그늘"*).
잎·꽃·과일이 온 지금은 안 맞는다 — 초록이 회보라로 죽는다.

→ `gateTimeTint` 로 빼고 **기본을 0** 으로 뒀다. 1 이면 예전과 비트 단위로 같다.
⚠ 다시 켤 일이 생기면 **`times.js` 의 색부터 이 자산에 맞춰 다시 고른다.** 지금 값을 그대로 켜지 않는다.

⚠ **밤(`sceneTime 2`)에서는 잎이 어두운 바다 위에 밝게 남는다** — 실루엣이 아니라 '앞에서 조명을 받은 것' 으로
  읽힌다. 원본 색 그대로 내보낸 결과이고 깨진 것은 아니다. 밤만 눌러야 한다고 판단되면
  `gateTimeTint` 를 0.3~0.5 쯤으로 올리는 것이 아니라 **`times.js` 의 밤 색(`#394056`)을 덜 어두운 값으로
  다시 고르는 쪽**이 맞다 — 지금 색은 RGB 를 22/25/34% 로 눌러 향조 색이 통째로 사라진다.

### 3-1-2. ⚠⚠⚠ 기울기가 **바깥 아래 모서리를 띄운다** — 세로 보정을 더한다

2026-09-21 사용자 : *"카메라가 조금 위에있어서 바다 모서리 및 하단 띄워져서 부분이 자꾸 보임 ·
조금 이미지를 하단으로 내려야하나? 실측좀 해서 너가 확인해봐야겠는데"*

**실측했다 — 카메라 탓이 아니라 `gateTilt`(판의 안쪽 기울기 14°) 탓이다.**
판이 **제 가운데를 축으로** 돌아서 바깥 모서리가 카메라에서 멀어지고, 멀어진 만큼 투영이 작아져
아래 변이 위로 당겨진다. `needX` 가 가로로 하던 보정의 **세로 짝이 없었다.**

1920×1080 · GREEN · 바깥 아래 모서리가 화면 아래(y 1080)에서 **뜬** px :

| 기울기 | `far` | `mid` | `near` |
|---|---:|---:|---:|
| **14°** (그때 기본값) | **+12.5** | **+36.0** | **+18.6** |
| 0° | −57.8 | −22.8 | −5.3 |

(+ 가 틈이다. 기울기만 0 으로 놓으면 셋 다 화면 아래로 내려간다 — 이게 원인을 가른 실험이다.)

바깥 모서리의 깊이는 `dist + sign·(w/2)·sin(tY)` 다 (로컬 +x 의 전방 성분이 `sin tY` 이고 바깥쪽
로컬 x 가 `sign·w/2`). 그 깊이에서 화면 아래는 `halfH × depth/dist` 이므로 —

```
needD = max(0, sign · sin(tY)) × w / (2·dist)      →  y 에서 halfH × needD 를 더 뺀다
```

⚠⚠ **절댓값이 아니다** — 마우스가 판을 반대로 꺾으면 바깥 모서리가 오히려 **가까워져** 저절로
내려간다. 그때까지 내리면 그림 밑동만 더 잘린다 (`needR` 과 같은 한쪽 보정).

**보정 뒤 실측** (1920×1080 · 마우스 가운데) — 바깥 아래 모서리가 여섯 판 모두 **정확히 y 1080**,
안쪽 아래 모서리는 50~162px 화면 아래로 넘어간다 (기운 판이라 아래 변이 비스듬하다 — 정상이다).

⚠ 딱 0px 이면 서브픽셀 반올림에서 실오라기가 비칠 수 있어 `gateDrop` 을 0 → **0.004**(1080 에서 4.3px)로 뒀다.
**마우스를 네 모서리로 밀어 가며 잰 최소 여유는 +3.8 ~ +5.9px 로, 어디서도 음수가 안 된다.**

### 3-2. ⭐⭐⭐ 크기 — **손으로 정하지 않는다. 원고 캔버스(1920×1080)에서 나온다**

2026-09-21 사용자 :
*"연출 시점에 카메라를 고정해놓고 연출시에 **외곽에 이미지가 가득차게** 설정해야함 ·
이 이미지가 하단에 잘려있는 이유가 연출 이미지를 만들때 **1920 x 1080** 에 왼쪽 이미지는
**왼쪽 하단**에 배치하고 오른쪽 이미지는 **오른쪽 하단**에 딱 맞게 연출 구도를 이미 다 만들어두었음"*

이 한마디가 앞의 모든 크기 손잡이를 지웠다. **원본 PNG 픽셀 수가 곧 그 캔버스 안에서의 배치 크기다** —
잘라 낸 상자가 내용에 딱 맞고(§1-1) 바깥쪽 아래 모서리에 뿌리를 두므로, 크기만 알면 구도가 복원된다.

**검증** — 54장 중 1920 이나 1080 을 넘는 것이 **하나도 없고**, `green-right-far` 가 **정확히 1080** 이다
(캔버스 위아래를 꽉 채운 판). 최대 폭은 `amber-right-far` 1666 이다.

```
s = max(화면폭 / 1920, 화면높이 / 1080) × gateScale     ← CSS 의 background-size: cover 와 같다
판 폭 = 원본 px 가로 × s      판 높이 = 원본 px 세로 × s
```

- **16:9 에서는 가로·세로 배율이 같아 원고 구도가 픽셀 단위로 재현된다.**
- 다른 비율에서는 **큰 쪽 배율**을 써서 원고가 화면을 덮게 한다 — 넘치는 쪽은 **안쪽·위쪽**으로 흐르므로
  바깥 아래 모서리의 구도는 그대로고, 바깥이 비는 일이 없다 (*"외곽에 이미지가 가득차게"*).
- 배율은 **화면 비율에서 나오므로 층이 달라도 같다** → 세 층의 상대 크기가 원고 그대로 유지된다.

⚠⚠⚠ **그래서 변환할 때 줄이지 않는다** (§1-3). 09-21 오전에는 긴 변 1280 으로 줄였는데,
그러면 `img.width/height` 가 더 이상 원고 좌표가 아니라 **구도 정보가 통째로 사라진다.**

⚠⚠ **없앤 것들** — `gateWidth`(0.58) · `gateMinH`(0.55) · 층별 크기 배수(1.00 / 0.92 / 0.86) ·
`IMG_ASPECT = 1536/1024` 상수. 손으로 고르던 값이 전부 원고에 이미 들어 있었다.
남은 손잡이는 **`gateScale` 하나**(기본 1 = 원고 그대로)다.

⚠ 비율은 텍스처가 실린 뒤 `tex.image.width/height` 에서 읽는다 — 그래서 **텍스처가 오기 전에는
판을 안 보인다.** 모르는 채로 세우면 한 프레임이 찌그러진 채 뜬다.

### 3-3. 지연 적재 — 존에 들어갈 때 그 향조만

⚠⚠ **48판을 다 올리면 GPU 가 1.2GB 다.** 1280×900 RGBA 한 장이 약 4.6MB 이고 밉맵까지 치면 6MB 가 넘는다.

- 향조 6판은 **그 존에 들어갈 때** 만든다 (`gate.use(key)`)
- **최근 `gateCache` 개 향조**(기본 2)만 남기고 나머지는 `dispose()` 한다 — 12판 ≈ 55MB
- `gate.preload(key)` 를 밖으로 연다. `main.js` 의 `arriveAt` 과 `startTravel`(먼 곳 이동 목표에 존 키가 있을 때)이 부른다 —
  ⚠ 안개 전환이 1~2초라 그동안 받으면 **연출이 시작될 때 이미 와 있다**

⚠ 못 읽은 판은 **조용히 쉰다** (`console.warn` 한 줄 + 그 판만 안 보인다). 우디가 지금 그 상태다 (§1-5).

### 3-4. 아주 느린 sway — §5 가 권한 한 줄

> 살아 있는 느낌이 필요하면 판마다 **위상이 다른 아주 느린 sway 한 줄**(진폭 0.2° 안팎)이면 된다.
> 인터랙션이 아니라 아이들 모션이라 비용이 사실상 0 이다.

`gateSway`(도, 기본 **0.18**) · `gateSwaySpeed`(기본 0.08Hz). 판마다 위상이 다르다 (인덱스에서 파생).
⚠ 기울기 보정식(`needX`/`needY`)이 **최종 각**을 받으므로 sway 를 더해도 가장자리에 여백이 안 생긴다.
⚠ 0 으로 두면 예전과 비트 단위로 같다.

### 3-5. 개별 hover 는 **넣지 않는다**

§5 의 결론 그대로다 — 레이캐스트 대상이 늘고(`marks.pick` 과 부딪친다), 프레임은 배경이라 반응하면 누를 수 있다는 힌트가 되고,
카메라 하나만 움직이면 6판이 전부 다른 속도로 움직이므로 **판마다 코드를 쓸 이유가 없다.**

⚠⚠ **1920×1080 으로 재는 법** (§3-1-2 의 실측이 이 방법이다) — pane 을 화면에 띄워 둔 채
  `resize_window 1920×1080` 을 잡고, **`PB.params.siteHeader = 0; PB.apply();` 로 자리표시 헤더를 끈 뒤**
  `window.dispatchEvent(new Event('resize'))` 를 한 번 보낸다. 그래야 무대가 1920×**1080** 이 된다 —
  끄지 않으면 헤더 90px 을 뺀 1920×990 이라 세로 비율이 달라진다.
