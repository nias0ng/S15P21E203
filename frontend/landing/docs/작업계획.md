## 0. 전제가 바뀌었다

### 0-1. 돛단배가 정식 요구사항이 됐다

08/31 개정으로 MAP 요구사항이 11개 → 24개가 됐고, **늘어난 13개가 전부 항해 메커니즘**이다.

| ID | 기능명 | 3D 에 요구하는 것 |
|---|---|---|
| **MAP-21** | 향 지도 탐색 위치(돛단배) 이동 | 돛단배 = 현재 탐색 위치. 탐색 행동이 생기면 **즉시 이동** |
| **MAP-12** | 취향 기반 위치 이동 제안 | 제안 모달 → YES 면 그 방향으로 이동, NO 면 제자리 |
| **MAP-24 / 22** | 향해 일지 | 과거 탐색 지점 이력 → 선택하면 **그 위치로 복원** |
| **MAP-23** | 취향 기반 지도 위치 갱신 | 누적 행동 데이터로 돛단배 위치가 스스로 갱신 |
| **MAP-08** | 내 취향 영역 표시 | 취향 영역 + 돛단배 + **데이터 클러스터 Top View 전환** |
| **MAP-16/17/18** | 비회원 임시 탐색 | 로그인 없이 전부 가능. 이탈 시 저장 안내 |
| **MAP-19/20** | 회원 탐색 상태 유지 | 지도 위치·취향 위치·YES/NO 응답 저장 후 복원 |
| **TST-03** | 취향 테스트 | 대표 향 4개 선택 결과가 **지도 초기 위치**를 결정 |

**우선순위도 여기 몰려 있다.** 요구사항 정의서 (2) 기준 **P1 = MAP 전부 + NLR(자연어)** 뿐이고,
계정·상세·추천은 P2, 진열대·컬렉션·커뮤니티는 P3다.

### 0-2. MAP-08 은 "취향 영역" 으로 확정됐다 (2026-08-31, 사용자 확정)

기능명세서에서 두 갈래로 갈려 있던 것 — 팀도 파일명에 `[이거 수정해야할듯요 너무 향수로 되어 있어서?]` 라고 적어둔 상태 — 을 사용자가 확정했다.

> **개인화 추천 지도 표시 = 작게 띄워져 있는, 또는 Top View 로 확인했을 때 사용자가 선호하는 향 위치 영역.**

이 확정이 3D 설계를 크게 단순화한다.

```
멀리 / Top View  →  향 영역 (MAP-08)        — water.js 의 수면 얼룩이 그대로 구현체
가까이 / 항해 시점 →  향수 노드 (MAP-05/06/07) — 메시 + Raycaster, 근접 시에만 존재
```

개별 향수 오브젝트가 **항상 존재할 필요가 없다.** Raycaster 대상이 수십 개씩 상주하지 않으므로
성능 부담이 크게 준다. `grid.js` 가 이미 3단 LOD 로 등고선을 갈아끼우고 있으니 개념도 같다.

### 0-3. 페르소나가 말하는 것 — 3D 지도는 메인 유저를 위한 것이 아니다

| 유저 | 페인 포인트 | 3D 지도와의 관계 |
|---|---|---|
| **메인** — 커뮤니티 애호가 | **경유 과정이 지나치게 길다** | ⚠ 항해는 경유를 **늘린다** |
| 서브1 — 추천받고 싶은 사람 | 시향이 너무 많아 코가 피곤 | 개인화 추천의 시각화 |
| 서브2 — 입문자 | **취향의 정의·표현·언어화가 어렵다** | ✅ 말 대신 **위치**를 준다. 이게 지도의 존재 이유 |

**설계 원칙 하나가 여기서 나온다** — 3D 지도는 첫 화면이되, **메인 유저를 위한 우회로가 같은 화면에 있어야 한다.**
검색바(COM-05)와 커뮤니티 진입이 항해를 거치지 않고 닿아야 한다.
지금 검색바는 "배를 그 방향으로 돌리는" 입력이라 오히려 경유를 늘리는 쪽이다 — 나중에 갈라야 한다.
Chanel Factory 5 가 같은 문제를 "3D 공간 탐색" 과 "일반 제품 페이지" 두 갈래 진입로로 풀었다.

## 1. 지금 코드와 스펙 사이의 최대 충돌

### 1-1. 좌표계 — 순환하는 바다 vs 좌표가 있는 지도

| | 현재 구현 | 스펙 요구 |
|---|---|---|
| 위치 | `nav.scroll` = 배가 나아간 누적 거리 | 지도 위 절대 좌표 |
| 향 영역 | **100 단위로 x·z 순환** (`zones.js` 의 `wrapP`) | 유사도 데이터 기준 고정 배치 (MAP-01) |
| 이동 | 조타로만 연속 이동 | **즉시 이동 / 복원** (MAP-21, MAP-24, MAP-20) |
| 줌 | 없음 (속도에 따른 후퇴·상승뿐) | 확대·축소 (MAP-01), Top View (MAP-08) |

**`zones.js:88` 의 `wrapP` 가 핵심 장애물이다.** 어느 방향으로 가도 같은 4개 영역이 반복되므로
"이전 탐색 지점으로 돌아간다"(MAP-24)가 성립하지 않는다.

다행히 **`nav.scroll` 자체는 이미 절대 위치**다. 순환은 `zones.js` 표시 단계에서만 일어난다.
즉 유한한 좌표 공간으로 바꾸는 것은 `zones.js` 국소 변경이고, "카메라 고정 + 물이 흐른다"는 연출은 그대로 유지된다.

### 1-2. 카메라를 움직이는 순간 터지는 지뢰

```js
// grid.js  g.uni.uCam.value.set(0, camZ);
// water.js   uni.uCam.value.set(0, camZ);
```

거리 페이드의 원점 **x 가 0 으로 하드코딩**돼 있다. 카메라를 X축으로 옮기거나 Top View 로 올리는 순간
페이드 기준이 배(원점)에 남아 **원경이 비대칭으로 지워지고 반대쪽 지평선에 선이 뜬다.**
원인이 셰이더 유니폼이라 증상만 보고는 못 찾는다.

> **Top View(MAP-08)·도착 샷·인트로 카메라를 만들기 전에 이 두 줄을 먼저 고치고,
> 화면이 그대로인지 확인한 뒤에 카메라 작업을 시작한다.**

### 1-3. 입력이 "클릭"을 표현할 수 없다

`input.js` 의 `pointerdown` 이 곧 드래그 시작이자 자동 조타 해제다. 포인터 절대 좌표(`clientX/Y`)를
저장하지 않아 Raycaster 용 NDC 를 만들 수 없다. 이 상태로 향수 클릭 오브젝트(MAP-05)를 얹으면
**클릭할 때마다 자동 항해가 끊기고, 살짝 흔들린 클릭이 조타로 샌다.**

대응 : `pointerdown` 에서 좌표·시각 기록 → `manual()` 호출과 `drag.on` 활성화를 **이동거리 6px 를 넘긴
첫 `pointermove`** 로 미룬다 → `pointerup` 에서 임계값 이하면 클릭으로 승격.

### [2단계] 아트 디렉션 확정 — *한 번에 끝낸다* ✅ **완료 (2026-09-01)**

> **실제로 해보고 알게 된 것 — 아래 원래 계획과 갈라진 지점들**
>
> **1. 물리적 `dot(N, L)` 은 이 씬에서 작동하지 않는다.** 계획의 한 줄짜리 레시피
> (`normalize(vec3(-gr.x*uHScale, 1.0, -gr.y*uHScale))`)를 그대로 넣었더니 화면이 그대로였다.
> 재보니 이 바다는 월드 단위로 거의 평평하다 — **너울 기울기 중앙값 0.036**, 법선이 수직에서
> 2도밖에 안 기운다. 내적이 0.61~0.69 사이에서만 움직여 진폭 0.08 짜리 신호가 된다.
> → 경사의 **방향**(`-dot(∇h/|∇h|, L_xz)`)과 **세기**(`clamp(|∇h| · uSteepK)`)를 갈라서 쓴다.
> 세기 상수는 매직 넘버를 쓰지 않고 **이미 있던 `CONFIG.grid.steepK`(31)** 를 재사용했다 —
> 실측 필요값 26과 거의 같고, 진폭을 키우면 `vSteep` 과 함께 자동으로 따라온다.
>
> **2. 빛을 높이 명암과 같은 `clamp` 안에 더하면 안 된다.** `0.5 + vH * 2.6` 만으로 이미
> -0.27~1.27 을 넘나들어 대부분의 면이 포화 상태다. 더한 빛이 통째로 잘린다.
>
> **3. 흰 종이 위에서는 빛이 아니라 그늘을 그려야 한다.** 이게 가장 큰 발견이다.
> 밝고 어두운 쪽을 대칭으로 변조했더니 **원본보다 그림이 흐려졌다**(실측 : 대비 15.46 → 14.21,

### [2단계 후속 14] 얇은 선의 진짜 범인 — 거품 판정이 한 대역이었다 <span>— 2026-09-02</span>

### [2단계 후속 12] 거품 — 부서진 자리를 기억한다 <span>— 2026-09-02</span>

[후속 11]과 같은 구조를 시뮬의 남는 `.w` 채널에 넣었다. 마루가 부서진 자리를 기록하고
서서히 지운다. 그래서 마루가 지나간 **뒤에도** 남았다가 흩어진다 — 그게 거품이 색이 아니라
물질로 보이는 이유다. 오늘 반복해서 부딪힌 "높이로 자르니 등고선 뚜껑 같다"의 근본 해결이다.

**시뮬은 자기 높이만 안다.** 화면의 큰 파도는 해석적 너울이라 그걸 안 보면 마루가 부서지는
것을 통째로 놓친다 (옛 물보라가 죽어 있던 이유가 정확히 이것이다). 8대역을 640² × 서브스텝마다
돌릴 수는 없으므로 **주파 하나만** 시뮬에 넘겼다 (`SWELL_MAIN`, sin·cos 각 하나).

**세 번 틀렸고 전부 측정으로 잡았다.**

1. **절대값 임계 → 거품 0%.** 주파의 기울기 최댓값이 진폭에 비례해 0.35 인데 임계도 0.35 였다.

   (마루 색을 2σ 로 정규화한 것과 같은 이유).
2. **정규화 후 50%.** 모든 마루에 계속 쌓였다.
3. **임계를 올리자 0.70 → 0.85 에서 35% → 0% 로 절벽.** 원인이 모델링이었다 —
   ⚠⚠ **정현파에서 가장 가파른 곳(영교차)과 가장 높은 곳(마루)은 위상이 90도 어긋난다.**
   "가파르고 동시에 높은 곳"의 곱은 구조적으로 거의 0 이다. **높이를 주 조건으로, 가파름을
   가중치로** 바꾸니 그제야 다이얼이 됐다 (0.65 → 43.8%, 0.80 → 25.5%, 0.90 → 10.1%, 0.98 → 6.0%).

확정 `foamHigh 0.92` → 점유 6.5%. 항적 0.57%. 백파는 마루의 일부여야 한다 —
전부 부서지면 그건 거품이 아니라 색면이다.

### [2단계 후속 11] 항적을 화면에 올렸다 — 이 바다의 첫 '기억' <span>— 2026-09-02</span>

레퍼런스(Three.js Water Pro)의 기능 목록을 읽고 나온 결론이다. 저쪽의
MULTI-LAYERED FOAM / BUOYANCY PHYSICS / BOAT WAKE 가 사실감을 주는 이유는
'디테일이 많아서'가 아니라 셋 다 **기억(history)** 을 갖기 때문이다 — 거품은 부서진

**지금까지 이 바다에는 기억이 하나도 없었다.** 마루 색도 백색도 반짝임도 반사도 전부

`.x` 만 읽어서 화면에 안 그려지고 있었다.** 새 시스템을 만든 게 아니라 이미 돌던 것을
보이게 한 것이다.

1. **흰 종이 위에서 거품을 흰색으로 그리면 안 된다.** 물이 237, 종이가 246 이라 안 보이고,

2. **원본 값을 그대로 칠하면 띠가 아니라 얼룩이 된다.** 자국은 아주 옅은 꼬리를 멀리까지
   끌어서, 문턱 없이 칠하면 화면의 23% · 폭 1982px 를 덮는 넓은 안개가 됐다.
   ⚠ `trailLife` 를 1 → 0.25 로 줄여도 23% → 19.5% 밖에 안 줄었다 — 넓은 원인이
   **지속 시간이 아니라 지금 이 순간의 자국 자체**였기 때문이다. `wakeLo/wakeHi` 문턱으로

속도에 반응하고, 멈춘 뒤에도 남았다가 사라진다 — 기억이 작동한다.

### [2단계 후속 10] 물보라를 '부딪혀 튀는 물'로 다시 썼다 <span>— 2026-09-02</span>

속도**다 — 배가 멈춰 있어도 파도는 배를 때린다. 그 값은 부력 프로브에서 공짜로 나온다

### [2단계 후속 9] 마루를 짧게, 배는 파도를 버티게 <span>— 2026-09-02</span>

**마루 길이.** 방향의 *퍼짐*이 정한다 — 좁으면 길게 이어지고(골판지), 넓으면 짧게 끊긴다

측정은 자기상관으로 했다 : 마루 방향으로 높이가 얼마나 멀리까지 상관을 유지하는가
(0.5 로 떨어지는 거리). **3.48 → 2.40 월드.** 50도까지 넓히면 1.92 로, 진행 방향
상관거리(0.60)의 3배까지 내려와 방향성이 사라지고 격자 쪽으로 기운다.

> 방향 **자체**를 돌리려면 여덟 줄을 같은 각만큼 돌린다. 하나만 돌리면 그 대역이 어긋나
> 무늬가 뜬다. 슬라이더로는 못 뺀다 — GLSL 과 CPU 부력이 둘 다 이 표에서 생성된다.

**배가 파도를 버틴다.** 예전에는 목표 자세가 곧 수면의 기울기였다 — 배가 파도에 얹힌
종잇조각처럼 보였다. 둘을 넣었다.

- **복원력** — 목표를 `rightLimit`(6도)에서 tanh 로 포화시킨다. 작은 각에서는 선형이라
  잔파도는 그대로 따라가고, 큰 각에서는 포화해 버틴다.
- **위상 선행** — 목표의 변화율만큼 앞질러 둔다(`rightLead` 1.2). 실제 배는 마루에
  올라타는 동안 이미 내려갈 준비를 한다. 그게 "파도를 이겨낸다"로 보인다.

한계값은 분포에서 잡았다 : 배 밑 수면 기울기가 **p50 9.6도 · p75 14.1도 · p90 19.8도 ·
최대 30.9도** 다. 6도면 중앙값에서 42%, p90 에서 70% 를 깎는다.

45초 실측 : 수면 기울기 평균 8.18도에 배 roll 4.18도 — **따라가는 비율 0.51.**
상하는 그대로 따라간다 (배 y −0.33 ~ 0.49). 버티는 것은 기울기지 부침이 아니다.

⚠ 이 측정에서 한 번 속았다. 설정 A 와 B 를 시간차를 두고 재면 **그 사이에 바다가 거칠어져**
비교가 무너진다 (수면 기울기 1.87도 → 6.43도). 시뮬 파면이 시간에 따라 쌓이기 때문이다.
자세는 반드시 **같은 구간에서 수면 기울기와 함께** 재고 비율로 봐야 한다.

45초 연속 : 평균 235.6~236.7, NaN 0, 발산 없음, `glError 0`, 2.83ms/프레임.

### [2단계 후속 8] 반사를 거울에서 광선으로 <span>— 2026-09-01</span>

[후속 7]에서 넣은 거울 카메라 방식을 통째로 걷어냈다. 사용자 지적이 정확했다 —
**"파도의 높이를 무시하고 화면 그대로 도장 찍듯이 하고 있다. 그 뜻은 파도의 높이를
판별하지 못하게 하는 것이고, 지금까지 했던 것도 방해하고 있는 것이다."**

맞는 진단이었다. 화면 좌표로 반사 텍스처를 되읽으면 **반사 이미지가 화면에 못 박히고
물이 그 밑으로 흘러간다.** 마루가 솟든 골이 패든 그 자리의 반사는 같다. 그리고 그날
하루 종일 한 일이 '높이를 읽히게 만드는 것'(마루 색·백색·메시 세분)이었는데, 그 위에
높이와 무관한 자국을 얹었으니 쌓은 것을 스스로 덮은 셈이었다.

내가 넣었던 '일렁임'(되읽는 좌표를 기울기로 미는 것)도 해결이 아니었다 — **이미지를
일그러뜨릴 뿐 파도 위에 얹지 않는다.** 도장을 찍고 그 위를 문지른 것에 가깝다.

**바뀐 방식.** 이 면의 실제 법선으로 시선을 튕기고, 그 광선이 배를 향하는지 본다.

    vec3 R = normalize(reflect(-V, Nr));      // 빛이 들어오는 방향
    vec3 dirB = normalize(uBoatPos - vW);     // 배가 있는 방향
    // 어긋난 각을 가로·세로로 갈라 잰다 (세로를 넓게 → 상이 길어진다)

배 쪽으로 기울어진 면에만 뜬다. 마루 앞면에는 뜨고 뒷면과 골에서는 끊긴다.
**파도가 반사를 만들지, 반사가 파도 위에 얹히지 않는다.** 실측으로 같은 장면에서
시각에 따라 점유율이 1.7% ~ 4.1% 로 변한다 — 파도가 지나가며 반사가 조각나고 이어진다.

**평평한 수면이면 반사는 선체 앞 한 뼘에만 생긴다.** 카메라가 15도로 스치기 때문이다
(계산 : 카메라 y 2.3, 배 y 0.05 → 거울상까지의 시선이 수면과 z ≈ 0.82 에서 만난다).
길이를 만드는 것은 파도다 — `reflectLong` 이 광선이 배에서 얼마나 벗어나도 봐줄지를
정하고, 그 각도 안에 들어오는 파면이 멀리까지 이어진다.

**비용은 0.024ms.** 렌더타깃도, 거울 카메라도, 추가 드로우콜도 없다.
`reflect.js` 는 삭제했다.

색은 `crestApex`(따뜻한 백색)가 아니라 `boatRefl`(#F4F8FB, 차가운 백색)이다 —
같은 색을 쓰면 반사가 그냥 '햇빛이 더 있는 곳'으로 읽혀 배가 비친 것으로 안 보인다.

⚠ 함께 드러난 것 : **h 의 분포는 파도 상태를 따라 통째로 오르내린다.** 같은 백색 임계가
어떤 순간엔 1.5%, 다른 순간엔 5.2% 를 덮었다. 그래서 임계를 넉넉히 위쪽(0.78~0.84)에 뒀다.

45초 연속 : 평균 236.1~237.5, std 7.4~8.2, NaN 0, 발산 없음, `glError 0`, 3.0ms/프레임.

### [2단계 후속 7] 그림자를 반사로 바꾸고, 잔물결 반짝임을 걷어냈다 <span>— 2026-09-01</span>

사용자 지시 네 가지 : 파도를 조금 더 잔잔하게 / 임의 그림자 제거 / 배가 수면에 **일렁이며** 비치게 /
작은 파티클처럼 흩뿌린 빛 삭제.

**어느 것이 '흩뿌린 빛'인지 먼저 특정했다.** 후보가 둘이었다(물보라, 잘게 부서지는 반짝임).
밝아진 픽셀의 연결 덩어리를 세어 보니 물보라는 **0픽셀**(잔잔해서 안 뜬 상태)이었고,
반짝임의 거친 갈래가 **작은 점 5,230개 / 37,120픽셀**을 뿌리고 있었다. 그쪽을 걷어냈다 —
[후속 5]에서 넣은 `rough0/rough1/glitCalm/glitRough/shineCalm/shineRough` 여섯 값이
`shine` · `glitterCell` 둘로 줄었다. 남은 것은 크고 느긋한 덩어리 하이라이트 하나뿐이다.

**그림자 → 반사.** 예전 타원 그림자는 광원 방향과 무관하게 늘 발밑에 붙어 있었고 파도를 안 탔다.
`reflect.js` 가 대신한다 — 수면(y=0)을 거울로 카메라를 뒤집어 **레이어로 배만** 절반 해상도
타깃에 찍고, 수면 프래그먼트가 자기 화면 좌표로 되읽는다. `Reflector` 와 달리 씬을 다시
그리지 않는다(종이배는 삼각형 수십 개). 배와 같은 게이트(8fps)로만 갱신한다.

일렁임은 되읽는 좌표를 **수면 기울기(`vGradW`)로 밀어서** 만든다 — 수영장 바닥을 미는 그
기울기와 같은 값이라, 바닥의 일렁임 · 빛의 반짝임 · 배의 반사가 한 파도를 따라 같이 흔들린다.

**세 번 걸렸다.**
1. `scene.background` 를 안 떼서 타깃이 배경색으로 알파 1 이 됐다 → 수면의 56.5% 가 반사색.
2. `onResize` 를 `resizeCbs` 선언보다 먼저 불러 TDZ 로 죽었다.
3. 계측이 거짓말을 했다 — `reflect.update()` 는 앱 루프에서만 도는데 계측 하네스가 그걸 안 불러,
   낡은 타깃(창이 접혀 1×280 이던 것)을 읽고 "검은 덩어리"로 보였다. 실제 배 픽셀은 195 였다.

세기는 0.75 에서 가장 어두운 점이 191 까지 내려갔다(주변 물 236.7, 종이 246) — 물의 최암부와
맞먹어 반사가 아니라 먹으로 그은 획으로 보인다. **0.45** 로 낮추고 세로 3탭 번짐을 넣었다.
번짐이 없으면 렌더타깃의 알파 경계가 그대로 드러나 오려 붙인 것처럼 보인다.

**파고 0.175 → 0.135, gerstner 0.45 → 0.38.** ⚠ 파고를 낮춰도 **물의 대비는 안 바뀐다**
(std 7.6 → 8.2). 색이 2σ 로 재정규화되기 때문이다 — 달라지는 것은 기하, 즉 실루엣의 높이다.
그리고 정규화가 해석적 너울만 보므로, 너울을 줄이면 시뮬 성분이 `h` 안에서 상대적으로 커져
**h 가 더 높이 올라간다.** 백색이 1.76% → 2.35% 로 늘어 임계를 0.655~0.695 → 0.70~0.75 로
올렸다(1.46%). 오로라도 0.55 → 0.48 로 내렸다(6.39% → 5.96%).

45초 연속 : 평균 235.9~237.0, std 7.5~8.4, NaN 0, 발산 없음, `glError 0`.
드로우콜 10 → 9 (그림자 메시가 빠졌다). 반사 포함 1.64ms/프레임.

### [2단계 후속 6] 수면 메시 256 → 512 <span>— 2026-09-01</span>

사용자 지적 : **"파도 하나하나 자세히 보면 삼각형으로 뾰족뾰족한 부분이 있다"**. 메시 삼각형이었다.

정점 간격 = `domain / mesh` = 110/256 = **0.43**. 주파장 3.2 를 정점 7.4개로,
잔물결 1.60 을 3.7개로 표본화한다는 뜻이다 — 사인파를 7점으로 그리면 곡선이 아니라 다각형이다.
법선은 해석적(`swellG`)이라 면 안쪽 음영은 매끄럽고, **각은 실루엣에만** 나타난다.
평소에는 반짝임 노이즈가 덮고 있어서 "자세히 보면" 보였다 — `glitter`·`specAmount` 를 0 으로
두면 근경 전체에 톱니가 드러난다.

**한 번 헛짚었다.** 처음에는 "도메인을 줄여 같은 정점을 근경에 몰면 공짜"라고 했는데 틀렸다.
화면에 보이는 물은 중심에서 33.1 월드까지인데 UV 가장자리 페이드가 반폭의 0.76(41.8)부터
시작해서, 그보다 줄이면 물이 녹아 사라지기 전에 메시가 먼저 끝나 잘린 단면이 보인다.
여유는 20.8% 뿐이고 간격이 0.430 → 0.340 밖에 안 된다. 단독으로는 답이 못 된다.

**측정** (근경, 조명만 남기고 mesh 1024 를 매끈한 기준으로 둔 오차 / 프레임 시간) :

| mesh | 간격 | 주파당 정점 | 오차 평균 · 최대 | ms |
|---|---|---|---|---|
| 256 | 0.430 | 7.4 | 0.612 · 4.2 | 2.105 |
| 384 | 0.286 | 11.2 | 0.273 · 2.2 | 2.317 |
| **512** | **0.215** | **14.9** | **0.142 · 1.3** | **2.721** |
| 640 | 0.172 | 18.6 | 0.078 · 1.0 | 2.989 |

512 에서 오차가 눈에 안 보이는 수준(최대 1.3 레벨)으로 내려가고, 640 은 비용만 10% 더 든다.

⚠ **1픽셀 라플라시안으로는 이 각짐을 못 잡는다** (256 → 640 에서 100% → 93% 밖에 안 움직였다).
삼각형이 화면에서 100px 급이라 1픽셀 미분은 픽셀 노이즈만 본다. 더 촘촘한 메시를 '정답'으로
두고 거기서의 이탈을 재야 한다.

**발산이 아님을 확인한 방법** : 30초 지점에서 std 가 8.5 → 13.2 로 올라 의심스러웠다.
`mesh` 는 시뮬에 되먹임이 없으므로(시뮬은 별도 640² 렌더타깃, 메시는 읽기만 한다)
**시뮬을 한 스텝도 안 돌리고 메시만 갈아 끼워** 비교했다 — 같은 물에서 std 8.70(512) 대
8.73(256) 로 거의 같았다. 30초의 13.2 는 큰 너울이 지나가던 순간이었고 45초 8.47,
60초 8.70 으로 돌아왔다. NaN 0, 드로우콜 10 그대로.

삼각형은 131,126 → 524,342 개가 된다.

### [2단계 후속 5] 반짝임을 파도 상태에 묶었다 <span>— 2026-09-01</span>

사용자 지적 : **"잔잔할 때는 노이즈가 크게 보이고, 파도가 많이 칠 때는 부서져서 난반사가 된다.
지금은 아무 계산 없이 노이즈를 흩뿌려둔 느낌"**. 맞았다. 정반사 노이즈가 화면 어디서나
셀 1/45 로 고정이었다 — 국소 파도 상태와 아무 관계가 없었다.

**측정으로 뒤집힌 가설이 둘 있다. 둘 다 눈으로는 반대로 보였다.**

**1. 성격을 만드는 것은 로브(`pow` 지수)가 아니라 노이즈 셀 크기다.**
처음에는 "잔잔 = 로브를 넓게"로 잡고 `shineCalm` 을 16 까지 내렸다. 결과는 큰 덩어리가 아니라
**화면의 55% 를 덮는 균일한 뿌연 안개**였다 (근경 가로 연속 158px). 로브는 *성격* 이 아니라
*커버리지* 를 정한다 — 30 → 180 에서 커버리지가 42% → 8% 로 움직이고 알갱이는 거의 안 변한다.
커버리지를 13% 로 맞춰 놓고 셀만 갈랐더니 그제야 갈라졌다.

| | 노이즈 셀 | 로브 | 커버리지 | 근경 알갱이 |
|---|---|---|---|---|
| 잔잔 | 월드 1/12 (보간) | 120 | 13.25% | **35.9 px** |
| 거침 | 월드 1/70 (양자화) | 110 | 12.97% | **3.1 px** |

밝기는 같고 알갱이만 **11.6배**. 이게 레퍼런스 두 장의 차이 그대로다.
그래서 두 로브는 거의 같은 값이고, 갈라지는 것은 셀과 노이즈 세기뿐이다.

잔잔 쪽은 `floor` 양자화를 쓰면 안 된다. 셀이 커지므로 **흰 사각 타일**이 된다 (셀 0.2 에서
실제로 그랬다). 이중선형 보간 + smoothstep 으로 이어 붙여야 둥근 덩어리가 나온다.
거친 쪽은 반대로 양자화가 맞다 — 부서진 면끼리는 원래 안 이어진다.

**2. 거칠기를 '기울기'로 재면 안 된다.**
당연해 보였지만 측정에서 통째로 무너졌다. 정반사는 하프벡터에 맞는 면만 고르는데,
이 구도에서 그 조건이 **기울기 ≈ 0.47 하나로 고정**된다 (`Hv.y = 0.904` → 법선이 25도 기울어야
정렬). 그래서 *빛나는 픽셀은 전부 같은 기울기* 다. 임계를 0.05 → 2.0 으로 훑어도
0.3~0.5 구간에서 알갱이가 11 → 36px 로 한 번 넘어가고 그 위로는 아무것도 안 남았다 —
어디를 잘라도 한쪽으로만 간다. **선택 효과**라 기울기 분포를 CPU 로 재도 안 보인다
(CPU 기울기는 p50 0.32 / p90 0.88 로 멀쩡히 퍼져 있었다).

물이 부서지는 곳은 마루다. 그래서 **마루 색을 구동하는 그 정규화 높이**로 바꿨다.
같은 양을 재사용하므로 보라·백색으로 물드는 바로 그 마루가 잘게 반짝인다.
임계로 훑으니 이번에는 전 구간이 반응했다 (근경 알갱이 : h>0.44 에서 13.2px → h>0.62 에서 32.8px).

확정 `rough0 0.55 / rough1 0.85` → 근경 24.8px. 잔잔(35.9)이 주인이고 마루에만 부서짐이 얹힌다.
오로라 띠(0.68~0.94)보다 **조금 앞서 시작**하도록 잡았다 — 색보다 부서짐이 먼저 와야 순서가 맞다.

### [2단계 후속 4] 파도의 스케일을 배 기준으로 다시 깔았다 <span>— 2026-09-01</span>

사용자 지적 : **"파도라는 표현보다는 등고선이 움직이는 높은 물의 일렁임이 지나가는 느낌"**.
재보니 정확했고, 원인이 색이나 디테일이 아니라 **스케일 비율 하나**였다.

| | 고치기 전 | 고친 뒤 | 레퍼런스(추정) |
|---|---|---|---|
| 주파장 / 배 길이 | **16.5척** | **3척** | 2~3척 |
| 가파름 (파고 ÷ 파장) | **1.96%** | **11.9%** | 그래픽 파도 10~15% |
| 보이는 바다에 든 파도 | 1.4 주기 | 5 주기 | 3~4 |
| 화면 대비 std | ~5 | **10.4** | — |

**파도 하나에 배가 16.5척 들어가면 그건 파도가 아니라 지형이다.** 그 스케일에서는 아무리 색을
맞춰도 '움직이는 등고선'으로 읽힌다. 그리고 두 색상 가이드는 **파도가 파도로 읽히는 것을
전제**하고 마루·골·능선의 색을 정의하므로, 그동안의 색 작업이 레퍼런스에 안 가까워진 이유가
여기 있었다.

**진폭은 거의 그대로 두고 파장만 줄였다.** 가파름 = 파고 ÷ 파장이라, 파장을 5배 줄이면
가파름이 5배가 된다. 스펙트럼을 통째로 다시 깔았다 — 너울 11.0 / **7.5(주파)** / 5.2,
잔물결 3.6 / 2.7 / 2.1 / 1.7. 각속도는 심해 중력파 분산관계 ω = 0.62·√(g·k) 에서 뽑았다
(긴 파가 빠르고 짧은 파가 느린 관계가 맞아야 파들이 서로 미끄러지지 않는다).

**딸려온 것 다섯 개를 같이 고쳤다. 하나라도 빠지면 그림이 깨진다.**

1. **Gerstner 루프 한계가 3.07 → 0.92** 로 내려갔다 (파수가 커졌으므로). `gerstner` 1.2 →
   0.65, 상한 0.8.
2. **`steepK` 를 수면 전용으로 분리했다.** `grid.steepK`(31)를 빌려 쓰고 있었는데, 너울 기울기가
   0.036 → 0.351 로 6배가 되어 31 을 곱하면 어디나 포화하고 명암의 계조가 통째로 사라진다.
   `surface.steepK = 5.0` 신설.
3. **바닥 격자의 밀림이 다시 칸을 넘었다.** 기울기가 6배가 됐으니 `refract` 도 3.5 → 0.5 로
   같이 내려야 한다 (밀림/칸 1.66 → 0.24).
4. **최상단 백색이 터졌다** (화면의 6.3% 가 252 이상). 원인 둘 — 마루가 둥글면 '높이 상위 8%'
   가 넓은 뚜껑이 된다. 띠를 0.92 → **0.95** 로 좁혔고, **가산 발광 항을 뺐다** (블룸이 있어야
   번지는 항인데 없으면 그냥 255 로 잘려 흰 덩어리만 만든다). 결과 0%.
5. **시뮬 파면도 같이 줄였다** (`ambR` 8 → 3, `ambLength` 26 → 10). 파면 하나가 주파장보다
   훨씬 크면 그 층만 다시 '지형'이 된다.
6. 보이는 바다 `fade` 30/56 → **20/40**, 거리 LOD 22/52 → **12/30**.

⚠ 카메라는 그대로 뒀다 (사용자 선택). 레퍼런스의 "파도 사이에 앉은 배" 구도는 카메라를
수면 가까이 내려야 나오지만, 그러면 **수영장 바닥 격자가 거의 안 보이게 된다** — 스치는
각도에서 물속이 안 보이는 게 물리적으로 맞기 때문이다. 그 둘은 동시에 만족시킬 수 없다.

검증 : 배 40초 안정 / 백색터짐 0% / glError 0 / 밀림·칸 0.24

### [2단계 후속 3] 바다 팔레트 재정의 · 물속이 보이게 <span>— 2026-09-01</span>

근거 : `threejs-ocean-color-composition-guide.md` + 사용자 지적 "베이지가 과하다 / 수면 아래에
격자를 깔고 수영장 바닥처럼 일렁이게".

**베이지의 원인을 측정으로 특정했다.** 원인이 두 단계로 겹쳐 있었다.

| | R−B | 채도 |
|---|---|---|
| 배경 `#F8F7F3` | 5 | 2.0% |
| 물 기본색 `#E6E2D9` (내가 고른 값) | 13 | 5.7% |
| `waterShade` 2.2 로 외삽된 deep | 22 | 10.6% |
| **실제 화면 최암부** | **27** | **13.1% — 종이의 6.5배** |

`mix(uBg, uWater, uShade)` 는 `uShade > 1` 이면 외삽하는데, **외삽은 배경→물의 차이 벡터를
밝기와 색조까지 한 덩어리로 늘린다.** 그래서 형태를 읽히게 하려고 `waterShade` 를 올린 순간
베이지도 같이 2.2배가 됐다. 가이드가 지목한 실패 모드("물의 기본색과 그림자색을 모두 따뜻한
베이지로 설정")와 정확히 같다.

**고친 방법 — 색 온도를 요소별로 분리했다.**

| 요소 | 색 | 온도 |
|---|---|---|
| 배경·안개 | `#F6F5F2` | 미세하게 따뜻함 — **따뜻함은 여기에만** |
| 수면 기본 | `#F0EFEC` | 거의 무채색 |
| 중간 면 | `#E4E5E8` | 차가운 블루·라일락 그레이 |
| 골짜기 | `#D4D8E0` | 차가운 회청색 |
| 투과광 | `#EAF2F5` | 낮은 채도의 시안 |

그리고 **방향광이 별도의 색 축을 만들지 않게** 바꿨다. 이제 빛은 색을 섞는 게 아니라
'정규화된 높이를 미는' 것으로만 작용한다(`h + uShade · lit · 0.16`) — 따뜻한 색이 두 번
겹칠 경로 자체를 없앴다.

**결과 : 최암부 R−B 가 +27 → −9 로 뒤집혔다.** 중간값 +1(무채색), 배경만 +4(따뜻함).

**물속 — 수영장 바닥 격자.** 지오메트리를 새로 깔지 않았다. 반투명 정렬 문제와 오버드로가
생기기 때문이다. 대신 `WATER_FRAG` 안에서 **수면 기울기만큼 밀린 좌표**로 절차적 격자를
샘플한다 (굴절 흉내). 일렁임이 공짜로 나온다 — 빛과 마루 색을 구동하는 그 기울기를
그대로 쓰기 때문에 위상이 자동으로 맞는다. 드로우콜 0.

⚠ **여기서 두 번 틀렸고, 사용자가 "하단에 안 깔려 있는 것 같다" 고 짚어줘서 잡았다.** 재보니
화면 아래 띠의 대비 std 가 1.88 (밝기 범위 7) 로 사실상 비어 있었다. 원인이 둘이었다.

1. **칸 크기를 원경 기준으로 잡았다.** 칸 2.9 월드인데 화면 맨 아래는 카메라에서 4.5 월드다 —

그리고 **물속은 내려다볼 때만 보이게** 했다 (`smoothstep(0.03, 0.40, V.y)`). 스치는 각도에서는
반사가 이겨 바닥이 안 보이는 게 물리적으로 맞고, 원경에서 잔 격자가 앨리어싱하는 것도
이 한 항이 같이 막는다.

### [2단계 후속 2] 마루 색을 3색으로 제한 · 파도 높이·속도 재조정 <span>— 2026-09-01</span>

근거 : 사용자가 준 `threejs-wave-crest-color-guide.md` + "파도를 더 높게, 속도는 더 느리게".

- **전체 스펙트럼을 버리고 3색으로 제한했다.** 코사인 팔레트(무지개 한 바퀴)를
  보라 `#C9A7FF` → 아이스블루 `#9FE6F3` → 따뜻한 백색 `#FFFDF8` 로 바꿨다.
  가장 높은 마루는 보라도 파랑도 아니라 **따뜻한 백색**이라는 게 가이드의 핵심이다.
- **구동축을 경사에서 '정규화된 파도 높이'로 바꿨다.** 마루 0.68~0.94, 최상단 0.92~1.0.
  경사로 몰면 이 바다는 어디나 조금씩 기울어 있어 색이 전면을 덮는다.
- **속도** : `params.waveSpeed`(기본 0.55)가 전 대역의 각속도에 한꺼번에 걸린다.
  파장별 상대 속도(긴 파가 빠르다)는 유지되므로 파가 서로 어긋나지 않는다.
- **높이** : `oceanSwell` 0.14 → **0.45**. 봉우리→골 진폭이 1.04 → 2.46 월드가 됐다.

**여기서 세 번 헛짚었고, 세 번 다 실측이 잡아줬다.**

1. **정규화 기준을 진폭의 단순 합(0.614)으로 잡았더니 마루 색이 아예 안 떴다.**
   그건 모든 대역의 마루가 한 점에 정렬돼야 나오는 값이고 실제로는 도달하지 않는다 —
   실측 p99 가 0.48 이었다. **무작위 위상 정현파 합의 실질 마루 높이는 2σ = √(2·ΣA²)**
   (해양학의 유의파고 / 2). 바꾸니 실측 p99 와 거의 정확히 맞았고, 마루 면적이
   25.1% · 최상단 2.3% 로 가이드가 의도한 두께가 나왔다.
2. **가이드의 base `#F2F0ED` 를 그대로 썼더니 파도를 아무리 높여도 형태가 안 읽혔다.**
   그 값은 블룸을 전제한 것이고, 블룸 없이 쓰면 배경과 11레벨 차이뿐이다. `#E6E2D9` 로 내렸다.
3. **그래도 안 보여서 픽셀을 재보니 `waterShade` 1.0 에서 물의 대비 std 가 5.4 였다**
   (배경 247 근처에 거의 다 몰려 있었다). 2.2 에서 13, 4.0 에서 27. 내가 잡아둔 범위
   `[0, 1.5]` 가 애초에 너무 좁았다. 기본값 2.2, 범위 `[0, 5]` 로 고쳤다.

⚠ **진폭을 올려도 마루 색은 안 세진다.** `uHNorm` 이 진폭에 반비례해 같이 움직이기 때문이다 —
색은 절대 높이가 아니라 '그 바다에서 상대적으로 얼마나 높은 마루인가'에 붙는다. 의도된 동작이다.

루프 한계 3.07 대비 gerstner 1.2 / 번들 gzip 142.83KB

### [2단계 후속] 표현면을 그리드에서 수면으로 옮겼다 <span>— 2026-09-01, 사용자 지시</span>

위 2단계를 끝낸 뒤 사용자가 지적했다 — **"격자 배열을 삭제해야 할 것 같다. 파도의 빛 반사가
진행되고 있는지 모르겠다."** 재보니 정확한 지적이었다.

| | 잉크 비율 |
|---|---|
| 그리드 켜짐 | 10.47% |
| 그리드 꺼짐 | **1.45%** |
| **그리드가 담당하던 비중** | **86.2%** |

수면 메시는 배경색으로만 칠하고 있었다 (깊이 마스크가 유일한 역할). 즉 **그리드는 배경 요소가
아니라 유일한 표현면이었고**, 빛·반사가 전부 선 위에서만 일어나 격자에 덮여 있었다.

- **`water.js` 가 자기 명암을 갖게 했다.** 핵심 제약은 배경(`#F8F7F3`, 밝기 246)보다 밝을 수
  없다는 것이다. 그래서 물을 배경보다 조금 내려놓고(`CONFIG.color.water`), **빛을 받는 면이
  배경색으로 올라오는 것**을 하이라이트로 삼았다. 멀어지면 여전히 배경색으로 흩어지므로
  흰 여백 전제는 그대로다. `waterShade` / `waterSpec`.
- **`showGrid` 기본값을 false 로 바꿨다.** GPU 1.904 → **1.177ms (38% 감소)**, 드로우콜 13 → 10,
  선분 64,720 → 0. 선 렌더가 GPU 시간의 40% 였다.
- **오로라 분광**(`iriWater`). 코사인 팔레트로 무지개를 만들고, 스침각(프레넬) × 경사의 좁은
  구간(리본) × 빛을 향한 면으로 삼중으로 걸렀다.
  ⚠ `steep` 을 그냥 곱했더니 **무지개가 화면 100% 를 덮어 기름막이 됐다.** 이 바다는 어디나
  조금씩 기울어 있어서, 선택성 없이는 분광이 표현이 아니라 오염이 된다.
- **파도의 규칙성**을 깼다. 대역을 4 → 7 개로 늘리고 방향·주파수를 서로 약수 관계가 아니게 골랐다.
  **그리드를 끈 덕에 잘게 넣을 수 있게 됐다** — 예전엔 가장 거친 LOD 셀이 1.6 이라 파장 4 밑이
  모아레였는데, 수면 메시는 0.43 간격이라 파장 2.8 까지 안전하다 (6.5 샘플/파장).
- **거리 LOD.** `swellH`/`swellG`/`swellD` 가 `detail` 인자를 받아 **잔물결 대역에만** 그 계수를
  건다. 저주파 너울은 절대 줄이지 않는다 — 지평선까지 이어져야 하는 바다의 형태다.
  오로라도 같은 곡선으로 함께 사라진다. GPU 0.139 → **0.107ms (23% 감소)**.

⚠ 이 작업 중 2단계에서 넣은 버그를 하나 잡았다. `vGradW` 에서 **시뮬 기울기와 너울 기울기의
z 부호가 반대**였다 — `suv.y = 0.5 - z/domain` 이라 텍스처 기울기의 y 성분은 `-∂h/∂z` 인데
`swellG` 는 `+∂h/∂z` 를 준다. 원래 코드는 `length()` 와 `atan()` 에만 써서 부호가 무의미했지만,
2단계에서 둘을 더하면서 문제가 됐다. `grid.js`·`spray.js`·`water.js` 셋 다 고쳤다.

⚠ **측정 하네스가 두 번 거짓말을 했다.** (1) 패널이 숨겨지면 뷰포트가 0×0 으로 접혀 픽셀 통계가
1픽셀 폭을 읽는다 — 스크린샷으로 깨운 직후 같은 왕복에서 재야 한다. (2) `renderer.render()` 만
직접 부르면 `water.update()` 가 안 돌아 유니폼이 갱신되지 않는다 — 파라미터를 아무리 바꿔도
같은 그림이 나온다. 측정 전에 `tick()` 의 갱신 체인을 그대로 태워야 한다.

---

**`swell.js` 를 구조적으로 고쳤다.** 불변식 "GLSL 과 CPU 사본은 항상 같은 식"이 손으로 지키는
약속이었는데, 대역을 하나 더하는 순간이 정확히 그게 깨지는 지점이었다. 이제 `swellH`/`swellG`/
`swellD`/`swellCPU` 가 **전부 `BANDS` 표 하나에서 생성된다.** 대역 추가는 한 줄이고 어긋날 방법이 없다.
검증 : 컴파일된 셰이더 소스를 JS 로 옮겨 CPU 사본과 대조 — **3,996 표본에서 최대오차 0.**

⚠ **Gerstner 는 좌표계를 하나 가른다.** GPU 는 매개변수 `p` 의 정점을 월드 `p + D(p)` 에 놓는데,
배는 반대로 "월드 `X` 에서의 수면 높이"를 물어야 한다. `swellCPU` 안에 뉴턴 한 걸음(`p ≈ X − D(X)`)이
들어 있다. **역변환 있음 오차 0.00072 / 없음 0.02009 — 28배 차이다.** 빼면 배가 파도와 어긋나 뜬다.
루프(자기교차) 한계는 현재 진폭에서 8.91 (`gerstnerLoopLimit`), 그래서 파라미터 상한을 4 로 잡았다.

**"유도된 자유"** — 자유 조타의 약점은 사용자가 무엇을 해야 할지 모른다는 것이다.
스크롤을 도입할 게 아니라, 시작 시 배가 자동으로 천천히 전진하며 첫 마커 근처를 지나가고(온보딩),
조타 입력이 들어오면 자동 항해를 즉시 놓아준다. GSAP 타임라인 하나 + `kill()` 한 줄.
The Boat(SBS)의 "내버려두면 진행되고, 만지면 내 속도가 된다" 페이싱이 이 컨셉과 정확히 맞는다.

### [6단계] 에셋 — 종이배 GLB + 이미지

5장 참고. `createBoatMesh()` **내부만** 바꾼다.
⚠ 이 함수는 동기이고 `createBoat(scene)` 이 모듈 로드 시 즉시 호출한다 →
플레이스홀더를 먼저 넣고 로드 완료 시 `pivot.children[0]` 을 교체하는 구조로.
치수는 `g.scale.setScalar(1.35)` 와 `CONFIG.buoy.armX/armZ` 에 맞춰야 자세가 유지된다.

### [7단계] 마감

- `renderer.compileAsync(scene, camera)` 로 셰이더 사전 컴파일.
  **핑퐁 시뮬용 풀스크린 쿼드 씬도 별도로 대상에 넣어야** 첫 시뮬 스텝이 매끄럽다.
- **로딩 화면이 필요 없는 희귀한 케이스다.** html/body/컨테이너를 전부 `#F8F7F3` 으로 칠하면
  JS 파싱 중에도 화면은 이미 "완성된 흰 여백"이다.
  순서 : 흰 배경 즉시 → 시뮬 워밍업 수십 스텝을 화면 밖에서 → `compileAsync` → 등고선 opacity 0→1 로 400ms 페이드인.
- `prefers-reduced-motion` 대응 (6장).
- WebGL 미지원·컨텍스트 손실 폴백. 이 아트 디렉션은 폴백이 유난히 싸다 — **등고선 SVG 한 장**이면 컨셉이 유지된다.
- 파비콘 · OG · 메타 (현재 전무).

## 5. 이미지 · 텍스처 에셋

> **현재 이 프로젝트에는 이미지가 단 한 장도 없다.** `src/` 전체에 `TextureLoader` / `.png` 참조가 0건이고
> 외부 리소스는 Pretendard CDN CSS 하나뿐이다. **이미지를 넣는 순간 "로딩"이라는 개념이 처음 생긴다.**

### 5-1. 진짜로 필요한 것은 네 가지뿐이다

| 에셋 | 규격 | 만드는 법 |
|---|---|---|
| **파비콘 세트** | `favicon.ico` 32² + `icon.svg` + `apple-touch-icon.png` 180² | 종이배 실루엣을 1px 선 SVG 로(씬의 선 언어와 동일) → 파생. SVG 안에 `@media (prefers-color-scheme: dark)` 로 다크탭 대응 |
| **OG 이미지** | 1200×630, sRGB, 300KB 이하 | ⚠ `preserveDrawingBuffer` 가 꺼져 있어 `toDataURL()` 이 **빈 이미지를 준다.** `renderer.render()` 직후 **같은 JS 턴 안에서** 호출하거나 캡처용으로만 옵션을 켠다 |
| **한글 폰트 교체** | Pretendard dynamic-subset (SIL OFL) | ⚠ **URL 만 바꾸면 안 된다.** variable 판의 패밀리명은 `"Pretendard Variable"` 이라 `index.html:20` 의 `font-family:Pretendard,...` 도 함께 고쳐야 한다. 안 그러면 **조용히 시스템 폰트로 폴백**한다 |
| **종이 노멀맵** | 512², `NoColorSpace`(중요), Repeat 3~6, `normalScale` 0.15~0.35 | [ambientCG Paper001](https://ambientcg.com/view?id=Paper001) (CC0) 1K-JPG → NormalGL 만 → 512 리사이즈. ⚠ **Paper005 는 갈색 골판지**다, 흰 종이가 아니다. Poly Haven 에는 paper 텍스처가 **0건**(확인함) |

### 5-2. 효과 대비 비용이 가장 좋은 것 — 블루 노이즈 디더

`#F8F7F3` 근처의 near-white 그라데이션(수면 페이드, 향 영역 얼룩, 거리 페이드)은 8bit 출력에서 **반드시 밴딩 띠가 보인다.**
흰 여백 컨셉이라 특히 눈에 띈다. 파일 하나 + 셰이더 두 줄로 완전히 사라진다.

- [Calinou/free-blue-noise-textures](https://github.com/Calinou/free-blue-noise-textures) 의 `128_128` (CC0). 원본 [Moments in Graphics](https://momentsingraphics.de/BlueNoise.html)
- `NearestFilter`(min/mag 둘 다, **필수**), `RepeatWrapping`, `generateMipmaps=false`, `NoColorSpace`
- 샘플 UV 는 반드시 **화면 좌표** : `texture2D(uNoise, gl_FragCoord.xy / 128.0).x` — 월드 UV 로 하면 노이즈가 카메라를 따라 헤엄쳐 더 지저분해진다
- ⚠ **넣는 위치가 중요하다.** `WATER_FRAG`/`GRID_FRAG`/`SPRAY_FRAG` 셋 다 `gl_FragColor` **다음 줄**에 `#include <colorspace_fragment>` 가 있다. 즉 `gl_FragColor` 값은 아직 **선형**이다. 디더는 8bit 출력의 1 LSB 를 겨냥하므로 **sRGB 인코딩 이후**에 적용해야 한다. 선형 단계에서 `1/255` 를 더하면 밴딩이 그대로 남는다

### 5-3. 그다음 — 색을 이미지로 내리기

**선 색 LUT / gradient ramp** (256×1 PNG, `SRGBColorSpace`)
지금 선 색은 `mix(uIriA, uIriB, drift)` 라 중간색을 못 만든다. 램프 이미지로 빼면
**포토샵에서 그라데이션 바를 고쳐 저장하는 것만으로 씬 전체 색조가 바뀐다.**
파일명을 `ramp_iri_a.png` / `_b.png` 로 두면 `params.js` 문자열 하나로 A/B 비교가 된다.
⚠ Vite 가 작은 파일을 base64 인라인하므로 `?no-inline` 을 붙이거나 `public/` 에 둔다.

**향 영역 수채 얼룩 마스크** (512² 그레이스케일, R 채널만)
지금 향 영역은 `smoothstep` 로 만든 완벽한 원이라 4개가 다 똑같이 생겼다.
종이 위에 물감이 번진 불규칙 얼룩은 절차 생성이 매우 까다로워 **이미지가 명백히 낫고**, 컨셉(종이·수채)과도 맞는다.
1장을 회전·스케일·미러로 재사용하는 편이 유지보수가 낫다.

**matcap** (512², LDR 이므로 `SRGBColorSpace`) — 배에 방향광 대신. [matcap-studio](https://kchplr.eu/matcap-studio/) 로 밝기·대비만 눌러 제작.
⚠ [nidorx/matcaps](https://github.com/nidorx/matcaps) 는 **통일된 라이선스가 없다**(저장소가 스스로 "여러 사이트에서 수집" 이라고 명시). 참고만.

## 6. 애니메이션 검수

> **이 씬은 정지 스크린샷으로 판정할 수 없다.** 발산은 30초 뒤에야 화면에 나타난다.
> 그래서 검수의 1순위는 "눈으로 보기" 가 아니라 **숫자로 먼저 잡기** 다.

### 6-1. 1순위 — 렌더타깃 readPixels 로 발산·NaN 을 코드로 잡는다

⚠ **핵심 함정** : `util.js` 의 `h2f()` 는 `if (e === 31) return 0;` — half-float 지수 31(=Inf/NaN)을 **0 으로 뭉갠다.**
**발산 탐지에 절대 재사용하면 안 된다.** 기존 부력 프로브로는 NaN 이 절대 안 잡힌다.

```js
// (1) sim.js 의 api 에 훅 하나 추가 :  debugRT() { return rtA; },
// (2) Playwright
const r = await page.evaluate(() => {
  const { renderer, sim } = window.PB;
  const rt = sim.debugRT(), N = rt.width;          // 640
  const buf = new Uint16Array(N*N*4);
  buf.fill(0xDEAD);                                 // 센티넬 — 아래 주석 참고
  renderer.readRenderTargetPixels(rt, 0, 0, N, N, buf);
  if (buf[0] === 0xDEAD && buf[4] === 0xDEAD) return { read: false };
  const dec = h => { const s=(h&0x8000)?-1:1, e=(h>>10)&0x1f, f=h&0x3ff;
    if (e===31) return f ? NaN : s*Infinity;        // ← h2f 와 다른 지점
    if (e===0)  return s*f*5.9604644775390625e-8;
    return s*Math.pow(2,e-15)*(1+f/1024); };
  let nan=0, maxAbs=0;
  for (let i=0;i<buf.length;i+=4) { const v = dec(buf[i]);
    if (!Number.isFinite(v)) { nan++; continue; }
    if (Math.abs(v) > maxAbs) maxAbs = Math.abs(v); }
  return { read: true, nan, maxAbs };
});
expect(r.read).toBe(true);
expect(r.nan).toBe(0);
expect(r.maxAbs).toBeLessThan(8);
```

**센티넬이 필요한 이유** : three r160 의 `readRenderTargetPixels` 는 포맷 미지원이나 범위 초과 시
**예외 없이 `console.error` 만 찍고 return** 한다. 버퍼가 그대로 남으므로 직접 확인해야 한다.

### 6-2. "하얗게 날아갔는가" 의 기계적 정의 — inkRatio

배경 `#F8F7F3` 의 휘도는 약 246. **휘도 < 230 인 픽셀 비율**이 `inkRatio` 다.
⚠ `preserveDrawingBuffer` 가 꺼져 있으므로 **`renderer.render()` 직후 같은 JS 턴 안에서** `gl.readPixels` 해야 한다.

2 / 10 / 30 / 60초 네 지점을 찍어 **단조 감소하지 않는지** 본다. 이 함수 하나를 가상클록 테스트·워치독·플래시 검사가 공유한다.

### 6-2b. ⚠ 브라우저 창이 안 보이면 시간 기반 측정이 전부 거짓이 된다

**2026-08-31 실측에서 확인.** 미리보기 pane 이 숨겨져 있으면 브라우저가 `requestAnimationFrame` 을
정지·스로틀한다. 그러면 이 씬은 렌더 루프가 멈춘 채로 화면만 남는다. 증상이 아주 헷갈린다 —

- `sim.qT` 가 36초 동안 **한 번만** 바뀐다 (게이트가 깨진 것처럼 보인다)
- `inkRatio` 가 소수점 4자리까지 **완전히 고정**된다 (정지 화면이므로)
- 높이맵 최대값이 `0.008` 로 죽어 있다 → **"바다가 죽었다" 는 오진**을 하게 된다

실제로는 시뮬이 거의 스텝하지 않았을 뿐이다. 파면은 uv 0.22~0.28(=24~31 월드)에서 태어나
배까지 오는 데 **시뮬 시간 2~3초**가 필요하므로, rAF 가 몇 번밖에 안 돌면 파가 도착할 수가 없다.

**해법 — rAF 를 기다리지 말고 시뮬을 직접 스텝시킨다.** 결정론적이고 훨씬 빠르다.

```js
const { sim } = window.PB;
let t = sim.qT; const dt = 1/60;
for (let i = 1; i <= 60*60; i++) {          // 60 시뮬초
  t += dt;
  sim.update(dt, t, { vX:0, vZ:4.0, mv:1, scrollX:0, scrollZ:4.0*dt*i });
  if (i % 600 === 0) console.log(i/60, readField());
}
```

<strong>실측 : 120 시뮬초가 wall clock 508ms.</strong> 60초 방치 테스트를 0.25초에 끝낼 수 있다.
`page.waitForTimeout(60000)` 을 쓸 이유가 없다.

측정 전에 항상 확인할 것 : `document.hidden === false`, 그리고 rAF 실측 fps.
둘 중 하나라도 이상하면 그 실행의 시간 기반 수치는 **전부 버린다.**

### 6-2c. `sim.sampler()` 로 바다를 재지 마라

`sampler()` 는 선수 주변 **16×16 텍셀(≈2.75×2.75 월드)** 만 읽고, 그 밖의 좌표는 인덱스를
`clamp(0, 15)` 로 접는다. 즉 `at(8, -8)` 을 불러도 창 가장자리 값이 돌아온다 —
그런데 그 창은 정확히 **선체가 물을 붙잡고 있는 자리**라서, 무엇을 넣든 흘수 깊이(`bowDepth × 0.12`)
근처의 상수가 나온다. 부력 계산용으로는 맞지만 **바다 상태 측정에는 쓸 수 없다.**

전체 필드를 보려면 `sim.texture` 를 **내가 만든 렌더타깃으로 한 번 블릿한 뒤** 읽는다
(씬을 건드리지 않는 read-only 경로).

### 6-2d. 실측 기준선 <span>— 2026-08-31, RTX 3060 Ti · WebGL2 · dpr 1</span>

| 항목 | 값 |
|---|---|
| 드로우콜 / 프로그램 / 텍스처 | 13 / 7 / 2 |
| 선분 / 삼각형 | 64,720 / 131,126 |
| 60초 정지 — 월드 최대 파고 | 0.065 ~ 0.099 (평균 0.007) |
| 60초 항해(mv=1) — 월드 최대 파고 | 0.166 ~ 0.316 (평균 0.018) |
| NaN / Inf 텍셀 | **0** (양쪽 60초 후에도) |
| 누적 발산 | **없음** — 60초 값이 10초 값과 같은 대역 |
| 시뮬 처리량 | 120 시뮬초 = 508ms wall |
| **프로덕션 번들** | 518.8KB → **gzip 137.96KB** (`npm run build`, 988ms) |

프로덕션 빌드는 이때 **처음 검증됐다.** 통과했고, gzip 138KB 가 앞으로의 번들 예산 기준선이다.
이미지 에셋 총량을 500KB 이하로 묶으라는 5장의 지침이 이 숫자와 맞물린다 —
지금은 번들이 전부이므로 에셋을 더하면 그만큼 첫 프레임이 늦어진다.

여기서 나온 판단 하나 — <strong>정지 상태에서 시뮬 파도(0.07)는 해석적 너울(<code>oceanSwell</code> 0.14 +
<code>ripple</code> 0.035 ≈ 최대 0.26)의 약 1/4 밖에 안 된다.</strong> 즉 멈춰 있을 때 눈에 보이는 일렁임은
파동방정식이 아니라 너울이다. 2단계 “파도 융기” 작업이 겨냥해야 하는 것이 정확히 이 격차다.
그리고 시뮬이 wall clock 의 0.4% 밖에 안 쓰므로, <strong>융기를 키우는 비용은 성능이 아니라 발산 위험뿐이다.</strong>

### 6-2e. 실사용 창 실측 <span>— 2026-09-01, Intel Arc iGPU · 120Hz · dpr 2 · 1440×731</span>

6-2b 때문에 자동화된 브라우저에서는 잴 수 없었다. 그래서 `vite.config.js` 에 `/__perf` 회수
경로를 만들고(개발 서버 전용), `?perf` 로 띄운 페이지가 자기 측정치를 `perf-report.json` 으로
POST 하게 했다. **71.1초 · 8,518프레임 · 평균 119.8fps · 숨은 프레임 0 · 포커스 유지** — 유효한 샘플이다.

| 예산 항목 | 목표 | 실측 | 판정 |
|---|---|---|---|
| rAF p95 | ≤ 20ms | **13.5ms** (p50 8.3 / p99 18.1 / max 19.1) | ✅ |
| LoAF blockingDuration | 0ms | **워밍업 이후 0ms** (0.1초에 30.2ms 1회) | ✅ |
| 물 갱신 간격 | 83.3ms ±9 | **83.4ms** | ✅ |
| 배 갱신 간격 | 125ms ±13 | **124.4ms** | ✅ |
| 드로우콜 | 기준선 +20% | **13** (기준선 그대로) | ✅ |
| GPU 텍스처 메모리 | ≤ 64MB | 2장 ≈ 6.5MB | ✅ |

**전 항목 통과. 그것도 08-31 기준선의 RTX 3060 Ti 가 아니라 더 약한 내장 그래픽에서 나온 값이다.**
예산이 보급형 하드웨어에서도 선다는 뜻이므로, 2단계에서 아트를 얹을 여유가 이 숫자만큼은 있다.

**여기서 1-4 의 "시뮬 스텝 버스트"가 정량화됐다.** GPU 시간이 평시 **3.66ms 인데 최대 12.85ms** 로
3.5배 튄다. 120Hz 프레임 예산(8.33ms)을 넘는 것은 이 튐뿐이고, 초당 12번 = 120프레임 중 10% 라
**p95(13.5ms)가 정확히 이 버스트를 물고 있다.** 즉 p95 를 끌어올리는 주범은 등고선 렌더가 아니라
게이트가 열리는 프레임의 640² 패스 10연발이다.

→ 2단계에서 진폭·조명을 올려 p95 가 예산을 넘기 시작하면, 먼저 볼 곳은 그리드가 아니라
**시뮬 스텝을 프레임에 분산시키는 것**이다 (한 프레임에 10번 대신 여러 프레임에 나눠).

⚠ 이 값들은 **120Hz 디스플레이 기준**이다. 6-4 의 "p95 ≤ 20ms" 는 60Hz 를 가정한 수치라
여기서는 헐거운 기준이 된다. 이 기기에서의 진짜 프레임 예산은 8.33ms 다.

### 6-3. 재현 가능하게 만들기 — 시드 RNG + 가상 클록

`src/` 전체에 `Math.random()` 이 **13곳**(파면 생성·물보라)이다. 시드 고정 없이는 어떤 시각 비교도 무의미하다.

```js
await page.addInitScript(() => {           // mulberry32
  let s = 0x9E3779B9;
  Math.random = () => { s|=0; s=(s+0x6D2B79F5)|0;
    let t = Math.imul(s ^ (s>>>15), 1|s);
    t = (t + Math.imul(t ^ (t>>>7), 61|t)) ^ t;
    return ((t ^ (t>>>14))>>>0) / 4294967296; };
});
await page.clock.install({ time: 0 });
await page.goto(url);
for (let i=0;i<30;i++) await page.clock.runFor(1000);   // 1초씩 30번
```

`THREE.Clock` 이 `performance.now()` 를 쓰므로 그대로 걸린다. 30초 시뮬이 **실측 2~5초**로 줄어든다.
`runFor` 를 1초씩 끊어 쓴다(`fastForward` 는 재귀 rAF 에서 이력이 있다 — 해당 이슈는 2025-10 종료됐지만 `runFor` 가 안전하다).

### 6-5. 골든 프레임

해상도·DPR 을 **반드시 고정**한다. `main.js` 가 `min(devicePixelRatio, 2)` 를 쓰고 `grid.js` 가
`setRes(sz.x*pr, sz.y*pr)` 로 픽셀 밀도 페이드를 계산하므로, **DPR 이 다르면 선 밀도 자체가 달라져 골든이 전부 깨진다.**

```js
use: { viewport: { width: 1280, height: 720 }, deviceScaleFactor: 1 }
// 0 / 2 / 5 / 10 / 30초 5장, maxDiffPixelRatio: 0.02
```

실행 전 `WEBGL_debug_renderer_info` 로 렌더러를 로그하고 **SwiftShader/llvmpipe 면 스킵**한다.

### 6-6. 그 외 자동 검사

- **셰이더 컴파일 실패 후킹** — `renderer.debug.onShaderError` 는 **머티리얼 컴파일 전에** 걸려 있어야 하므로 `addInitScript` 로는 늦다. `main.js` 에 `?debug=1` 플래그로 심는다. three 는 컴파일 실패해도 검은/투명으로만 그려 눈으로 못 알아챈다.
- **webgl-lint** (`?lint=1`) — NaN 유니폼·미설정 유니폼을 GL 경계에서. `grid.js` 의 `atan(+1e-6)` 가드 같은 종류를 자동으로 잡는다.
- **컨텍스트 소실·복구** — 이 프로젝트는 핑퐁 RT 에 **상태(수면 높이)를 들고 있어** 컨텍스트가 날아가면 물이 사라진 채 복구된다. 현재 핸들러가 없다. `webglcontextlost` 에서 `e.preventDefault()` 를 부르지 않으면 `restored` 가 **아예 오지 않는다.**
- **params 스냅샷 회귀** — `CONFIG.sim.c < 0.5`, `damping > 0.99`, **LOD 셀 비율이 정확히 2배**(0.4/0.8/1.6), `PARAM_RANGES` 의 모든 키가 `PARAMS` 에 있는지를 단위 테스트로.
- **CI 분리** — CI(GPU 없음)는 **수치 판정만**. `--use-angle=swiftshader --enable-unsafe-swiftshader`(`--disable-gpu` 는 넣지 말 것 — 조용히 SwiftShader 로 되돌린다). 골든·영상은 GPU 러너 또는 로컬. **소프트웨어 렌더링 골든은 영구 플레이키가 된다.**

### 6-7. 사람이 해야 하는 것 — 고정 절차 5~8분

정지 비교는 무의미하다. **매번 같은 순서·같은 시간**으로 돌린다.

1. **정지 30초** — 물이 살아 있나? 파면이 반복 패턴으로 보이나?
2. **가속 → 정속 → 정지** 각 5초 — 배가 파를 타나, 미끄러지나
3. **좌/우 선회** 각 5초 — 항적이 곡선으로 남나, 끊기나
4. **0.25배속 재생** — **컷아웃이 의도로 읽히는가, 버그로 읽히는가.** 이 구분이 이 프로젝트 모션 품질의 핵심이다
5. **한 파라미터씩 극단으로** 밀었다 되돌려 원래 그림으로 정확히 복귀하는지 (상태 누수 탐지)
6. **원경 지평선 10초 정지** — 모아레·선 겹침

각 항목에 통과/실패와 **한 줄 근거**를 남긴다. "괜찮다" 는 기록으로 인정하지 않는다.
before/after 는 `ffmpeg -i before.webm -i after.webm -filter_complex hstack out.mp4` 로 병치.

> Awwwards 심사에서 OceanX 2025 는 Creativity 7.79 인데 **Development 6.65 로 가장 낮았다.**
> 비주얼이 좋아도 개발 완성도는 따로 평가된다 — **12fps/8fps 드롭은 "의도"임이 명확히 읽히지 않으면 버벅임으로 오독된다.**

### 6-8. 접근성

- **`prefers-reduced-motion` 대응이 현재 0 이다.** 물을 완전히 멈추면 배가 뜬 채 굳으므로,
  "정지" 가 아니라 **"진폭 축소 + 반짝임 제거 + 자동 표류 중지"** 가 이 씬에 맞는 대응이다
  (`reduce` 는 "모션 최소화" 이지 "모션 금지" 가 아니다).
- **캔버스 sub-DOM** — `<canvas>` 여는 태그와 닫는 태그 **사이**의 DOM 은 보조기술에 노출되고 탭 순서에도 들어간다.
  향수 클릭 오브젝트를 만들 때 **같이 안 하면 나중에 못 붙인다.**
  ⚠ 캔버스 안 요소는 포커스는 되지만 **포커스 링이 그려지지 않는다** — `focus` 이벤트를 받아 씬에 직접 렌더해야 한다.
- **플래시** — `glintAmount 0.8` + `glintScatter 18` + 12fps 컷아웃 조합은 실제 위험 구간이다.
  릴리스 전 [PEAT](https://www.trace.umd.edu/peat/) 로 60fps 영상 정식 검사.
