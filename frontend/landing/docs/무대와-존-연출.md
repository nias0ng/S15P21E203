## 0. 무엇을 만드는가

레퍼런스 두 장(사용자 제공, 2026-09-09)의 차이가 그대로 명세다.

| 층 | 평상시 | 존 진입 후 | 지금 코드에 있는가 |
|---|---|---|---|
| 하늘 · 태양 · 수평선 | 있음 | 있음 | ⭕ **생겼다** (§12 수평선 · §14 하늘) — ⚠ 하늘이 아직 거의 안 보인다 |
| 원경 산 실루엣 · 안개 | 있음 | 있음 | ❌ 없다 — **[3단계]** |
| 좌우 근경 암석 프레임 | 없음 | 화면 좌우를 덮는다 | ❌ 없다 |
| 대형 타이포 `WOODY` | 없음 | 수평선에 걸쳐 수면에서 솟는다 | ❌ 없다 |
| 우측 향조 정보 · 좌하단 `03 ZONE` | 없음 | 있음 | ⭕ `scent-card` 계열 |
| 카메라 | 항해 구도 | **다른 구도로 전환** | ⭕ 파라미터는 이미 있다 (§4) |

⚠ **핵심은 마지막 칸이 아니라 첫 두 줄이다.** 등장하는 것(암석·타이포)보다, *평상시 화면에 이미
있어야 하는 것*이 우리에게 없었다. **`WOODY` 가 걸릴 선이 없었다** — 그래서 [0단계]가 수평선
실측이었다.

⚠ 이 문단에 처음 적었던 *"`fade0/fade1 = 20/40` 이라 물이 40 월드에서 사라진다"* 는 **틀렸다.**
그 값은 `camDist` 를 곱해 79.2/158.4 가 되고(§12-8), 실제로 물을 지우는 것은 **UV 가장자리
페이드**다(§14-5). 두 번 정정했으니 인용할 때는 §14-5 를 본다.

### ⚠ 이 방향은 `README.md` 첫 줄과 충돌한다

> *"흰 여백 위를 종이배 한 척이 떠간다. **하늘도 지평선도 없고**, 물은 배경색으로 흩어져 사라진다."*

이건 버그가 아니라 아트 디렉션 **선언**이고, `CLAUDE.md` 의 불변식 여럿이 그 위에 서 있다.
수평선을 세우면 그 선언이 바뀐다. **코드보다 이 문장을 먼저 고칠지 정한다.**

관련해서 열린 결정 하나 : 레퍼런스는 전부 **은백색 밝은 바다**인데 지금은 `waterTone` **0.85**
(짙은 회청, 2026-09-08 사용자 지시)다. 수평선이 생기면 물과 하늘의 밝기 관계를 새로 정해야 한다.
**사용자 확인 없이 만지지 않는다.**

## 1. 이 기법의 이름 — 인용할 때 여기서 가져온다

사용자 질문 : *"화면과 다른 이런 레이아웃 효과를 어떤 기법이라고 부르는지"*

| 우리가 만드는 것 | 이름 | 어디서 온 말인가 |
|---|---|---|
| 좌우 근경이 화면을 감싸는 것 | **포그라운드 프레이밍** (foreground framing) · **내추럴 프레이밍** | 촬영. 근경 물체로 피사체를 둘러싸 시선을 가둔다 |
| 그 좌우 판 자체 | **윙**(wings) · **레그**(legs) | 무대. 객석에서 안 보이게 좌우를 가리는 막 |
| 깊이별로 판을 여러 장 겹쳐 다른 속도로 움직이는 것 | **멀티플레인** (multiplane) | 디즈니 멀티플레인 카메라(1937). **이 연출의 정확한 이름이다** |
| 마우스에 따라 카메라가 조금 움직이는 것 | **마우스 패럴랙스** · **카메라 스웨이**(sway) | 웹 인터랙션 |
| 글자가 수면에 잘려 솟는 것 | **마스크 리빌** (mask reveal) · 여기서는 **워터라인 클리핑** | 모션 그래픽 |
| 화면이 통째로 다른 구도로 바뀌는 것 | **시네마틱 트랜지션** · 카메라 리그 전환 | |
| 만지지 않아도 살아 있게 하는 미세한 움직임 | **아이들 모션** (idle motion) · **세컨더리 애니메이션** | 애니메이션 |

⚠ **패럴랙스 스크롤링이 아니다.** 그건 스크롤이 구동축인 2D 기법이고, 우리는 **마우스와 상태**가
구동축인 3D 멀티플레인이다. 문서·발표에서 섞어 쓰지 않는다.

## 2. 층 구조 — 넷으로 쪼갠다

"등장 이펙트" 하나로 뭉치면 파라미터 하나로 못 묶는다. 성질이 다른 넷이다.

```
        ┌────────────────────────────────────────────────────────┐
        │  phase.js   상태머신 + 중립 상태 객체(cue)               │
        │  ⚠ THREE 를 import 하지 않는다. 씬을 모른다             │
        └──────────────────────┬─────────────────────────────────┘
                               │  cue = { zone, t, open, rise, look, dim }
      ┌────────────┬───────────┴───────────┬────────────────┐
      ▼            ▼                       ▼                ▼
  stage.js      title.js                gate.js        main.js 카메라 블록
  원경 무대      수면 타이포              좌우 윙          camPitch/Yaw/Dist
  하늘·산·안개   워터라인 클리핑          멀티플레인 3층    를 cue 로 민다
  (상시)        (게이트 시계)            (실시간)         (실시간)
```

네 층은 **서로를 모른다.** 각자 매 프레임 `cue` 만 읽는다. `main.js` 에 `update()` 세 줄이 는다.

작업계획 [5단계]의 규율 그대로다 — *"절대 three 객체를 직접 트윈하지 마라. 중립 객체 하나만 몰고
렌더 루프가 그 값을 읽는 유일한 지점이 되게 한다."* `cue` 가 그 중립 객체다.

**되돌리는 값은 층마다 하나씩** (`docs/롤백-지도.md` 규율, `bloom.js` 가 이미 그 패턴) :
`stageAmount` / `titleAmount` / `gateAmount` 가 0 이면 그 층은 씬에 아예 안 들어간다.

## 3. 전환의 해부 — 무엇이 언제 움직이는가

사용자 : *"하단 좌우 오브젝트가 **순서대로 좌, 우로** 등장하고 바다 수평선 쯤에서 텍스트가
수면위로 떠오르는 연출"*

| 시각 | 층 | 움직임 | 커브 |
|---|---|---|---|
| 0.00 → 2.00s | 카메라 | 항해 구도 → 존 구도 | `easeInOutCubic` |
| 0.00 → 1.15s | `gate` **좌** | 화면 밖 왼쪽 → 안으로 | `easeOutCubic` |
| **0.22** → 1.40s | `gate` **우** | 화면 밖 오른쪽 → 안으로 | `easeOutCubic` |
| 0.15 → 1.00s | `stage` | 안개가 짙어지고 원경이 향조 색으로 물든다 | `easeOutQuad` |
| **0.55 → 1.45s** | `title` | 수면 아래 → 위로 솟는다 | `easeOutBack` |
| 1.20s → | DOM | 우측 향조 정보 · 좌하단 `03 ZONE` 페이드인 | `easeOutQuad` |

⚠⚠ **2026-09-10 에 전체를 늦췄다** (1.20 → 2.00s) — 사용자가 화면을 보고 *"그렇게 빠르게
진행할 필요는 없음 전체적으로"*. 커브도 `outExpo` → `outCubic` 으로 바꿨다 —
outExpo 는 t=0.1 에 벌써 50% 라 튀어나온 뒤 **마지막 3% 를 남은 시간 내내** 좁혔고,
그 3% 가 화면에서 **좌우 가장자리의 틈**으로 보였다.

**좌우 0.22s 시차가 "순서대로" 의 전부다.** 이보다 크면 두 동작으로 쪼개져 보이고, 0 이면
자동문이 된다. 프레임이 닫히는 동안 타이포가 그 안에서 솟아 **먼저 멈춘다** — 셋이 같이
끝나면 슬라이드쇼가 된다.

⚠ 나가는 연출(존 → 항해)은 **들어온 순서의 역순이 아니다.** 타이포가 먼저 가라앉고, 좌우가
같이 열리고, 카메라가 마지막에 돌아온다. 역순으로 재생하면 "되감기" 로 읽힌다.

## 4. 카메라 — ⭐ 리그를 새로 만들지 않는다

### 이미 있다

`main.js:248~274` 가 카메라를 **구면 좌표**로 배치한다. 파라미터 셋이 이미 나와 있다.

| 파라미터 | 지금 | 뜻 |
|---|---|---|
| `camPitch` | **15.4** (2026-09-09 : 23.1 → · §12-9) | 내려다보는 각(도). **수평선 위치를 정한다** |
| `camYaw` | −52.1 | look 점을 축으로 옆으로 돈 각(도) |
| `camDist` | 3.96 | look 점에서 물러난 배율 |

⚠ 이 셋은 좌하단 **시점 패널**(`campanel.js`, §13)에서 실시간으로 만질 수 있다.

→ **전환은 이 셋을 트윈하는 일이다.** 새 카메라도, 새 리그도, GSAP 도 필요 없다.
`cue` 가 목표값 셋을 들고, `main.js` 의 카메라 블록이 그걸 읽는 유일한 지점이 된다.

### ✅ 반사 지뢰는 이미 해소돼 있다

작업계획 1-2 의 *"카메라를 움직이는 순간 터지는 지뢰"* 는 **낡은 경고다.**
`src/reflect.js:89` 주석 : *"⚠ 예전에는 `CONFIG.cam.look` 을 고정으로 봤다."*
지금은 137~141행이 본 카메라의 실제 `position` 과 전방 벡터에서 파생시킨다. **따라온다.**

남은 `CONFIG.cam.look` 고정 참조는 둘뿐이다 :
- `main.js:249, 274` — **여기가 바꿀 곳이다**
- `viewbar.js:130` — 개발 바 전용. 프로덕션에 없다

### ⚠⚠ 그러나 `camDist` 는 카메라만 움직이지 않는다 — 이 문서에서 제일 큰 지뢰

`water.js:2284~2292` :

```
uni.uFade0.value = CONFIG.surface.fade0 * kD;   // kD = P.camDist
uni.uFade1.value = CONFIG.surface.fade1 * kD;
```

`uFloorNear`(429행)와 LOD 도 같은 배율을 탄다. 즉 **`camDist` 를 트윈하면 바다의 끝과
바닥 격자가 같이 숨을 쉰다.** 카메라가 물러날 때 페이드를 같이 밀어 주려고 일부러 만든
연결(2026-09-06)인데, 1.2초 전환에서는 **원경이 부풀었다 줄어드는 것으로 보인다.**

**선택지 :**

| | 무엇 | 대가 |
|---|---|---|
| A | 전환 중 `camDist` 를 고정하고 `camPitch`/`camYaw` 만 트윈 | 전환이 덜 극적이다 |
| B | 페이드 배율을 `camDist` 에서 떼어 별도 `cue` 값으로 | 2026-09-06 결정을 되돌리는 것. 물러남 보정을 손으로 다시 짜야 한다 |
| C | 그대로 두고 눈으로 판정 | 수평선이 생긴 뒤에는 **원경이 훨씬 잘 보인다** — 예전 판정을 재사용할 수 없다 |

→ **2단계(원경 페이드 재조정)에서 같이 결정한다.** 수평선을 세우기 전에는 판정할 화면이 없다.

⭐ **2026-09-09 실측으로 이 지뢰가 완화됐다 — §12-8 참고.** 지금 `camDist` 3.96 에서는
페이드가 물 메시 **밖**(79.2 / 158.4 vs 물 끝 104.5)이라 24% 만 진행된 채 잘린다. 전환 범위를
`camDist` **2.75 위**로 잡으면 페이드가 계속 잠들어 있으므로 선택지 **C** 로 갈 수 있다.

### 마우스 패럴랙스 — ⚠ orbit 이 아니라 look 도 같이 옮겨야 한다

사용자 : *"마우스를 움직이면 약간식 카메라 각도를 변경하여 좌우 화면을 약간더 확인할 수 있는"*

`cam.lookAt(CONFIG.cam.look)` 이 고정이므로 `camYaw` 에 마우스를 더하면 **같은 점 주위를 도는
궤도 운동(orbit)** 이 된다. 좌우가 더 보이는 게 아니라 **같은 것을 다른 각도에서 볼 뿐이다.**

좌우를 더 보려면 **look 점도 마우스 쪽으로 옮긴다**(팬). 카메라는 반대로 조금 움직이면 시차가
커진다. 권장 배분 :

| | 양 | 효과 |
|---|---|---|
| `camYaw` 가산 | ±2.5° | 미세한 각도 변화 |
| look 점 수평 이동 | ±0.35 월드 | **좌우가 실제로 더 보인다** |
| `camPitch` 가산 | ±1.2° | 세로. 가로의 절반 이하로 — 넘으면 뱃멀미가 난다 |

⚠⚠ **마우스 룩에 ease 나 트윈을 걸지 않는다.** 목표가 매 프레임 바뀌므로 트윈이 계속
재시작돼 끈적거린다. **크리티컬 댐핑 lerp** 가 정답이고, 이 코드가 이미 그 패턴을 쓴다 :

```
nav.speed += (target - nav.speed) * CONFIG.cam.lerp;    // main.js:175
nav.headV += (... - nav.headV) * M.turnLerp;            // main.js:213
```

⚠ 마우스 패럴랙스는 **존 화면에서만** 켠다. 항해 중에 켜면 `input.js` 의 드래그 판정(SLOP 6px)과
겹쳐 "조타하려는데 화면이 흔들린다" 가 된다.

⚠ 전환 중에는 **끈다.** 트윈 목표와 마우스 오프셋이 같은 값을 두 곳에서 밀면 도착점이 흔들린다.
전환이 끝난 뒤 0.3초에 걸쳐 마우스 영향력을 0 → 1 로 올린다.

## 5. 좌우 윙 — 덩어리 하나가 아니라 멀티플레인 3층

사용자 질문 : *"덩어리 크게 하나 좌우로 레이아웃이 등장하게 할지 / 여러 개 SVG 형태나 이미지
형태로 겹쳐서 그것조차 마우스를 올렸을때 돌아가거나 흔들리는 연출까지 넣어야할지"*

### 답 — **여러 겹으로 나눈다. 단 개별 hover 는 넣지 않는다.**

두 질문이 붙어 있지만 답이 다르다.

**나누는 것은 필수다.** 요청하신 *"마우스를 움직이면 좌우 화면을 약간 더 확인할 수 있는"* 연출은
**깊이가 있어야만 성립한다.** 덩어리 하나면 카메라를 움직여도 판이 통째로 미끄러질 뿐이라
**판자로 읽힌다.** 깊이가 다른 판이 서로 다른 속도로 어긋나야 그게 공간이 된다 — 그게 멀티플레인이다.

**개별 hover 는 반대다.** 이유 셋 :

1. **레이캐스트 대상이 는다.** `input.js` 의 클릭/드래그 분리(SLOP 6px)와 `marks.pick` 이 지금
   간신히 균형을 잡고 있다. 배경 판까지 피킹 대상이 되면 *"향수를 고르려고 눌렀는데 배경이 반응"* 이 난다.
2. **프레임은 배경이다.** 반응하면 클릭할 수 있다는 힌트가 되고, 눌러도 아무 일이 없으면 그게 버그로 읽힌다.
3. **필요가 없다.** 카메라 하나만 움직이면 6판이 전부 다른 속도로 움직인다. **판마다 코드를 쓸 이유가 없다.**

살아 있는 느낌이 필요하면 판마다 **위상이 다른 아주 느린 sway 한 줄**(진폭 0.2° 안팎)이면 된다.
인터랙션이 아니라 아이들 모션이라 비용이 사실상 0 이다.

### 구성

| 층 | 카메라에서 | 마우스 반응 | 화면에서 |
|---|---|---|---|
| 근경 | 가장 가깝다 | 가장 많이 움직인다 | 화면 모서리. 어둡고 디테일이 뭉개져 있다 |
| 중경 | 중간 | 중간 | 형태를 알아볼 수 있는 주된 실루엣 |
| 원경 | 가장 멀다 | 거의 안 움직인다 | 안개에 반쯤 먹힌다 |

좌우 3층씩 **6판**. ⭐ **좌우는 같은 이미지를 반전해 쓴다** — 이미지 **3장**으로 6판이 선다.
웹 무게가 정확히 절반이 된다. (자연물이라 반전이 티나지 않는다. 티나면 그 판만 따로 그린다.)

### 이미지 규격 — 사용자가 만들어 제공

| | 권장 |
|---|---|
| 포맷 | **WebP + 알파.** PNG 대비 60~70% 작다. AVIF 는 인코딩이 느리고 이득이 적다 |
| 크기 | 근경 1536px · 중경 1280px · 원경 1024px (긴 변 기준) |
| 예산 | **3장 합계 400KB 이하.** 넘으면 원경부터 줄인다 |
| 색 | ⚠ **원경은 이미 안개에 먹힌 상태로 그리지 않는다.** 안개는 셰이더가 입힌다. 두 번 입히면 사라진다 |
| 여백 | 화면 바깥으로 나가는 쪽에 **최소 15% 여백.** 등장 전 위치에서 가장자리가 보이면 안 된다 |

⚠ **SVG 는 쓰지 않는다.** three.js 에서 결국 래스터화하거나 `SVGLoader` 로 지오메트리를 만들어야
하는데, 암석 같은 유기적 형태는 패스가 수천 개가 되어 **PNG 보다 무거워지고 드로우콜도 는다.**
SVG 가 이기는 것은 로고·아이콘처럼 패스가 적고 무한 확대가 필요한 경우다.

### 예산

지금 기준선은 `draw 13 / tri 131126` 이다. 6판 = **`draw +6`** (19). 판마다 삼각형은 2개다.
⚠ 기준선이 움직이므로 이 단계가 끝나면 `perf-report.json` 을 새로 찍는다.

## 6. 타이포 — ⭐ 이미지 없이 웹폰트로 간다

사용자 : *"폰트 정도는 일반적으로 지원되는 웹폰트를 사용해서 (…) 이미지를 사용하는 것보다
훨씬 웹 무게가 가벼워질텐데 그렇게 진행 가능하면"*

### 가능하다. 권장한다.

**경로 : 웹폰트 → Canvas 2D → `CanvasTexture` → 3D 평면.**

| | 왜 |
|---|---|
| 자산 | **0 바이트.** 글리프를 런타임에 그린다 |
| 텍스처 | ⭐ **1장을 재사용한다.** 한 번에 한 향조만 보이므로, 존이 바뀔 때 같은 캔버스에 다시 그린다 |
| 3D | 평면이라 **배가 글자 앞을 지나고 수면에 잘린다.** 레퍼런스가 정확히 그 그림이다 |
| 수정 | 향조 이름·자간·굵기를 코드에서 바꾼다. 이미지 다시 뽑을 일이 없다 |

### 다른 길과 비교

| 방법 | 판정 |
|---|---|
| **CanvasTexture** ⭐ | 의존성 0. 크기 고정. **이걸 쓴다** |
| MSDF (`troika-three-text`) | 어떤 크기에도 벡터급으로 선명. 하지만 **의존성이 는다** — 지금 이 리포는 `three` 하나뿐이다 |
| `TextGeometry` | `typeface.json` 자산이 필요하고 삼각형이 수천 개. 두께가 필요할 때만 |
| DOM 오버레이 | ❌ **배 뒤로 못 간다.** 항상 캔버스 위에 뜬다 |
| 이미지 4장 | ❌ 무겁고, 향조가 늘면 다시 뽑아야 한다 |

### 해상도 — 화면 폭에서 역산한다

`WOODY` 가 화면 폭의 약 60% 를 먹는다. 1600px 창 · dpr 2 → 실제 필요 **약 1920px**.

→ **2048 × 512 로 시작한다.** 4K · dpr 2 에서는 부족하므로 캔버스 크기를 `min(4096,
화면폭 × dpr × 1.3)` 로 잡고 리사이즈 때 다시 굽는다. ⚠ 알파만 쓰면 되지만 `CanvasTexture` 는
RGBA 로 올라간다 — 2048×512 RGBA ≈ **4MB**. 1장 재사용이므로 이걸로 끝이다.

### ⚠⚠ 폰트 로딩 — 여기서 반드시 한 번 문다

`document.fonts.ready` 를 **기다리지 않고** 캔버스에 그리면 **폴백 폰트로 구워진다.** 그리고
텍스처는 이미 GPU 에 올라갔으므로 폰트가 나중에 도착해도 **화면은 영원히 폴백이다.**
새로고침하면 캐시 덕에 맞게 나와서 **재현이 들쭉날쭉하다** — 개발 중엔 멀쩡하고 배포하면 틀어진다.

`document.fonts.load()` 로 해당 굵기·크기를 명시적으로 기다린 뒤 굽는다.

### 폰트 선택

레퍼런스의 `WOODY` 는 **기하학적 산세리프 대문자, 자간이 넓고 획이 굵다.**
`index.html` 이 이미 Pretendard 를 CDN 에서 받고 있지만 그건 한글 본문용이다.

→ 라틴 대문자만 쓰므로 **구글 폰트 하나를 라틴 서브셋으로** 받는 게 맞다. 후보 : Jost ·
Archivo · Outfit. ⚠ **서브셋을 꼭 건다** (`&text=ABCDEFGHIJKLMNOPQRSTUVWXYZ`) — 전체 파일은
수백 KB 지만 대문자 26자면 **10KB 아래**다.

⚠ 시스템 폰트 스택으로 때우지 않는다. Windows·macOS·Android 에서 전부 다르게 나와
**대형 타이포에서는 그 차이가 그대로 보인다.**

### 워터라인 클리핑 — 어떻게 "수면에서" 솟는가

글자의 아래쪽이 **수면에 잘려야** 물에서 나오는 것으로 읽힌다. 방법 둘 :

| | 무엇 | 대가 |
|---|---|---|
| A | 평면을 수면 아래에 두고 **월드 y 로 알파를 자른다** | 직선으로 잘린다. 파도가 있으면 어색하다 |
| B | 수면 높이맵(`sim.texture`)을 읽어 **파도를 따라 자른다** | ⭐ 물결이 글자를 넘나든다. 텍스처 페치 1회 추가 |

→ **B 를 권한다.** 이 프로젝트에서 물과 무관하게 움직이는 층은 전부 "붙인 스티커" 로 읽혔다
(`CLAUDE.md` 불변식 14 의 교훈). 페치 1회는 지금 비용 지도(픽셀당 최대 54)에서 무시할 만하다.

⚠ **솟는 높이는 `sim.qT` 게이트를 탄다** (`README.md` 규칙 2). 실시간이면 이 층만 60fps 로
미끄러져 *"배는 끊기는데 글자만 매끄러운"* 부조화가 난다. `CSS2DRenderer` 를 안 쓴 것과 같은 이유다.
**밝기·알파는 실시간이어도 된다** — *"형태는 멈춰도 빛은 계속 흐른다."*

### ⚠ 접근성 — `CLAUDE.md` 와 충돌하는 지점

*"텍스트는 전부 DOM 에 둔다 — 캔버스에 그리면 SEO·스크린리더·복사·번역·확대를 전부 잃는다."*

→ 대형 타이포는 **순전히 장식**으로 선언하고(`aria-hidden`), 같은 글자를 **우측 정보 블록의
DOM 제목으로 한 번 더** 둔다. 레퍼런스 2번 사진도 우측에 `WOODY` 를 따로 적고 있다 —
**원본 디자인이 이미 그 답을 냈다.**

## 7. ease 규약 — GSAP 을 넣지 않는다

사용자 : *"연출 대부분 극적인 연출이 필요하니 ease 관련 효과를 다 넣긴해야함"*

### 커브 표

| 무엇 | 커브 | 왜 |
|---|---|---|
| 카메라 전환 | `easeInOutCubic` | 양끝이 부드럽다. 구도 이동의 기본 |
| 더 극적으로 | `easeInOutQuint` | 중간이 훨씬 빠르다. 1.2s 를 0.8s 처럼 느끼게 한다 |
| 윙 등장 | `easeOutExpo` | **빠르게 들어와 천천히 멈춘다.** 등장은 전부 out 계열 |
| 타이포 솟기 | `easeOutBack` | 살짝 넘겼다 돌아온다. **물에서 튀어나온 관성**이 된다 |
| 안개·DOM 페이드 | `easeOutQuad` | 눈에 안 띄어야 하는 것은 약한 커브로 |
| 퇴장 | `easeInCubic` | 천천히 시작해 빨라진다. 등장의 거울 |
| **마우스 패럴랙스** | ❌ **ease 아님 — 댐핑 lerp** | §4 참고. 트윈을 걸면 끈적거린다 |

⚠ `easeOutBack` 의 오버슈트는 **타이포에만** 쓴다. 윙에 걸면 화면 밖에서 되돌아오는 게 보인다.

### GSAP 은 쓰지 않는다

작업계획 [5단계]가 GSAP 을 언급하지만, **이 규모에 필요 없다.**

- 필요한 커브 6개는 각 한 줄이다. 합쳐서 **10줄**
- 타임라인이라 해 봐야 §3 표 한 장이고, `phase.js` 안의 `t` 하나로 전부 파생된다
- 이 리포의 의존성은 `three` **하나**다 (`package.json`). 그게 강점이다
- **⚠ GSAP 은 60fps 로 도는데 물은 12fps 다.** 물에 닿는 값(타이포 높이)을 GSAP 이 몰면
  게이트를 우회하게 된다. 직접 짜면 그 실수를 할 방법이 없다

타임라인이 스크롤·분기까지 감당해야 할 만큼 커지면 그때 다시 본다. (GSAP 은 2025년 4월부터
ScrollTrigger 포함 전면 무료라 언제 들여도 비용이 없다.)

## 9. 지뢰 — 이 프로젝트에서만 나오는 것

1. **⚠⚠ `camDist` 가 물의 원경 페이드를 끌고 간다** — §4. 이 문서에서 제일 큰 것
2. **블룸이 새 층을 삼킨다.** `bloomThreshold` 1.40 은 부표를 물(p95 0.965) 위로 띄우려고 잡은
   값이다. 흰 타이포나 밝은 암석이 그 사이에 끼면 **의도 없이 빛난다.** 어두운 암석은 무관하다
3. **반사 참여를 층마다 따로 정한다.** `reflect.add(obj)` 한 줄이면 되지만 ⚠ 렌더타깃이
   좌우 반전(`flipX: true`)이라 새 소비자는 `ruv.x = 1.0 - ruv.x` 를 같이 가져가야 한다.
   ⚠⚠ **2026-09-10 에 뒤집혔다.** 여기 오래 적혀 있던 *"레퍼런스를 보면 암석은 비치고
   **타이포는 거의 안 비친다**"* 는 이제 반대다 — 사용자가 **타이포를 비치게** 해 달라고 했다.
   `reflect.add(title.mesh)` 한 줄로 들어갔다 (v0.28.0).
   ⚠ 그리고 **암석(gate)은 넣지 않는다** — 원래 문장과 정반대인데 이유가 있다. 판이
   `depthTest:false` + `renderOrder 20` 이라 반사 타깃에서도 모든 것 앞에 그려져 **반사를
   통째로 덮는다.** §11 의 *"본 카메라에 매달린 물체는 엉뚱한 곳에 선다"* 가 그 얘기다.
   ⚠ 타이포가 괜찮은 이유는 자리를 카메라에서 **파생**시킬 뿐 월드에 실재하기 때문이다.
   ⚠ 세기는 배와 **같다** — 타이포만 옅게 하려면 반사 패스일 때만 `uAmount` 를 낮추는
   `onBeforeRender` 한 단계가 더 필요하다.
4. **전환 중 클릭 차단.** `input.js` 의 `onPick` 이 `marks.pick` 을 바로 부른다.
   전환 중 재클릭이면 `cue` 가 두 향조 사이에서 찢어진다
5. **GLSL 주석 안의 백틱이 빌드를 죽인다** (셰이더가 템플릿 리터럴). 이미 한 번 죽었다
6. **게이트를 곱으로 쌓지 않는다** — 페이드가 셋(거리·안개·연출)이면 화면 최대차가 몇 레벨로 죽는다
7. **드로우콜 예산.** 기준선 `draw 13 / tri 131126` → 윙 6 + 타이포 1 + 하늘 1 = **`+8`**.
   이 단계가 끝나면 `perf-report.json` 을 새로 찍는다
8. **⚠ 창이 안 보이면 시간 기반 측정이 전부 거짓이다** (`docs/다음-세션.md` §2).
   ease 타이밍을 재려면 창을 실제로 띄워 둔다
9. **`zones.js` 의 자동 조타가 지금 보이지 않는 곳으로 향한다** (그 파일 주석에 그대로 적혀 있다).
   ⭐ 이 연출이 **'이 향의 해역으로' 버튼이 도착했을 때 보여줄 그림**의 빈자리를 그대로 채운다 —

## 12. [0단계] 수평선 실측 — ✅ **끝났다** <span>— 2026-09-09</span>

> 측정 조건 : v0.15.7 · 캔버스 **792×682** · 정지(`s` 0, `fov` **43**) ·
> `camPitch` **23.1** · `camYaw` −52.1 · `camDist` **3.96** · 개발 UI 숨김
> ⚠ px 값은 캔버스 높이에 비례한다. **비율(%)로 인용하라.**

### 12-1. 식 — 수평선은 `camPitch` 와 `fov` 만으로 정해진다

```
수평선 NDC y = tan(camPitch) / tan(fov_v / 2)        [ 1 을 넘으면 화면 밖 ]
화면 y(px)   = (1 − NDC y) / 2 × 캔버스높이
```

⚠ **종횡비와 무관하다.** 창을 넓혀도 수평선은 안 움직인다.
⚠ `fov` 는 three 에서 **수직** 화각이다. 수평으로 착각하면 값이 통째로 틀어진다.

**검산** : 카메라 전방 무한원점(1e6)을 실제로 투영한 값과 위 식이 **오차 4.5e-5** 로 일치했다.
광축 하향각도 **정확히 23.100°** 로 `camPitch` 와 같다 — 구면 좌표 배치(`main.js:265~274`)와
`lookAt` 이 정확히 맞물려 있다는 뜻이다. **`camPitch` 는 곧 광축 하향각이다.**

### 12-2. ⚠⚠ 결론 : 지금 수평선은 **화면 밖**이다

| 상태 | `fov` | 수평선 NDC | 화면 y(px) | |
|---|---:|---:|---:|---|
| **정지** | 43.00 | **1.0828** | **−28** | ⚠ **화면 위로 4.1% 밖** |
| 순항 (s 0.45) | 47.95 | 0.9591 | +15 | 겨우 걸린다 |
| 부스트 (s 1.0) | 54.00 | 0.8371 | +59 | 화면 안 |

### 12-3. ⚠ 부수 발견 ① — 속도가 수평선을 **88.5px 출렁이게** 한다

`fov` 가 속도에 따라 43↔54 로 변한다(`CONFIG.cam.fovNear/fovFar`). 그래서 가속만 해도
수평선이 **화면 높이의 12.3%** 만큼 위아래로 움직인다. **지금은 수평선이 없어서 아무도 몰랐다.**
수평선을 세우는 순간 이게 화면에서 제일 눈에 띄는 움직임이 된다.

→ 1단계에서 같이 정한다 : `fovNear/fovFar` 폭을 좁힐 것인가, 수평선을 `fov` 와 무관하게 고정할 것인가.


⚠ **예전처럼 `querySelectorAll` 로 숨기지 마라.** `tweaks` 는 `display:flex` 인데 인라인
스타일 하나로 선언돼 있어서, `style.display = ''` 로 지우면 **flex 까지 같이 지워져 레이아웃이
깨진다.** `solo()` 는 원래 값을 `Map` 에 기억했다가 돌려준다.

### ⚠ 만든 사람이 밟은 것 둘

1. **TDZ** — `campanel` 을 `tweaks`·`viewbar` 뒤(`const`)에 선언했더니 `tick()` 이 그 전에
   시작해 **매 프레임** `Cannot access 'campanel' before initialization` 이 터졌다.
   `let campanel = null` 을 루프 **앞**에 두고 뒤에서 대입한다.
   ⚠ `tweaks`·`viewbar` 가 무사한 것은 **루프에서 안 읽기 때문**이지 순서가 안전해서가 아니다.
2. **`box-sizing: border-box`** — `index.html` 이 전역으로 걸어 둬서 게이지의 `height:74px` 에
   테두리 2px 이 포함된다. 그걸 기준으로 선을 그으면 2px 어긋난다 → `clientHeight` 를 쓴다.

### 검증 (2026-09-09, 캔버스 720px)

- 수평선 **15.0% · 108px** · 원경 띠 **12.9% · 93px** · 물끝 **28.0% · 201px** — §12-9 실측과 일치
  ⚠ 물끝은 **화면 중앙 열 정면** 기준이다. 좌우로 갈수록 가까워져 실제로는 아치가 된다 (§12-4)
- 프리셋 : 10%→17.5° · 15%→**15.4°** · 20%→13.3° · 25%→**11.1°** · 밖→23.1° ✅
- `[화면만]` → 넷 다 `none` · `H` → `tweaks` 가 `flex` 로 정확히 복원 ✅
- 검색창 안에서 `h` 를 쳐도 숨지 않는다 ✅

### 14-1. 무엇을 만들었나

카메라를 따라다니는 반지름 300 스카이 스피어(`BackSide` · `depthWrite:false` ·

쓴다 — 물이 반사에 부르는 것과 **글자 그대로 같은 함수**라 화면의 하늘과 물에 비친 하늘이

### 14-2. ⚠⚠ 태양이 세 곳에서 갈라져 있었다 (기존 버그)

`sky.js` 주석이 *"둘이 다른 하늘을 반사하면 그 순간 같은 장면에 있는 것으로 안 읽힌다"* 고
경고했는데, **실제로 갈라져 있었다.** `sunRot` 이 들어오면서(2026-09-07~08) 나머지가
따라가지 않은 것이다. 실측 :

| 무엇 | 방향 | 물과의 각도차 |
|---|---|---:|
| **물** (`uLightDir3`, `sunRot` −84 반영) | [ 0.866, 0.249, −0.433] | — |
| 환경맵 (`CONFIG.sun`, `sunRot` 을 모른다) | [−0.340, 0.249, −0.907] | **80.8°** |
| 조명 (`dirLight.position`) | [−0.634, 0.634, 0.444] | **125.7°** |

→ 하늘은 **`water.js` 의 유니폼 객체를 참조로 공유**한다 (복사하지 않는다). 넷째 태양이
생길 방법이 없다. ⚠ **환경맵·조명은 안 건드렸다** — 배 밝기(불변식 0-4 : 돛 254.9 vs
선체 236.9 = 18레벨)가 걸려 있다. §10 에 열린 결정으로 남긴다.

⚠ 참고로 **물의 태양조차 화면 밖**이다 — 광축에서 **31.9°** (화각 반각 21.5°). 화면
오른쪽 위로 벗어나 있다. 레퍼런스는 태양이 화면 중앙 수평선 위다.

### 14-3. ⚠⚠⚠ 화면 변화 실측 — **최대 13레벨, 그나마 방향이 반대다**

⚠ 재는 법 : three 는 hex 를 **선형**으로 바꿔 셰이더에 넣고 `<colorspace_fragment>` 가
다시 sRGB 로 인코딩한다. **그 경로를 그대로 따라가야 한다** — 처음에 hex 를 선형처럼 다뤄
RGB 266 같은 불가능한 값을 얻었다.

| 화면 위치 | 지평선 위 | RGB | 배경색(246,245,242)과 차이 |
|---|---:|---|---:|
| 맨 위·왼쪽 | 5.1° | 246, 246, 243 | **+0.5** |
| 맨 위·중앙 | 6.1° | 254, 254, 251 | +8.3 |
| 맨 위·오른쪽 | 5.1° | 252, 251, 248 | +5.9 |
| 수평선 높이·중앙 | 0° | 254, 253, 250 | +8.4 |

**화면 전체 최대 차이 13레벨.** 눈에 보이는 문턱(연속 그라디언트 약 2레벨)은 넘지만,
이미 246 인 자리가 254 가 되는 것이라 **둘 다 "흰색" 으로 읽힌다.**

#### 원인 둘 — 하나는 각도, 하나는 태양 로브

1. **화면에 보이는 하늘이 지평선 위 6.1° 뿐이다.** `SKY.band` 가 0.55(≈33°)라 그라디언트의
   **약 10% 구간만** 화면에 든다. 천정이 어두운 효과(−15레벨)가 거의 나타나지 않는다.
2. **넓은 태양 로브가 그 자리를 채운다.** `broadK` 6.0 은 매우 넓어서 태양이 31.9° 밖에
   있어도 `pow(cos 31.9°, 6) = 0.374` 만큼 기여한다. 그래서 **위가 오히려 밝아졌다.**

⚠ `sky.js` 의 규칙 *"천정을 지평선보다 밝게 두지 않는다 — 뒤집으면 물 위에 흰 판이 떠 있는
것처럼 읽힌다"* 는 `zenith` 상수로는 지켜졌지만, **태양 로브가 그 위에 얹혀 결과가 뒤집혔다.**

### 14-4. 왜 이대로 두는가

`SKY` 표는 2026-09-06 에 **반사용**으로 정해졌고 그때 사용자 결정이 *"흰 종이 톤을 유지한다.
레퍼런스의 석양으로 가지 않는다"* 였다. 화면에 그리는 지금은 전제가 달라졌지만,
**그 표를 넓히는 것은 아트 디렉션 변경이라 임의로 못 한다.** §10 의 열린 결정이다.

선택지 (수치는 §14-3 에서 나온다) :

| | 무엇 | 대가 |
|---|---|---|
| A | `SKY.band` 0.55 → **0.12** 근처 | 그라디언트가 화면에 보이는 6° 안에서 일어난다. ⚠ **물이 반사하는 하늘도 같이 바뀐다** (같은 함수를 쓰는 것이 규율이자 대가다) |
| B | `SKY.zenith` 를 더 진하게 | 09-06 아트 디렉션을 뒤집는 것. 가장 직접적이다 |
| C | `broadA` 0.10 → 낮춘다 | 화면 전반의 옅은 밝기를 걷어 낸다. ⚠ 물의 빛 무리도 같이 옅어진다 |
| D | 그대로 두고 **[3단계] 원경 산·안개**로 깊이를 만든다 | 레퍼런스의 하늘도 그라디언트가 아니라 **태양 + 산 실루엣 + 안개**로 읽힌다 |

→ **D 가 유력하다.** 레퍼런스 사진을 다시 보면 하늘 자체의 색 변화는 크지 않고, 화면을
만드는 것은 산의 실루엣과 그 사이의 안개다. 다만 A~C 는 D 와 배타적이지 않다.

### 14-5. ⚠ §12-8 정정 — 물끝은 하드 엣지가 아니다

§12-8 에서 *"물이 76% 불투명한 채로 메시 경계에서 잘린다"* 고 적었는데 **틀렸다.**
`water.js` 의 마지막 줄에 페이드가 **둘** 있고 그중 하나를 못 봤다 :

```glsl
vec2 d = abs(vUv - 0.5) * 2.0;
float vis = (1.0 - smoothstep(0.76, 0.98, max(d.x, d.y)))            // ← UV 가장자리 (못 봤던 것)
          * (1.0 - smoothstep(uFade0, uFade1, length(vW.xz - uCam))); // ← 거리
gl_FragColor = vec4(mix(uBg, c, vis), 1.0);
```

**UV 가장자리 페이드가 물을 녹이고 있다** — 메시 반경 55 기준 **41.8 ~ 53.9 월드**에서
배경색으로 사라진다. 거리 페이드(79.2/158.4)가 잠들어 있어도 이쪽이 일한다.

⚠⚠ 그런데 이 페이드는 `max(d.x, d.y)` 즉 **체비셰프 거리**라 경계가 **정사각형**이다.
원형이 아니다. §12-4 의 아치가 남는 이유가 이것이다 — 물이 사라지긴 하는데 **사라지는
경계선 자체가 네모나다.**

→ **[3단계] 안개의 진짜 할 일이 여기서 정해진다** : 물을 지우는 것이 아니라
(이미 지워지고 있다) **네모난 경계를 원형·거리 기반으로 바꾸는 것**이다.

좌하단, 시점 패널 위에 쌓인다. **묶음마다 [원본] 을 눌러 "그 작업을 하기 전 값" 으로 오간다.**

여기는 *작업 전 값*으로 **묶음별로** 오간다. 켠 채로 A/B 를 반복해야 판정이 된다.

⚠ 숫자를 여기 또 적지 않는다 — 하늘 값 셋은 `sky.js` 의 `SKY` 표에서 `import` 해서 쓴다.

### 곁들여 바뀐 것 — 하늘 값 셋이 런타임 값이 됐다

`SKY.band` / `broadA` / `zenith` 는 GLSL 에 **상수로 굳어** 있어서 파일을 고쳐야만 바꿀 수 있었다.
셋을 유니폼으로 뺐다 (`SKY_UNIFORMS`).

⚠⚠ **`water.js` 와 `stage.js` 가 그 객체를 `spread` 로 가져간다 — 사본이 아니라 공유다.**
한 곳만 갱신하면 둘 다 따라오므로 갈라질 수 없다. 나머지(지평선색·태양색·로브 지수)는 상수로 뒀다.

⚠⚠⚠ **하늘 값이 바뀌면 환경맵을 다시 굽는다** (`main.js` 의 `applySky`). 안 그러면
**배·부표만 예전 하늘을 반사하는** 상태가 된다 — `sky.js` 가 경고한 바로 그것이다.
PMREM 이 끼어 수십 ms 걸리므로 **값이 실제로 바뀌었을 때만** 돈다 (열쇠 비교).
실측 : 하늘 값을 바꾸면 `scene.environment.id` 가 6 → 27 → 30 → 33 으로 갱신되고,

## 16. 부표의 빛과 반사 자리 <span>— 2026-09-09</span>

> 사용자 : *"부표의 블룸값? 또는 밝게 빛나고 있는게 너무 밝게 표현되고있음. (…) 부표가 바다에
> 반사되고 있는 위치 값과 부표의 빛나는 표현의 반사 위치가 지금 다른위치에 구성되고있는데
> 같은 값의 위치에서 반사되게 표현 위치 설정을 맞춰야함"*

두 지적이 **하나의 뿌리**에서 나왔다 — 부표 반사가 **두 경로**로 그려지고 있고
(`docs/다음-세션.md` §6-2 의 미해결 항목), 그 둘이 자리도 밝기도 따로 놀았다.

### 16-1. ⚠⚠ 자리가 갈라진 이유 — 부표가 공중에 떠 있다

| 경로 | 어디에 그리나 | 근거 |
|---|---|---|
| **평면 패스** (`reflect.js`, 레이어 2) | 부표의 **거울상 `y = −markHeight`** | 거울 카메라 투영. 물리적으로 맞다 |
| **해석적** (`markReflect`, `water.js`) | 부표의 **수직 발밑 `y = 0`** | `ground` 항이 xz 거리로 못 박았다 |

`markHeight` **1.95** 라 부표가 물에 안 닿는다(2026-09-03 결정). 그래서 두 기준이 갈라졌다.
**실측 : 화면의 부표 6개 전부 거울상이 발밑보다 32~72px 아래** (평균 49 = 화면의 6.8%).

⚠ **부표가 물에 닿아 있었다면 둘이 같은 자리였다.** 띄우면서 생긴 구조적 불일치이고,
`camPitch` 를 15.4 로 내리며(§12-9) 반사가 세져 눈에 띄게 됐다.

### 16-2. 고친 방법 — `markReflAnchor`

`ground` 의 기준점을 발밑에서 **거울상이 수면과 만나는 자리**로 옮겼다.

```glsl
float tt = cameraPosition.y / (cameraPosition.y + markHeight);
vec2 anchor = mix(cameraPosition.xz, markPos.xz, tt);
```

⭐ **카메라에서 거울상으로 가는 직선 위의 점이라 화면 투영이 정확히 일치한다 — 근사가 아니라
항등이다.** 실측 검산 : 부표 4개 **어긋남 0.000px**.

`markReflAnchor` **0** = 예전(발밑, 비트 단위 롤백) · **1** = 거울상 (지금).

### 16-3. 밝기 — 주범은 블룸이 아니라 `markGlow` 였다

끄면서 좁혔다 :

| | 결과 |
|---|---|
| 블룸만 끔 (`markGlow` 3 유지) | **여전히 밝다.** 부표가 흰 공 |
| 블룸 켜고 `markGlow` 0 | **전혀 안 날아간다.** 부표가 제 색으로 보인다 |

→ 부표 발광이 화면을 포화시키고 **블룸은 그걸 번지게 했을 뿐**이다.

`params.js` 에 이미 있던 실측표가 답을 갖고 있었다 —
`emissiveIntensity 1.2→휘도 1.16 · 2.0→1.51 · 3.0→1.95`, 물 천장 **1.25**, 문턱 **1.40**.

| `markGlow` | 휘도 | 문턱 1.40 | 화면 |
|---:|---:|---|---|
| 3.0 (예전) | 1.95 | 크게 넘음 | 하얗게 날아간다 |
| 2.0 | 1.51 | 넘음 | **아직 날아간다** (반경 0.60 으로 크게 퍼진다) |
| **1.5 (지금)** | 약 1.29 | 아래 | 제 색으로 보이고 물의 반사가 살아난다 |

⚠⚠ **문턱 창이 칼날처럼 좁다** (`tweaks.js` 부제가 경고한 그대로). 1.5 와 2.0 사이가
"안 번짐 ↔ 날아감" 의 이진 전환이다. 은은한 발광을 되살리려면 휘도를 문턱 바로 위로 올리고
**`bloomRadius`·`bloomAmount` 를 같이 낮춰야** 한다 — 시안 `은은` 이 그것이다.

⚠ **`bloomThreshold` 1.40 은 안 건드렸다.** 2026-09-08 실측(물 천장 1.25)에 근거가 있는 값이다.
한 번 1.60 으로 올려 봤지만 그건 근거 없는 판단이었고 **부표가 아예 안 번지게** 만들 뿐이었다.

⚠ 지금 문턱을 넘는 것은 물의 마루·정반사와 **부표 반사 심**(`markReflCore` 3 → 1.81)뿐이다.
더 차분하게 하려면 그다음 손잡이가 `markReflCore` 다.

### 16-6. ✅ 해석적 경로를 버렸다 — `markReflect` 0 <span>— 2026-09-09, 사용자 결정</span>

> 사용자 : *"빛나는 값이 거의 동일해야하는데 (…) 마치 2개의 오브젝트를 관리해야하는 이유가
> 뭐임? 반사 자체가 정말 반사하는게 아니라 물에도 새로운 오브젝트를 띄우는 경우라서그런가?"*

**직관이 맞았다.** 둘은 성질이 다르다 :

| | 평면 패스 (`reflect.js`) | 해석적 (`markReflect`) |
|---|---|---|
| 무엇 | 수면을 거울로 삼아 카메라를 뒤집고 **레이어 2를 한 번 더 그린다** | 물 픽셀마다 반사 광선을 부표 구와 교차 판정해 **색을 칠한다** |
| 진짜 반사인가 | **그렇다** (평면 거울 + 파도 법선 왜곡) | **아니다.** 오브젝트조차 아닌, 셰이더가 그리는 얼룩 |
| 밝기의 출처 | ⭐ 부표 본체와 **같은 재질·같은 emissive** | 부표 **색만** 안다. 세기는 자기 손잡이로 따로 |

#### 왜 둘이었나 — 역사적 사고

- **v0.9~0.10** (`4bd140d`) — 해석적이 **먼저** 생겼다. 평면 패스가 없던 시절의 유일한 방법
- **v0.15.0** (`b396f1c`) — 배를 위해 평면 패스를 만들며 `reflect.add(marks.group)` 으로 부표도 넣었다
- **해석적을 안 껐다** → 한 현상에 손잡이 **7개**
  (`markGlow` + `markReflect`·`Spread`·`Fall`·`Glow`·`Core`·`Anchor`)

⚠ §16-2 에서 만든 `markReflAnchor` 도 **두 경로를 억지로 맞추려던 것**이다. 경로가 하나면 필요 없다.

#### 실측 — 평면 패스만으로 완전하다

부표를 **3개로 줄여** 확인했다 (32개는 서로 겹쳐서 판정이 안 된다 — 처음에 그래서 오판했다) :

| | 결과 |
|---|---|
| 평면 패스만 (`markReflect` 0) | 부표 3개가 **각각 제 색의 반사를 바로 아래 맺는다.** 배 반사도 정상 |
| 평면 패스 끔 (`boatReflect` 0) | **반사가 전부 사라진다** |

→ ⭐ **`markGlow` 하나만 움직이면 본체와 반사가 같이 간다.** 평면 패스가 본체를 그대로 찍기
때문이고, 사용자가 요구한 *"빛나는 값이 거의 동일"* 이 구조적으로 보장된다.

⚠ **코드는 남겼다.** 셰이더 루프가 `if (uMarkRefl > 0.0)` 로 감싸져 있어 **비용이 0** 이고,
0.45 를 다시 넣으면 그대로 되살아난다 (`bloom.js` 와 같은 패턴). `markRefl*` 다섯은
`markReflect` 가 0 인 동안 **전부 무효**이며 `tweaks` 묶음 부제에 그렇게 적어 뒀다.

⚠ 잃은 것 하나 : `markReflFall` 의 *"부표 바로 밑은 진하게, 멀어질수록 연하게"*
(2026-09-03 사용자 지시). 평면 패스에는 부표별 감쇠가 없다 — 필요해지면 그때 평면 쪽에 넣는다.

⚠ 헤맨 자국 : `reflectAim`(*"반사 광선이 배를 향하는가"*)이 부표를 탈락시키는 줄 알았는데
**이미 0(해제)** 이었고, 그 이유가 `params.js` 주석에 그대로 적혀 있었다 —
*"배 전용 게이트였다. 평면 패스에서 올바른 게이트는 렌더타깃의 알파다."*
**값을 의심하기 전에 그 값의 주석을 먼저 읽는다.**

### 16-7. ⚠⚠ 반사 렌더타깃이 8비트였다 — 밝기가 전달되지 않았다 <span>— 2026-09-09</span>

> 사용자 : *"markGlow 올렸을 땐 왜 빛이 뿌옇게 밝게 빛나는 표현이 반사값에는 같이 적용이안됨?"*

§16-6 에서 *"평면 패스는 본체와 같은 emissive 를 찍으므로 `markGlow` 하나면 둘이 같이 간다"*
고 적었는데 **불완전했다.** 색과 형태는 같이 가지만 **1.0 을 넘는 밝기는 안 갔다.**

#### 원인 — 두 경로의 정밀도가 달랐다

| | 경로 | 1.0 초과 |
|---|---|---|
| 부표 **본체** | 씬 → **HalfFloat** 컴포저(`bloom.js`) → 블룸 | **보존.** 휘도 1.95 가 문턱 1.40 을 넘어 번진다 |
| 부표 **반사** | 씬 → **8비트 RT**(`reflect.js`) → water 가 읽어 섞음 | ❌ **1.0 에서 잘린다** |

`reflect.js` 의 렌더타깃이 `format: RGBAFormat` 만 주고 **`type` 을 안 줘서** 기본
`UnsignedByteType`(8비트)였다.

#### 실측 — 타깃 픽셀을 직접 읽었다

| `markGlow` | 8비트 (최대/포화px) | **HalfFloat** (최대/평균) |
|---:|---|---|
| 1.0 | 255 / 22,130 | 1.46 / 0.962 |
| 1.5 | 255 / 23,318 | 1.76 / 1.152 |
| 3.0 | 255 / 24,994 | 2.65 / 1.719 |
| **6.0** | **255 / 24,994** ← 같다 | **4.44** / 2.855 |
| **12.0** | **255 / 24,994** ← 같다 | **8.02** / 5.127 |

**8비트에서는 3.0 이상을 12배로 올려도 한 톨도 안 변했다.** 값이 전달 자체가 안 된 것이다.

#### 고침 — `type: THREE.HalfFloatType` 한 줄

화면 확인 : `markGlow` 4.0 에서 **부표와 반사가 함께** 뿌옇게 번진다.
⚠ 반사는 `boat.stepped`(8fps) 게이트를 타므로 **한 프레임 늦게** 반영된다 — 값을 바꾸고 바로
찍은 스크린샷은 아직 이전 상태다 (실제로 그렇게 한 번 오판했다).

⚠ **대가** : 타깃 메모리 2배(1440×784 기준 4.5MB → 9MB), 대역폭 2배.
⚠ 창이 가려진 환경에서는 GPU 시간을 못 믿으므로(`CLAUDE.md`) **보이는 창에서 HUD 로 확인해야 한다.**

⚠ `submerged.js`(잠긴 선체)도 **같은 8비트**다. 거긴 발광체가 아니라 지금은 문제가 안 되지만,
물에 비치는 밝은 것을 그쪽에 넣게 되면 같은 증상이 난다.

### 16-8. 부표가 "햇빛 쪽만" 빛나던 이유 — IBL <span>— 2026-09-09</span>

> 사용자 : *"markGlow 가 부표 전체가 빛나는게 아니었음? 왜 햇빛 방향에서만 빛이 나는건지"*

#### `emissive` 는 실제로 균일하다 — 증명

부표 하나를 크게 놓고 **조명과 환경맵을 껐더니 완전히 평평한 흰 원**이 됐다.
`emissive` 는 면 방향과 무관하게 전면 균일한 것이 맞다.

방향성은 그 위에 **더해지는** 항들이 만든다. `MeshStandardMaterial` 이므로 :

```
최종색 = emissive(균일) + 확산광(조명 방향) + 스페큘러 + IBL(하늘 방향)
```

⚠⚠ **`markGlow` 를 올려도 방향성이 안 사라진다** — 덮는 게 아니라 더하는 것이라 균일한 offset 만
얹힌다. 게다가 **블룸이 문턱(1.40) 기반**이라 밝은 쪽이 먼저 넘어 그쪽만 뿌옇게 번진다.
그래서 *"햇빛 방향에서만 빛난다"* 로 보인다.

⚠ 곁들여 : `emissiveIntensity` 는 `markGlow × 거리페이드` 다. 실측에서 `markGlow` 1.5 일 때
실제 값이 **0.369**(페이드 0.246)였다 — **먼 부표는 발광 자체가 크게 깎인다.**

#### ⚠ 완전히 균일하게 만들면 구가 아니라 스티커가 된다

조명을 끈 그 흰 원은 **음영이 없어 입체감도 없었다.** 방향성이 부표를 구로 보이게 하는 것이다.
그래서 `MeshBasicMaterial` 로 바꾸거나 `markGlow` 를 지배시키는 길은 택하지 않았다.

#### 적용 — `markEnv` (부표 전용 환경 반사 세기)

**하늘에서 오는 방향성(IBL)만 걷어내고 확산광 음영은 남긴다.**

⚠ `applyEnv()` 가 씬을 통째로 훑어 `envMapIntensity = P.envIntensity` 를 뿌리고 있었다 —
배와 부표가 **같은 값**을 썼다. 부표 재질을 `Set` 으로 모아 따로 가른다 :

| | 값 |
|---|---|
| 부표 | **`markEnv` = 0** (새 파라미터) |
| 배 | `envIntensity` = 0.35 (그대로) |

실측 확인 : 부표 재질 `envMapIntensity` **0** · 배 재질 **0.35** — 갈렸다.

⚠ IBL 을 빼면 부표가 그만큼 어두워진다(`envIntensity` 주석의 실측 : IBL 이 배·부표를
평균 **+51.4레벨** 밝혔다). 발광을 되살리고 싶으면 `markGlow` 를 올릴 여지가 생긴 것이고,
비교 패널의 `발광 3.0` 시안이 그 자리다.

⚠ `markEnv` 0.35 로 되돌리면 예전 동작이다. 비교 패널 **부표 빛** 묶음의 [원본]에 포함시켰다.

### 16-9. 발광 확정 — `markGlow` **2.0** <span>— 2026-09-09, 사용자 결정</span>

⚠⚠ **"2.0 은 아직 날아간다" 는 판정은 그때 조건의 것이었다.** 그 뒤로 둘이 바뀌었다 :

| | 전 | 후 | 효과 |
|---|---|---|---|
| 반사 타깃 | 8비트 | **HalfFloat** (§16-7) | 1.0 초과 밝기가 반사에도 전달된다 |
| 부표 IBL | 0.35 | **0** (`markEnv`, §16-8) | 부표가 그만큼 어두워졌다 |

그래서 지금 `markGlow` 2.0 은 **날아가지 않는다.** 부표가 제 색으로 은은히 빛나고
물의 반사도 같이 간다.

**실측 (반사 타깃 픽셀, 문턱 1.40)** :

| | p50 | p95 | 문턱 초과 |
|---|---:|---:|---:|
| **glow 2.0 · IBL 0 (지금)** | 1.25 | 1.79 | **43.2%** |
| glow 2.0 · IBL 0.35 (예전 조건) | 1.40 | 1.98 | 50.1% |

반사 픽셀의 **43%** 가 블룸 문턱을 넘는다 — 본체뿐 아니라 **반사도 뿌옇게 빛난다.**

#### ⚠ 측정에서 또 미끄러진 것 — `apply()` 는 발광을 설정하지 않는다

`markGlow` 를 바꾸고 `PB.apply()` 를 불러도 **재질의 `emissiveIntensity` 는 안 바뀐다.**
그 대입은 `marks.js` 의 **`update()`** 안에 있다 (`P.markGlow × m.fade`).
게다가 `PB.reflect.update()` 를 직접 부르면 `marks.update()` 가 안 돌아 옛 값 그대로 찍힌다.

→ 그래서 glow 를 바꿔 가며 잰 세 줄이 **전부 같은 값**으로 나왔다 (p50 1.25 · p95 1.79 동일).
**값이 너무 같으면 셰이더가 아니라 측정 창을 먼저 의심한다** (`docs/다음-세션.md` §3-③).
발광을 재려면 `emissiveIntensity` 를 직접 설정하거나 렌더 루프를 한 바퀴 돌려야 한다.

### 16-10. 발광 최종 — `markGlow` **2.1** <span>— 2026-09-09</span>

> 사용자 : *"빛이 밝아서 뿌옇게 되었으면 좋겠음 솔직히 형태가 거의 안보이게 빛나는걸 원함"*

**향조 색이 중심에서 흰색으로 포화**되어 계열이 번짐의 색으로만 남는다. 사용자가 **2.1** 로 되돌렸다.

(`zones.js` 가 *"향조는 장소가 아니라 부표의 색"* 이라고 못박은 것이 여기서 약해진다 —
계열 구분이 필요해지면 이 값을 다시 본다).

### 16-11. ⚠⚠⚠ `uBoatDir` 이 180° 뒤집혀 있었다 <span>— 2026-09-09</span>

> 사용자 : *"이동할때 길어지고 짧아지는 배에 적용되는 파도 거품이 배 선두에 생기고 있는것임.

> 서로 상쇄**했기 때문이다. 뱃머리를 바로잡으면(GLB_YAW) 이쪽도 같이 뒤집어야 한다."*

```js
// water.js  — 고치기 전
uni.uBoatDir.value.set(-Math.sin(rot.y), -Math.cos(rot.y));   // 로컬 −z 를 뱃머리로 봤다
// 고친 뒤
uni.uBoatDir.value.set( Math.sin(rot.y),  Math.cos(rot.y));   // 로컬 +z 가 뱃머리다
```

#### ⚠⚠ 뱃머리를 재다가 한 번 오판했다 — **y 대역을 갈라야 한다**

처음에 pivot 로컬에서 z 별 선체 폭을 쟀더니 `z −2.5 : 0.15` 로 −z 가 가장 좁았고,
그걸 뱃머리로 결론냈다. **틀렸다 — 그건 러더였다.** y 대역을 나눠 다시 재니 :

| y 대역 | z −2 | −1 | 0 | +1 | +2 | **+3** |
|---|---:|---:|---:|---:|---:|---:|
| **갑판** (0.9~1.4) | 0.67 | 1.13 | 1.40 | 1.43 | 1.33 | **0.08** |
| 선체 몸통 (0.2~0.9) | 0.76 | 1.23 | 1.63 | 1.61 | 1.36 | 1.02 |
| 용골 아래 (<0.2) | **0.24** | 0.74 | 0.78 | 0.86 | 0.74 | — |

**갑판이 한 점으로 모이는 +z 가 뱃머리다.** 용골 대역만 보면 −z 가 좁아 **정반대 결론**이 난다.
`docs/다음-세션.md` §3-③ *"지표가 틀리면 결론이 틀린다"* 가 또 나왔다.

#### 검증

`debugView 13` + 항공뷰 (`uBoatDir` = (0,1) → 화면 아래가 뱃머리) :
거품이 **아래(뱃머리)는 좁고 위(선미)로 넓게** 퍼진다 — 물방울이 제 방향으로 섰다.
⚠ `hullTaper` 를 0 으로 두면 꼬리가 통째로 사라진다 (그 항이 만드는 것이 맞다는 확인).

⚠ **다른 두 소비자는 영향이 없다.** `uBoatDir` 은 그림자(670행)·접촉 그림자(696행)에서
**대칭 타원의 축**으로만 쓰여(`dot(rel,F)/sizeX`) 부호가 바뀌어도 그림이 안 변한다.
앞뒤 비대칭을 쓰는 곳은 선체 거품의 `hullTaper` 하나다.

## 17. 배의 입체감 — 그림자 맵 <span>— 2026-09-09</span>

> 사용자 : *"배가 너무 흰색이라 입체감이 좀 떨어지는데 (…) 돛 기둥의 그림자 난간의 그림자
> 내부 조타 공간의 음영 이런 표현이 더 디테일하게 보여야 (…) 그림자 처리, 또는 종이 질감을
> 표현 해야할까?"*

### 17-1. 진단 — 형태 음영이 **0** 이었다

| | 실측 |
|---|---|
| 그림자 맵 | `renderer.shadowMap.enabled` **false**. `boat.js:416` 이 `castShadow = false` 로 껐다 |
| 텍스처 | 재질 **26개 전부** `map`·`normalMap`·`aoMap`·`roughnessMap` **없음** |
| 색 | 대부분 `#ffffff`. 흰 물·흰 하늘 위의 흰 배라 대비가 날 곳이 없다 |

⚠ **`boatNormal` 은 죽은 값이다.** `boat.js:355` 가 `m.normalScale` 을 설정하지만 노멀맵이 없다.

⚠⚠ **`aoMap` 은 GLB 가 들고 왔는데 버려지고 있다** — `boat.js:410` 주석 :
*"aoMap 은 uv2(three 0.160 의 uv1)가 없어 **어차피 안 먹는다.** 떼어 둔다."*
**UV2 를 넣으면 조타실 안쪽 음영이 공짜로 살아난다.** 사용자가 말한 세 가지 중 마지막이 그것이다.

### 17-2. "그림자냐 종이 질감이냐" — 둘은 **다른 기술**이고 그림자가 먼저다

| 사용자가 말한 것 | 필요한 기술 |
|---|---|
| 돛 기둥의 그림자 · 난간의 그림자 | **그림자 맵** (드리운 그림자) |
| **내부 조타 공간의 음영** | **AO** — 그림자 맵으로는 안 나온다 (구석의 차폐다) |
| 종이 질감 | 노멀/컬러 맵 — ⚠ **형태 음영이 선 뒤에** 의미가 있다 |

### 17-3. ⚠ 조명 대비만으로는 안 됐다 (A안 기각)

`hemi` 1.35 → 0.45 · 0.20, `dir` 2.2 → 3.4 · 4.0 을 시험했다. **개선이 미미했다** —
배 재질이 거의 `#ffffff` 라 세게 비추면 포화되고, 램버트 음영은 부드러워서 돛대·난간 같은
**가는 형태가 안 살아난다.** 조명은 원래대로 되돌렸다.

### 17-4. 적용 — `boatShadow`

```js
renderer.shadowMap.type = THREE.PCFSoftShadowMap;
dirLight.castShadow = true;  mapSize 1024²
그림자 카메라 : ±4.5 · near 0.5 · far 24     // 배 한 척(길이 5 월드)만 담는다
bias −0.0008 · normalBias 0.02               // 여드름 · 얇은 면의 자기 그림자
```

⚠ **물에는 안 드리운다.** 수면은 커스텀 셰이더라 three 의 그림자를 안 받고, 그쪽은 이미
`shadowAmount`·`contactAmount` 세 겹이 따로 있다 (불변식 0-3-2). 얻는 것은 **배 자기 위**의 그림자다.

⚠ 그림자 카메라를 넓게 잡지 않는다 — 1024² 를 허공에 흩어 쓰면 돛대 그림자가 계단이 된다.

⚠ 켜고 끄면 **재질을 다시 컴파일해야 한다** (`applyShadow` 가 값이 바뀔 때만 돈다).

### 17-5. ⚠ 비용은 아직 못 쟀다

`renderer.info` 는 **컴포저의 마지막 패스만** 센다 — 그림자 on/off 둘 다 `draw 1 / tri 1` 로
나와 못 쓴다. 배가 **279,810 삼각형**이고 그림자 패스가 그걸 깊이로 한 번 더 그린다.
**보이는 창의 HUD(GPU·rAF)로만 판정할 수 있다** (`CLAUDE.md` 의 그 규칙).

무거우면 손잡이는 셋이다 : `mapSize` 1024 → 512 · 캐스터를 돛대·난간·돛으로 제한 · `boatShadow` 0.

### 17-6. ⚠ 돛에 원형 얼룩이 생겼다 — 자기 그림자 <span>— 2026-09-09</span>

> 사용자 : *"GLB에서 veil 부분만 혹시 변경할 수 있나? 옆 부분 veil 네이밍 된 부분만 지금
> 점이 여러개 뜨고 있습니다"* (돛에 회색 원형 반점 4개)

**`Veil` 이 곧 돛천이다** — `visible = false` 로 하면 돛이 통째로 사라진다 (그렇게 확인했다).

원인은 §17-4 에서 켠 그림자다. 돛은 **얇은 양면(side 2) 천**이라 그림자를 받게 두면
**자기 자신에게** 얼룩이 진다 — `sailWind` 로 물결치는 굴곡이 자기 그림자를 만들어
원형 반점 몇 개로 나온다.

```js
// boat.js — 돛만 골라 리시버에서 뺀다
if (/veil/i.test(n.name || '')) n.receiveShadow = false;
```

⚠ **`castShadow` 는 살려 둔다** — 돛이 갑판에 드리우는 그림자는 이 층의 핵심이다.
얻는 것은 그대로 두고 부작용만 뗀 것이다.

⚠ `bias`/`normalBias` 로 밀어내는 길도 있지만 그러면 **갑판 그림자가 같이 뜬다**
(peter-panning). 얇은 천은 자기 그림자를 안 받는 쪽이 옳다.

⚠ 이름으로 고른다 (`/veil/i`). GLB 를 갈아끼우면 이 줄도 같이 본다 —
`boat.js` 는 이미 같은 방식으로 돛을 찾고 있다 (`/veil|sail|cloth/i`, 449행).

## 18. 종이 질감 (`paper.js`) <span>— 2026-09-09</span>

> 사용자 : *"mast, closed off 같은 철재 표현을 제외하고 나머지에 종이 질감표현을 넣고싶은데"*

### 18-1. 텍스처는 **파일이 아니라 함수다**

`sky.js` 와 같은 규율이다 — 이 리포에는 텍스처가 한 장도 없다(거품도 worley, 하늘도 함수).
512² **두 장**(노멀·러프니스)을 코드로 굽는다. **번들이 0바이트 늘어난다.**

⚠ **시드가 고정이다.** `Math.random()` 을 안 쓴다 — 새로고침마다 결이 달라지면 A/B 가 안 된다.

⚠ 두 장을 **같은 높이맵**에서 만든다. 따로 만들면 요철과 광택이 어긋나 젖은 돌처럼 보인다.
러프니스는 **높은 곳이 매끄럽다** (누른 자리가 반질해지는 종이의 성질).

종이의 결은 세 겹이다 — 하나만 쓰면 노이즈로 읽힌다 :
① 섬유(고주파) · ② 뭉침(중주파) · ③ 결(저주파 + **가로로 늘인 격자** = 약한 방향성)

### 18-2. 철재를 이름으로 가른다

```js
const PAPER_SKIP = /mast|closed[ _]?off|hinge|flange|helix|rope|wheel|glass|window|handle|edge/i;
```

GLB 재질 26개가 전부 이름을 갖고 있어 이름으로 가를 수 있었다. 실측 결과 :

| | |
|---|---|
| **종이** (11) | `Boat` · `Veil`(돛) · `Security` · `Pillow` · `Door` · `Entrance` · `Plank_Table` · `Support_Table` · `Support_Seat` · `Pot` · `Ground` |
| **제외** (12) | `Mast` · `Closed Off` · `Flange` · `Window` · `Handle` · `Rope` · `Glass` · `Hinge` · `Wheel` · `Helix` · `Edge` · `Support_Wheel` |

⚠ **여기 없는 이름은 전부 종이로 간주한다.** GLB 를 갈아끼우면 이 목록을 같이 본다.

⚠ 텍스처를 **모든 재질이 공유**한다 (VRAM 두 장). 그래서 반복(`paperScale`)은 전역이고
재질별로 못 준다 — 한 장의 종이로 접은 배라 한 결이어야 맞지만, GLB 의 UV 스케일이
자리마다 달라 결 크기가 조금씩 다르다.

### 18-3. ⭐ `boatNormal` 이 살아났다

§17-1 에서 **죽은 값**으로 확인했던 그것이다 (노멀맵이 없어 `normalScale` 이 무의미했다).
이제 그 값이 종이 결의 세기를 쥔다.

**실측으로 잡은 값** :

| | 결과 |
|---|---|
| `boatNormal` 1.0 · `paperScale` 24 | 거의 **안 보인다** |
| 3.0 · 8 | 종이가 아니라 **사포**로 읽힌다 |
| 1.8 · 40 | 너무 고와 사라진다 |
| **1.8 · 14** | ⭐ 확정. 돛에 결이 은은히 서고 선체는 매끈하게 남는다 |

⚠ **노멀맵은 직사광에서 드러난다.** 지금 `hemi` 가 1.35 로 세서 그늘이 채워지는 만큼
결이 묻힌다 — §17-3 에서 조명 대비를 기각했지만, 종이 결을 더 세우고 싶으면 그쪽을 다시 본다.

⚠ 되돌리는 값은 `paperAmount` 0 하나다. 비교 패널 **종이결** 묶음에 시안 둘(`굵게`·`곱게`)과 함께 있다.

### 18-4. 결을 키우고 **선실에 단계적 종이색**을 깔았다 <span>— 2026-09-09</span>

> 요소마다 전부 같은 짙은 종이색이 아니라 단계적 종이색을 구성해봐"*

**결** : `paperScale` 14 → **7**.

**색** : `boat.js` 에 `PAPER_SHADE` 표를 뒀다. 값은 짙은 종이(`#A79E8D`) 쪽으로 얼마나 갔는가다.

|---|---:|---|

| `Ground` (선실 바닥) | 0.46 | `#dcd9d5` |

⚠ `Handle`·`Wheel`·`Support_Wheel` 을 철재 목록(`PAPER_SKIP`)에서 뺐다 — 처음에 내가 임의로

⚠ 되돌리는 값은 둘이다 : `paperAmount` 0(결) · `paperShade` 0(색 단계). 비교 패널의
**종이 → [원본]** 이 둘을 같이 되돌린다.

### 18-5. `Mast` · `Closed Off` — 질감은 빼고 **색만** 진하게 <span>— 2026-09-09</span>

> 사용자 : *"mast 랑 closed off 는 종이질감이 아니라 색상을 더 진하게 만들어야하는데"*

⭐ **색과 질감이 서로 독립이라 표에만 넣으면 됐다.** 질감은 `PAPER_SKIP`(정규식)이 쥐고
색은 `PAPER_SHADE`(표)가 쥔다 — 둘은 서로를 참조하지 않는다.

| 재질 | 단계 | 색 | 종이 결 |
|---|---:|---|---|
| `Mast` (돛대) | **0.58** | `#d2cec8` | **없음** |
| `Closed Off` (선실 외벽) | **0.44** | `#dedbd7` | **없음** |

- **돛대를 가장 진하게** 잡았다 (0.58) — 흰 하늘을 등지고 서므로 진해야 형태가 읽힌다.
  실제로 켜면 회색 기둥으로 또렷해진다.
- **외벽은 덜 진하게** (0.44) — 면이 넓어서(69k 삼각형) 너무 짙으면 배가 무거워진다.

⚠ 철재라도 **같은 종이색 선**(`PAPER_DEEP`)을 쓴다. 여기에 차가운 회색을 섞으면 배 안에서
이 둘만 다른 재질로 튀고, *한 장의 종이로 접은 배*라는 전제가 깨진다.

⚠ 더 진하게/옅게는 `boat.js` 의 `PAPER_SHADE` 표에서 **숫자 하나**만 고치면 된다.

### 18-6. 결을 재질마다 흩고, 순백을 없앴다 <span>— 2026-09-09</span>

> 사용자 : *"재질표현이 너무 많은 곳에 일정한 비율로 되고 있는데 (…) 다양한 표현을 시킬수
> 있을지 (…) boat 부분도 약간의 무채색을 약간만 짙게해서 너무 흰색을 통한 모델링 화이트홀
> 같은 현상이 있는데"*

#### ⭐ 결을 재질마다 다르게 — **VRAM 은 그대로**

`Texture.clone()` 은 `source`(GPU 에 올라간 이미지)를 **공유**하고 `repeat`·`rotation`·`offset`
만 독립으로 갖는다. 재질 12개가 각자 clone 을 들어도 **텍스처는 두 장**이다.

실측 : 종이 도입 전 `renderer.info.memory.textures` **19** → 도입 후 **21** (+2, clone 12개는 0).

흩는 값은 **재질 이름 해시**다 (`Math.random()` 이 아니다 — 새로고침해도 같은 결이어야
A/B 가 된다). 배율 0.55~1.8배 · 방향 0~180° · 이음매 위치.

| 재질 | repeat | 회전 |
|---|---|---:|
| `Boat` | 10.9 × 11.9 | 25° |
| `Door` | 7.0 × 5.1 | 70° |
| `Pillow` | 8.7 × 11.3 | 170° |
| `Security` | 5.9 × 5.2 | 68° |

⚠ clone 은 **한 번만** 만든다. `paperScale` 을 드래그할 때마다 새로 만들면 그게 누수다 —
배율(`kx`,`ky`)을 같이 돌려받아 `repeat` 만 갱신한다 (`paperRescale`).

⚠ 노멀과 러프니스에 **같은 변환**을 준다. 어긋나면 요철과 광택이 따로 놀아 '젖은 돌' 이 된다.

#### 화이트홀 — 순백을 하나도 남기지 않는다

`#ffffff` 는 조명이 어느 각도로 와도 255 에서 포화돼 **면끼리 구분이 안 선다.**
몇 레벨만 내려도 램버트 음영이 살아난다.

| | 값 | 결과 |
|---|---:|---|
| `Boat` (선체) | 0.10 | `#f8f7f7` |
| `Veil` (돛) | 0.05 | `#fcfbfb` |
| **표에 없는 전부** (`PAPER_BASE`) | **0.06** | `#fbfbfa` |

⚠ 화이트홀은 선체만의 문제가 아니라 **흰 부속 전부**의 문제였다. 그래서 표에 없는 재질에도
바닥값을 깔았다 — 눈에 안 띄되 포화는 면하는 자리다.

⚠ 크게 내리지 않는다. 이 바다의 축은 여전히 *'흰 종이 위 흰 물'* 이다 (불변식 14).
**실측 : 이제 `#ffffff` 인 재질이 하나도 없다.**

⚠ 되돌리는 값이 셋이 됐다 : `paperAmount`(결) · `paperShade`(색 단계) · `paperVary`(결 흩기).

### 18-7. 금속 — 종이의 **여집합** <span>— 2026-09-09</span>

> 사용자 : *"종이 재질을 넣지 말라고한 모델 파트에 metalric ? 맞나 메탈 표현을 넣고 싶은데"*

용어는 `metalness` 다. 대상은 **`PAPER_SKIP` 에 걸린 재질** — 종이의 여집합이라 목록을
두 번 적지 않는다 (한쪽만 고치면 반드시 갈라진다).

```js
const 금속 = PAPER_SKIP.test(m.name || '');
const k = 금속 ? P.metalAmount : 0;
m.metalness = P.boatMetal + (P.metalMetalness - P.boatMetal) * k;   // 0.15 → 0.80
m.roughness = P.boatRough + (P.metalRough    - P.boatRough)    * k;   // 0.75 → 0.32
```

| | 재질 |
|---|---|
| **금속** (9) | `Mast` · `Closed Off` · `Edge` · `Flange` · `Glass` · `Helix` · `Hinge` · `Rope` · `Window` |
| 종이 (14) | 나머지 전부 |

#### ⚠ 걱정했던 것과 실제

**금속은 환경 반사로만 보인다.** `metalness` 를 올리면 확산광이 그만큼 죽고 IBL 만 남는데,
이 하늘은 종이 톤(232~250, 폭 18레벨)이라 비칠 것이 거의 없다 — **금속이 빛나는 게 아니라
어두워질 수 있다**고 봤다.

**실제로는 그게 오히려 도움이 됐다.** 흰 배에서 금속 부속이 어두워지니 **형태가 더 잘 읽힌다** —
돛대가 회색 기둥으로 서고 난간·경첩이 선으로 살아난다. §17 의 '화이트홀' 과 같은 처방이
다른 경로로 온 셈이다.

⚠ **`Rope`(밧줄)와 `Glass`(유리)도 금속이 됐다.** 둘 다 금속이 아니지만 `PAPER_SKIP` 에
있어서 딸려 왔다 — 종이도 금속도 아닌 세 번째 갈래가 필요해지면 그때 나눈다.
지금은 흰 배에서 어둡게 서는 것이 둘 다 이득이라 그대로 둔다.

⚠ 되돌리는 값은 `metalAmount` 0 하나다 (전부 `boatMetal`/`boatRough` 로 돌아간다).

## 19. [2단계] 원경 페이드 — ⚠⚠ **이 페이드는 거의 일하지 않고 있었다** <span>— 2026-09-09</span>

§8 의 [2단계]다. 결론부터 : **`surface.fade0/fade1`(20/40)은 화면에 거의 영향을 못 준다.**
물을 실제로 지우는 것은 §14-5 가 찾은 **UV 가장자리 페이드**이고, 그건 경계가 정사각형이다.

### 19-1. 기하 — 카메라가 메시 중심에서 35.8 벗어나 있다

실측 (캔버스 1280×720, `camPitch` 15.4 · `camDist` 3.96) :

```
물 메시   PlaneGeometry(110, 110), 원점 고정 (반경 55)     ← 카메라를 따라다니지 않는다
카메라    (−28.66, 10.30, 21.41)  ·  원점에서 XZ 35.77
전방      (0.789, −0.614)  — 거의 정확히 원점을 향한다 (내적 35.76 ≈ 거리 35.77)
```

⚠ **배가 제자리에 있고 물이 흐르는 구조**라 (`nav` 에 위치가 없고 `scroll` 만 있다)
카메라도 메시도 고정이다. 그래서 물끝은 화면에 **못 박혀** 있다.

카메라 전방으로 나아갈 때 :

| | 거리 | 무엇 |
|---|---:|---|
| UV 페이드 시작 (`max(d.x,d.y)` = 0.76) | **89.3** | 물이 녹기 시작 |
| UV 페이드 완료 (0.98) | **104.6** | 배경색 |
| 메시 경계 (x = 55 에 먼저 닿는다) | 106.0 | |
| 거리 페이드 `uFade0` = 20 × 3.96 | 79.2 | |
| 거리 페이드 `uFade1` = 40 × 3.96 | 158.4 | ⚠ **메시 밖이다** |

`smoothstep(79.2, 158.4, 104.6)` = **0.242**. 거리 페이드는 24% 만 진행된 채 끝난다.
§12-8 의 계산이 맞았다.

### 19-2. ⚠⚠ 그 결과 물끝이 **하드 엣지**다 — 실측

화면 중앙(x 640) 세로 프로파일 (R 채널, 배경 246) :

```
20/40 (지금)  … 246 246 246 246 | 238 232 229 226 222 219 216 212 207 186 …
                  ↑ 여기까지 완전한 배경    ↑ 한 픽셀에 22레벨 급락
11/22         … 243 242 241 238 237 236 235 234 233 232 231 230 229 226 …
                  ↑ 계단이 없다. 22px 에 걸쳐 19레벨
```

⚠ `README.md` 의 *"물은 배경색으로 흩어져 사라진다"* 는 **지금 화면에서 일어나지 않는다.**
문턱을 6·12·18·30·60 으로 바꿔도 물끝 y 가 2~4px 밖에 안 움직인다 — 경계가 그만큼 날카롭다.

### 19-3. ⭐ 스윕 — 거리 페이드(**원형**)가 UV 페이드(**정사각형**)를 이기게 한다

`length(vW.xz - uCam)` 은 원형이고 `max(d.x, d.y)` 는 정사각형이다. 거리 페이드를 앞당기면
경계 모양이 원형 쪽으로 넘어간다. **파도 4상태 평균** (1280×720 · 수평선 y 108 · 밴드 11) :

| CONFIG | 월드 | 물끝 y | 원경 띠 | **아치** | 좌÷중 |
|---:|---:|---:|---:|---:|---:|
| **20/40** (지금) | 79/158 | 200 | 92 | **37.5** | 1.414 |
| 14/28 | 55/111 | 208 | 100 | 28.8 | 1.285 |
| 12/24 | 48/95 | 224 | 116 | 17.8 | 1.154 |
| **11/22** | 44/87 | 234 | 126 | **12.5** | 1.099 |
| **10/20** | 40/79 | 247 | 139 | **12.5** | 1.090 |
| 7/14 | 28/55 | — | ~195 | 18.5 | 1.095 |
| 5/9 | 20/36 | — | ~290 | 29.5 | 1.102 |

### 19-4. ⭐⭐ 아치는 0 이 안 된다 — **아치 = 원경띠 × (좌÷중 − 1)**

화면 좌우 끝은 중앙보다 늘 더 내려간다 (16:9 원근). 그 비가 **좌÷중**이다.

- 정사각형 경계에서 **1.41**
- 원형에 가까워지면 **1.09 로 수렴하고 그 아래로 안 간다** (7/14·5/9 에서도 1.09)

그래서 페이드를 내리면 비는 떨어지지만 **원경 띠가 넓어져** 곱이 다시 커진다.
그 둘이 만나는 바닥이 **11/22 ~ 10/20 의 12.5px** 다.

검산 (네 설정 모두 오차 1px 안) :

```
20/40 :  92 × 0.414 = 38.1   (실측 37.5)
14/28 : 100 × 0.285 = 28.5   (실측 28.8)
12/24 : 116 × 0.154 = 17.9   (실측 17.8)
10/20 : 139 × 0.090 = 12.5   (실측 12.5)
```

⚠ 처음에 `1/cos(35°)` = **1.221** 이 하한일 거라 예측했는데 **틀렸다.** 실측은 1.09 다.
그 유도는 카메라가 수평일 때의 것이고, 지금은 `camPitch` 15.4° 로 기울어 있다.
⚠ **§14-5 의 *"[3단계] 안개의 할 일은 네모난 경계를 원형으로 바꾸는 것"* 은 절반만 맞다.**
원형으로 바꾸면 아치가 37.5 → 12.5 로 줄지만 **없어지지는 않는다.** 나머지는 안개가 덮어야 한다.

부표가 훨씬 먼저 사라진다. 물을 당겨도 이 순서는 유지되지만, **CONFIG 값 9.6 아래로 내리면

### 19-6. 넣은 것 — 런타임 값 + 비교 패널

물끝을 내리는 것은 화면 구성이라 **아트 디렉션 결정**이다 (§10-3 과 같은 갈래).
그래서 먼저 값을 고르지 않고 **고를 수 있게만** 만들었다.

- `water.js` — `P.waterFade0/1` 을 읽고 없으면 `CONFIG.surface` 로 떨어진다.
  ⚠ 슬라이더 둘이 독립이라 뒤집힐 수 있어 `max(wf1, wf0 + 0.5)` 로 최소 폭을 강제한다
  (`smoothstep` 은 `edge0 >= edge1` 이면 하드 컷이 된다)
- `tweaks.js` — 묶음 '수면 · 원경 페이드'
- `compare.js` — **`BASELINES` 에 '원경 페이드' 한 줄** + 시안 넷 (12/24 · 11/22 · 10/20 · 9/18)

⚠ 비교 패널이 한 줄 늘어 펼쳤을 때 **364px** 이 됐다 (§15 가 경고한 겹침). 뷰포트 1282 에서는
넘치지 않지만, 세로가 짧은 화면에서는 다시 볼 것.

### 19-7. ⚠⚠⚠ 재면서 밟은 것 셋 — 전부 **측정 창**이 거짓말을 했다

교훈 ③ *"값이 너무 같으면 셰이더가 아니라 측정 창을 먼저 의심한다"* 가 오늘 두 번 재현됐다.

1. **렌더타깃이 선형이었다.** `new THREE.WebGLRenderTarget()` 의 기본 `colorSpace` 는
   `NoColorSpace` 라, `#f6f5f2` 인 배경이 **235,233,226** 으로 읽혔다. 화면(sRGB) 경로와
   갈라진 것이다. `rt.texture.colorSpace = THREE.SRGBColorSpace` 로 고치니 정확히
   246,245,242 가 나왔다. §14-3 이 경고한 색공간 함정의 다른 얼굴이다.
2. **⚠⚠ Browser pane 이 숨겨져 rAF 가 아예 안 돌았다** (`rafCount` 0 / 805ms).
   그래서 `CONFIG` 를 바꿔도 `water.update()` 가 안 돌아 유니폼이 그대로였고,
   **스윕 여덟 값이 소수점까지 같게** 나왔다. 핸드오프 §2 의 *"유니폼만 바꾸고 다시 그린다"*
   로 우회했다 — 오히려 파도가 안 흘러 A/B 가 깨끗해졌다.
3. **화면 캔버스 스크린샷도 못 쓴다.** rAF 가 멈춰 있으면 `bloom.render()` 를 직접 불러도
   present 가 안 돼서, 20/40 과 10/20 의 스크린샷이 **똑같이 나왔다** (실제로는 물끝이 47px 차이).
   ⭐ 그래서 시안은 스크린샷으로 설득하지 않고 **비교 패널에 넣어 사용자가 직접 A/B 하게** 했다.
4. **배가 화면 중앙을 가린다.** x 640 세로 프로파일에서 y 210~260 의 어두운 띠를 물끝으로
   볼 뻔했는데 그건 배였다. 밴드를 쓸 때 `boat.pivot`·`marks.group`·`stage.mesh` 를 숨긴다.

## 20. [3단계] 원경 안개 — ⚠⚠ **물 메시가 하늘 위에 판으로 떠 있었다** <span>— 2026-09-10</span>

> ⚠⚠ **이 절의 산(20-3 ~ 20-5)은 같은 날 기각됐다. §21 을 먼저 읽는다.**
> 안개(20-1 · 20-2)는 유효하고 코드에 남아 있다.

§8 의 [3단계]. **여기까지가 평상시 화면**이다 (레퍼런스 3번 사진). 두 부분이고, 순서가 중요하다 —
안개를 먼저 고치지 않으면 산이 잘린다.

### 20-1. 진단 — 산보다 먼저 고쳐야 할 것이 있었다

물 메시는 **불투명**하다 (`gl_FragColor` 의 알파가 1.0). `vis` 가 0 이어도 무언가를 칠하는데,
그게 `uBg`(246,245,242) 하나였다. 그런데 하늘은 태양 로브 때문에 같은 자리에서 **249~250** 이다.

**즉 물 메시가 하늘 위에 3~4레벨 어두운 판으로 떠 있었다.** 실측 (12/24 · 1280×720) :

```
물 메시의 기하학적 경계 (밴드 11)   245 236 227 214 201 202 210 221 224 239 244
                                     → 아치 44px · 최고 y201
x300 에서 vis≈0 인 채 uBg 만 칠하던 띠   y225 ~ y282 = 57px
```

⭐ 화면 구조 (수평선 y108 · 물이 보이는 선 y224) :

```

       순수 하늘 93px
 201 ∿∿∿∿∿∿∿∿∿∿∿∿∿  ⚠ 물 메시 경계 — 정사각형이라 좌우로 44px 출렁인다
       uBg 만 칠하는 띠 57px

```

⚠⚠ **산을 하늘에 그리면 y201 아래가 그 들쭉날쭉한 선에서 잘린다.** 지금은 3레벨이라 안 보이지만
하늘에 무엇이든 얹는 순간 드러난다. §14-5 가 말한 *"안개의 진짜 할 일"* 의 실제 형태가 이것이다.

### 20-2. 안개 — 물이 사라진 자리는 **그 방향의 하늘색**이다

`water.js` 의 마지막 줄 한 곳이다.

```glsl
vec3 far = mix(uBg, skyWithLand(normalize(vW - cameraPosition), uLightDir3), uFadeSky);
gl_FragColor = vec4(mix(far, c, vis), 1.0);
```

⭐ **스카이 스피어와 같은 함수·같은 방향**이라 구조적으로 이어진다 — `stage.js` 의 `vDir` 도
카메라→픽셀이고 여기 시선도 카메라→그 점이다. 갈라질 방법이 없다.
⚠ `uFadeSky` 는 `stageAmount` 를 곱해서 들어간다. 하늘을 끄면 자동으로 `uBg` 로 돌아온다.

**검증 — 페이드를 극단(0.5/1)으로 당겨 물을 완전히 지우고 그 자리를 하늘과 픽셀로 비교했다 :**

| | 평균 채널합 차이 | 최대 |
|---|---:|---:|
| `waterFadeSky` **0** (예전) | 6.28 | **23** (물 246,245,242 vs 하늘 254,253,249) |
| `waterFadeSky` **1** (지금) | **0** | **0** |

**비트 단위로 일치한다.** 하늘 위의 판이 사라졌고, 그 정사각형 경계 44px 도 같이 사라졌다.

### 20-3. ❌ 산 — 절차적 능선 <span>(기각됨 · §21)</span>

사용자 결정 (2026-09-10). `sky.js` 에 `LAND` 표와 `skyWithLand()` 를 두고 **소비자 셋이 공유**한다 :
`stage.js`(화면) · 물의 원경 안개 · 물의 하늘 반사. 유니폼 `uLand` 가 `SKY_UNIFORMS` 를 통해
**같은 객체로 공유**되므로 (실측 확인 : `stage.uni.uLand === water.uniforms.uLand`) 갈라질 수 없다.

- 능선은 **방위각의 사인 합**이다. 주파수를 **정수**(3·7·13·23)로만 써서 −π 와 +π 가 구조적으로
  이어진다 — 소수를 쓰면 뒤쪽 어딘가에 세로 단층이 선다
- 겹 둘. 뒤(`#E4E7EC`)는 높고 옅고, 앞(`#D3D8E1`)은 낮고 짙다. 위상을 어긋내 겹쳐 보이게 한다
- **자산 0KB · 드로우콜 0 추가** (`paper.js` 가 종이 결을 코드로 굽는 것과 같은 패턴)

⚠ **환경맵(`skyColorCPU`)만 일부러 산을 모른다.** CPU 에 능선을 한 벌 더 구현하면 그게 조용히
갈라지는 자리가 된다. 배는 작아서 산이 비쳐 봐야 몇 픽셀이라, 잃는 것보다 갈라질 위험이 크다.

### 20-4. ❌ 밟은 것 — **산이 수평선 아래를 통째로 덮었다** <span>(기각됨 · §21)</span>

처음에 `smoothstep(h + sf, h - sf, d.y)` 만 썼다. 능선 **아래를 전부** 산으로 칠한 것이다.
그러면 `d.y < 0` 인 방향이 전부 산이 되고, **물이 사라진 자리(`far`)가 하늘색이 아니라 산 색**이 된다.

실측 : 화면 y150 을 물 없이 보니 **211,216,225** — 정확히 `LAND.near` 였다.

→ 밑동을 곱한다. `foot = smoothstep(-sf, sf, d.y)`.

**먼 산은 수평선 위로 솟고 밑동이 수평선에 잠긴다.** 수평선 **아래** 116px 은 산이 아니라
**안개에 묻힌 먼 바다**의 자리다 — §12-10 의 그림을 다시 읽으면 그렇게 되어 있다.
고친 뒤 같은 자리가 **250,248,245** (하늘색)로 돌아왔다.

### 20-6. ⚠⚠ 재는 창이 **또** 거짓말을 했다 — 이번엔 새 얼굴 둘

§19-7 에 이어 세 번째 세션 연속이다.

1. **⭐ `import('/src/sky.js')` 는 앱이 쓰는 것과 다른 모듈 인스턴스다** (실측 :
   `SKY.SKY_UNIFORMS.uLand === PB.stage.uni.uLand` → **false**). dynamic import 로 모듈 상태를
   바꾸면 앱은 그걸 못 본다. **§19 에서 `CONFIG` 를 못 바꿨던 것도 rAF 만의 문제가 아니었다** —
   두 원인이 겹쳐 있었고 우회법(유니폼 직접 밀기)이 우연히 둘 다 피했다.
   → **모듈 상태를 바꿔야 하면 `PB.apply()` 처럼 앱이 노출한 경로를 쓴다.**
2. **`syncSky()` 를 안 부르면 `params` 를 바꿔도 유니폼이 안 간다.** 측정 헬퍼가 `stage.update` 와
   `water.update` 만 불러서, `landAmount` 0/1 의 화면 차이가 **0** 으로 나왔다. 하마터면
   "산이 안 그려진다" 고 셰이더를 뒤질 뻔했다 — 실제로는 그려지고 있었다.
3. **GLSL 주석 안의 백틱이 빌드를 죽였다.** 이미 §9-5 와 §3-④ 에 두 번 적혀 있는데 또 밟았다.
   `node --check src/*.js` 가 즉시 잡는다.
4. **⚠ 콘솔은 리로드해도 옛 로그를 그대로 들고 있다.** 백틱을 고치고 리로드한 뒤 에러만 읽었더니
   `'uLand' : undeclared identifier` 가 그대로 나와서 **고친 것이 안 먹은 줄 알았다.**
   실제로는 컴파일 실패 0 · `gl.getError()` 0 이었고, 그 에러는 **고치기 전 로드의 잔상**이었다.
   → 리로드 뒤에는 **마지막 `[vite] connected` 이후**만 읽거나, 로그 대신
   `renderer.info.programs` 의 `diagnostics.runnable` 로 판정한다 (§3-④ 가 이미 그렇게 적었다).

## 21. ❌ 원경 산을 걷어냈다 — **사방이 산이면 바다가 아니다** <span>— 2026-09-10, 사용자 결정</span>

§20-3 에서 넣은 절차적 산을 **같은 날 통째로 걷어냈다.**
사용자 : *"산 만드는걸 취소하자 모양도 그렇고 **모든 방향에 산을 만들기는 이상한듯**"*.

### 21-1. 왜 틀렸나 — 방위각 전체에 능선을 깔았다

`skyWithLand()` 는 `atan(d.x, d.z)` 로 방위각을 얻어 **−π ~ π 전 구간**에 능선을 그렸다.
주파수를 정수로 써서 이음매가 안 생기게 한 것이 오히려 증거다 — **360도가 닫힌 고리**라는 뜻이다.

그 화면은 **사방이 산으로 둘러싸인 호수**다. 이 프로젝트의 바다는 외해이고,
배가 어느 쪽으로 돌아도 수평선이 열려 있어야 한다.

### 21-2. ⚠⚠ 왜 못 봤나 — **한 방향만 보고 판정했다**

카메라가 월드 고정이고 배도 제자리에 있다(물이 흐른다). 그래서 측정도 스크린샷도 전부
**같은 방위각 하나**를 봤다. `camYaw` 를 돌리거나 자유 시점(`freeView`)으로 한 바퀴 돌렸으면
즉시 드러났을 것이다.

⭐ **§3-① 의 사촌이다** — *"대칭인 시험 배치는 대칭인 버그를 숨긴다."*
**방위각 전체에 거는 효과는 한 방향만 보고 판정할 수 없다.**
불변식 0-2 의 *"방향을 재는 검사는 반드시 head 를 ±90° 로 돌려 놓고 한다"* 와 같은 규율이
표현 층에도 그대로 적용된다.

⚠ 화면 실측(원경 띠 1 → 20레벨 · 능선 기복 16px)은 **전부 맞았다.** 숫자가 틀린 것이 아니라
**재야 할 것을 안 쟀다.** 지표가 아니라 시험 배치가 문제였다 — §3-③ 과 다른 실패다.

### 21-3. 걷어낸 것과 남긴 것

| | |
|---|---|
| ❌ 걷어냄 | `sky.js` 의 `LAND` 표 · `ridge()` · `skyWithLand()` · `uLand` 유니폼 · `params` 의 `land*` 넷 · tweaks 묶음 · compare 의 '원경 산' 행 |
| ⭕ 남김 | **원경 안개 (`waterFadeSky`)** — 산과 무관하게 유효하다. 물 메시가 하늘 위에 떠 있던 판을 걷어냈고 픽셀 단위로 검증됐다 (§20-2) |

검증 : 하늘만 그린 세로 프로파일이 `250 … 249` (변화폭 **1레벨**)로 산 넣기 전과 같다.
`gl.getError()` 0 · 셰이더 컴파일 실패 0 · `land*` 파라미터 0개.

### 21-4. 다시 시도한다면 — 세 갈래

1. **한 방향에만 둔다** — 방위각 구간을 잘라 육지·섬을 한쪽에 세운다. 배가 돌면 나타났다
   사라지는데 그건 **자연스럽다** (실제 항해가 그렇다). ⚠ 그러면 그 방향이 `zones.js` 의
   자동 조타 목표와 어떤 관계인지 먼저 정해야 한다 — 육지가 향조 해역의 표지가 될 수 있다
2. **안개만으로 원경을 만든다** — 산 없이 거리감만. 지금 상태가 이것이고, 원경 띠는 비어 있다
3. **[7단계] 좌우 윙이 대신한다** — §5 의 근경 암석이 화면 좌우를 덮으면 원경 띠의 빈 느낌이
   줄어든다. ⭐ 그쪽은 **존 진입 연출**이라 평상시 화면은 여전히 비어 있다는 것이 차이다

⚠ 어느 쪽이든 **`camYaw` 를 한 바퀴 돌려 보고 판정한다.**

### 22-3. 검증 — 콘솔이 판정한다


⭐ `rise` 가 **1.099** 까지 갔다 1.0 으로 돌아온다 — `easeOutBack` 의 오버슈트이고
§7 이 *"살짝 넘겼다 돌아온다. 물에서 튀어나온 관성"* 이라 한 그것이다. **의도된 값이다.**
⚠ 소비자가 이 값을 그대로 곱하면 **1 을 넘는다.** title.js 는 그것을 전제로 짠다
(높이에 곱하는 것은 괜찮고, 알파나 색에 곱하면 외삽된다 — §5 의 `clamp` 누락과 같은 실패).

**퇴장** :

```
t=0.20  leaving  look=1.000 open=0.999/0.999 dim=0.772 rise=0.841
t=0.40  leaving  look=0.994 open=0.912/0.912 dim=0.265 rise=0.000   ← 타이포가 **먼저** 사라졌다
t=0.75  leaving  look=0.635 open=0.000/0.000 dim=0.000 rise=0.000   ← 좌우가 **같이** 열렸다
t=1.30  sailing  전부 0                                             ← 카메라가 **마지막**
```

### 22-4. ⭐ 화면이 안 바뀐다는 것을 실제로 쟀다

*"소비자가 없으니 화면이 그대로일 것"* 은 주장이지 측정이 아니다. 대조군을 세워 갈랐다
(1280×720 · 13픽셀마다 표본) :

| | 다른 표본 | 최대차 |
|---|---:|---:|
| 대조군 B — 연속 두 번 그리기만 | **0** | 0 |
| 대조군 A — `water.update()` 두 번 (phase 안 건드림) | 5 | 1 |
| **실험군 — phase 를 전환 한복판으로** | **4** | **1** |

⭐ 렌더 경로 자체는 **완전히 결정적**(대조군 B = 0)이고, `water.update()` 를 부르는 것만으로
5개가 바뀐다(부동소수점 누적). phase 전환은 그보다도 **적다.** 화면을 안 건드린다.

⚠ 이 대조군이 없었으면 "표본 7개가 다르다" 를 보고 **phase 가 화면에 샌다**고 오진했을 것이다.
§20-6 에 이은 같은 교훈 — **차이를 재기 전에 아무것도 안 했을 때의 차이를 먼저 잰다.**

### 22-5. 가드

- **전환 중 재진입 차단** (§9-4) — `enter()` 가 `busy` 면 `false` 를 돌려주고 아무것도 안 한다.
  실측 : 전환 중 `enter('floral')` · `enter('amber')` 둘 다 `false` 이고 `cue.zone` 이
  `'woody'` 로 유지된다. **두 향조 사이에서 찢어지지 않는다.**
  ⚠ `input.js` 는 아직 이걸 안 본다 — `cue.busy` 를 읽어 클릭을 막는 것은 진입점이 붙을 때 한다.
- **같은 존 재진입 차단** — `inspecting` 에서 같은 zone 으로 `enter()` 하면 `false`.
- **`phaseAmount` 0 = 비트 단위 롤백** — 상태는 유지한 채 값만 전부 0 이 되고, 되돌리면 즉시 복귀.
- **`phaseSpeed`** — 0.25 로 내리면 4배 느리게 흘러 눈으로 따라갈 수 있다 (비교 패널에 시안 셋).

### 22-6. ⚠ 게이트를 걸지 않는다

`phase.update(dt)` 는 `tick()` 에서 **매 프레임** 돈다. 카메라가 매 프레임 움직여야 하기 때문이다.
물에 닿는 값(타이포 높이 등)은 **소비자 쪽에서** 자기 게이트를 건다.

§7 이 GSAP 을 기각한 이유가 이것이다 — *"GSAP 은 60fps 로 도는데 물은 12fps 다. 물에 닿는 값을
GSAP 이 몰면 게이트를 우회하게 된다."* 직접 짜면 그 실수를 할 방법이 없다.

### 22-7. 남은 것

1. **소비자를 붙인다** — [5단계] 카메라(`cue.look`) · [6단계] `title.js`(`cue.rise`) ·
   [7단계] `gate.js`(`cue.openL/R`) · `stage.js`(`cue.dim`).
   ⚠ [5단계]는 끝났다 (§23). §19-9 의 제약은 **실측으로 뒤집혔다** — `camDist` 를 그대로
   트윈해도 원경이 안 부푼다 (단, 카메라와 물이 **같은 kD** 를 볼 때만).
2. **진입점** (§10-1, 사용자 미정) — 무엇을 클릭하면 `enter()` 가 불리는가.
   `phase.js` 는 그걸 모르므로 **나중에 붙여도 된다.**
   ⭐ §9-9 : `zones.js` 의 자동 조타 도착과 **같은 `phase` 로 묶으면** 연출을 두 번 안 만든다.

## 23. [5단계] 카메라가 `cue` 를 읽는다 — **첫 번째 소비자** <span>— 2026-09-10</span>

§8 의 [5단계]. [4단계]가 만든 `cue.look` 을 카메라가 실제로 읽기 시작한다.
**이 프로젝트에서 연출이 화면을 움직이는 첫 지점이다.**

### 23-1. ⭐⭐ 먼저 — **§19-9 는 틀렸다**

어제 §19-9 에 이렇게 적었다 : *"`uFade1` 95.0 이 물끝 106 보다 안쪽이라 페이드가 메시 안에서
완성된다 → `camDist` 를 트윈하면 원경이 부푼다 → 선택지 C 가 닫혔다."*

**실측이 뒤집었다.** `camPitch` 를 고정하고 `camDist` 만 **2배**(3.0 → 6.0) 바꿔 봤다 :

| camDist | 카메라 높이 | `uFade0/1` | 페이드 시작 y | 페이드 끝 y |
|---:|---:|---|---:|---:|
| 3.0 | 7.88 | 36/72 | 311.2 | 212.7 |
| 3.96 | 10.30 | 48/95 | 309.4 | 211.8 |
| 6.0 | 15.46 | 72/144 | 307.6 | **210.8** |

**끝이 1.9px, 시작이 3.6px 움직였다.** 거리가 2배가 됐는데도.

⭐ 이유는 `main.js` 주석에 이미 적혀 있었다 — *"물러나면 거리 페이드와 LOD 도 같이 밀어야
한다. 안 밀면 새로 보이게 된 원경이 흰 여백에 먼저 먹혀 아무것도 안 늘어난다."*
**카메라 높이와 페이드 거리가 같은 비율로 커지므로 화면 y(∝ camY/d)가 상쇄된다.**
페이드가 `camDist` 를 타는 것은 버그가 아니라 **화면상 물끝을 고정시키는 보정**이었다.

⚠ **내 오류의 형태** : "페이드가 작동한다"에서 "화면이 움직인다"로 **건너뛰었다.** 작동하는
것과 화면에 보이는 것은 다르고, 그 사이에 상쇄가 있었다. **재지 않고 추론했다.**

### 23-2. ⚠⚠ 다만 상쇄는 **둘이 같은 `kD` 를 볼 때만** 성립한다

`camDist` 소비자는 정확히 둘이다 — `main.js` 의 카메라 배치와 `water.js` 의 페이드·LOD.
전환 중에는 **보간된 값**을 써야 하는데, `water.js` 는 `P.camDist` 를 **직접** 읽고 있었다.
그대로 두면 카메라만 물러나고 페이드는 제자리라 상쇄가 깨진다.

실측 (존 구도 `look = 1`) : 보간을 안 넘기면 물끝이 **9.6px** 아래로 밀린다 = 원경이 부푼다.

→ `water.update(sim, cam, t, camK)` 로 인자를 하나 늘려 **같은 값을 넘긴다.**
⚠ 안 넘어오면 예전처럼 `P.camDist` 를 쓰므로 다른 호출부가 있어도 안 깨진다.

⚠ **상쇄의 정도는 `pitch` 에 의존한다.** pitch 15.4 에서는 2배 거리에 1.9px 인데,
pitch 9.0 에서는 작은 거리 변화에도 9.6px 이 났다. 낮은 각일수록 상쇄가 덜 된다 —
`zonePitch` 를 더 내리면 이 값을 다시 잰다.

### 23-3. 배선 — `main.js` 카메라 블록 세 줄

```js
const cl = phase.cue.look;                                    // 0 항해 · 1 존
const kD = Math.max(0.2, lerp(PARAMS.camDist,  PARAMS.zoneDist,  cl));
const yaw   = lerp(PARAMS.camYaw,   PARAMS.zoneYaw,   cl) * D2R;
const pitch = lerp(PARAMS.camPitch, PARAMS.zonePitch, cl) * D2R;
...
water.update(sim, view, t, kD);                               // ⚠ 같은 kD 를 넘긴다
```

⭐ **트윈을 여기서 짜지 않는다.** 커브는 전부 `phase.js` 의 `TL` 에 있고 여기는 **읽기만** 한다.
§2 의 *"렌더 루프가 그 값을 읽는 유일한 지점"* 이 이 세 줄이다.

### 23-4. 존 구도 — ✅ **확정됐다** (2026-09-10 오후, 사용자가 화면을 보고 정했다)

⚠ 아래 값은 09-10 **오후**에 바뀐 것이다. 그 전의 추정값(`−30 / 9.0 / 4.6`, 배가 정중앙)은
비교 패널 '존 구도' 행의 **[한가운데]** 로 남겨 뒀다 — 그 화면이 밋밋해서 바꿨다.

| | 항해 | 존 (확정) |
|---|---:|---:|
| `camYaw` | −52.1 | **−30** (정면 쪽으로 22°) |
| `camPitch` | 15.4 | **9.0** |
| `camDist` | 3.96 | **2.4** ← 4.6 에서 **다가섰다** |

#### ⭐⭐ 배는 더 이상 화면 정중앙이 아니다 — 그런데 **배를 옮긴 것이 아니다**

사용자 : *"왼쪽 하단쯤에 배가 확대된 상태로 카메라가 연출되어야 할 것 같은데 … 예시 이미지
정도의 극적인 연출이 필요할 것 같음"*. 예전에는 언제나 `cam.lookAt(CONFIG.cam.look)` 이라
배가 **늘 한가운데**였고, 그게 존 화면을 밋밋하게 만들고 있었다.

⭐ **시선 목표를 화면 기준으로 민다.** 배를 옮기면 항적·뱃머리 파가 따라가고, 카메라를 yaw 로
더 돌리면 **불변식 0-4** 의 광원·돛 관계가 깨진다. 셋 중 시선만이 부작용이 없다.

⚠ 단위는 **화면 반폭·반높이 대비 비율**이다 — 그래서 `zoneDist` 를 바꿔도 배가 화면에서
앉는 자리가 그대로다. 월드로 주면 거리마다 다시 잡아야 한다.

검산 : `lookX 0.30 · lookY 0.35` 이면 시선이 look 축에서 **14.1°** 벗어난다
(offset/baseDist = √((0.30·tan(21.5°)·aspect)² + (0.35·tan(21.5°))²) = 0.2515).
실측한 시선-배 내적이 **0.9698 = cos 14.1°** 로 정확히 맞았다.
⚠ **항해에서는 0 이다** — `cue.look` 을 곱하므로 오프셋도 같이 트윈된다. 실측 내적 **1.00000**.

⚠ 오른쪽이 비는 것은 의도다. 09-09 레퍼런스가 거기에 향조 정보를 놓고, §6 접근성이 요구하는
**DOM 제목**도 그 자리다 (`cue.ui` 가 값을 이미 밀고 있는데 읽는 쪽이 없다).

⚠⚠ **`zoneYaw` 는 음수를 유지한다** (불변식 0-4). 양수면 카메라가 배의 그늘진 쪽에 서서
흰 돛이 회색 판때기가 된다. 슬라이더 상한을 **0 으로 막아** 두었다.
⚠ 원경 띠가 60px 로 **좁아진다** — §12-6 의 *"pitch 를 내릴수록 간극이 준다"* 그대로다.
타이포가 걸릴 자리는 넓어지지만 원경이 들어갈 자리는 줄어든다. 둘의 균형이 이 값의 쟁점이다.

⚠ 존 구도를 잡으려면 `PB.phase.snap('inspecting')` 으로 고정하고 슬라이더를 민다 —
`sailing` 에서는 `cue.look` 이 0 이라 `zone*` 을 아무리 만져도 화면이 안 바뀐다.

다시 버리게 된다.** 두 판본이 충돌하는 지점이 정확히 여기이고, 이건 **아트 결정**이다.

### 23-4-b. ⚠ 그 김에 발견한 것 — **타이포 폭이 종횡비를 안 본다**

`titleWidth 69` 는 *"fov 43 · **16:9** 에서 화면 폭 = 1.40 × dist"* 에서 나온 값이다(§24).
그런데 화면 폭(월드)은 `2 · dist · tan(fov/2) · **aspect**` 라 **창이 좁아지면 같이 줄어든다.**
타이포 폭은 월드 고정이므로 화면 비율이 그만큼 부푼다 — 실측 :

| 종횡비 | 화면 폭(월드) | 타이포가 차지하는 비율 |
|---|---:|---:|
| 1.752 (지금 창) | 113.2 | 61% ✅ |
| 1.408 | 91.0 | **77%** |
| 1.0 | 64.6 | **107% — 잘린다** |

실제로 Browser pane 이 좁았을 때 `WOODY` 의 `Y` 가 화면 밖으로 나가는 것을 봤다.
고치는 것은 한 줄이다 — 굽는 쪽이 아니라 **평면 폭을 aspect 로 나눈다** (16:9 기준을 유지).

## 24. [6단계] `title.js` — 수면에서 솟는 향조 이름 <span>— 2026-09-10</span>

§8 의 [6단계]. §6 의 설계를 그대로 만들었다. **`cue.rise` 의 첫 소비자다.**

### 24-1. 자산 0 바이트 — 웹폰트를 캔버스에 굽는다

`Jost` (구글 폰트, **라틴 대문자 26자 서브셋** `&text=`) → Canvas 2D → `CanvasTexture` → 3D 평면.
텍스처는 **2048×512 한 장을 재사용**한다 (존이 바뀌면 같은 캔버스에 다시 굽는다).
글자는 `CONFIG.areas[].name` 을 대문자로 쓴다 — 이름을 두 곳에 적지 않는다.

⚠ 캔버스는 **알파 마스크**로만 쓰고 색은 셰이더가 준다. 그래야 색을 바꿀 때 다시 안 구워도 된다.

### 24-2. ⚠⚠ 폰트 로딩 — §6 보다 한 걸음 더

§6 은 *"`document.fonts.ready` 를 기다린 뒤 굽는다"* 인데, 그것만으로는 네트워크가 실패하면
글자가 영영 안 나온다. 여기서는 **일단 굽고, 폰트가 도착하면 한 번 더 굽는다.**

검증 : 구운 글자 폭 **1496px** 이 Jost 예측(1256.3 + 자간 228.5 = 1484.8)과 맞고
폴백 예측(1405.5)과는 90px 벌어진다 → **Jost 로 구워졌다.**

### 24-3. ⚠⚠⚠ 밟은 것 셋

1. **글자가 좌우로 뒤집혔다** — 화면에 `YDOOW` 로 나왔다.
   `PlaneGeometry` 는 +z 를 보므로 `atan2(ux, uz)` 는 평면을 카메라 **반대쪽**으로 돌린다.
   `DoubleSide` 라 뒷면이 보였다. → `atan2(−ux, −uz)`.
2. **`textBaseline = 'middle'` 이 글리프를 아래로 치우치게 뒀다** (실측 : 글리프 하단이
   캔버스의 **0.752** 지점). em 박스 기준이라 대문자만 쓸 때 그렇다. → `alphabetic` 으로 바꾸고
   **실제 글리프 박스를 재서 캔버스 중앙에 맞춘다.**
3. **`measureText` 의 `actualBoundingBox` 로는 부족했다** — 실제 픽셀과 **5.8%** 어긋나
   `titleLift 0` 에서 0.273 월드가 남았다. → **구운 캔버스를 직접 훑어** 글리프 범위를 잰다
   (굽기는 존이 바뀔 때만이라 비용이 무시할 만하다). 고친 뒤 오차 **0**.

⭐ 그래서 `titleLift` 의 뜻이 하나로 정해졌다 — **rise=1 일 때 글리프 밑동이 수면 위로 뜨는
양**(글리프 높이 대비). 0 이면 밑동이 딱 수면, 음수면 잠긴다.
실측 : `rise` 0 → 밑동 −9.49(= 글리프 높이만큼 완전히 잠김) · 0.5 → −4.75 · 1 → **0.00**.

### 24-4. 워터라인 클리핑 — CPU 너울로 낸다

§6 은 `sim.texture` 를 읽는 **B안**을 권했지만, 이 층은 원경에 거의 정지해 있어서
`swellCPU()` 한 번이면 같은 취지(*"물과 무관하게 움직이면 스티커로 읽힌다"*)를 이룬다.
텍스처 페치가 0 이고 불변식 2 를 안 건드린다.

⚠⚠ **`boat.js` 와 글자 그대로 같은 호출이어야 한다** — 물은 `qScroll` 로 흐르므로 월드
좌표에 그만큼 보정하고(불변식 0-2 의 비대칭 규약 : x 는 `+`, z 는 `−`), 시각은
`sim.qT × waveSpeed` 다. 처음에 이걸 빠뜨려 글자가 **다른 바다**를 볼 뻔했다.

⚠ 대가는 클리핑 선이 **직선**이라는 것이다 (글자 폭 전체가 같은 높이에서 잘린다).
원경이라 안 보일 것으로 보고 시작한다 — 티나면 다중 샘플이나 B안으로 올린다.

### 24-5. ⭐ 거리와 폭은 한 묶음이다 — 그리고 **95 는 너무 멀었다**

존 구도(fov 43 · 16:9)에서 화면 폭 = `1.40 × dist` 이므로, 레퍼런스의 *"화면 폭 60%"* 는

옅어서 잠긴 것으로 안 읽혔다.** 화면으로 보고서야 알았다 — 숫자는 처음부터 맞았다.

### 24-8. ⭐ 글자나 폰트가 바뀔 때 — 무엇이 자동이고 무엇이 손으로인가

사용자 질문 (2026-09-10) : *"폰트나 글자가 다르게 설정될 경우에는 어떻게 해결함?"*

**`WOODY` 하나로만 검증했던 것을 네 향조 + 긴 이름 + 한글로 다시 쟀고, 두 가지를 고쳤다.**

#### 글자가 바뀌는 경우 — 전부 자동이다

| 무엇 | 어떻게 |
|---|---|
| 다른 향조로 전환 | `bake()` 가 `글자+폰트준비+자간` 을 키로 비교해 **바뀔 때만** 다시 굽는다 |
| 글자 수가 다르다 | 높이가 고정이고 폭만 는다. 실측 : `FRESH` 56.9% · `AMBER` 63.9% · `FLORAL` 69.7% · `WOODY` 73% — **세로는 232~244 로 일정**하다 (타이포그래피적으로 맞다) |
| **긴 이름** | ⚠⚠ **잘렸다** — `MEDITERRANEAN` 99.9% · `OCEANIC BREEZE` 97% · `시트러스 블라썸` 99.9%. → 폭이 캔버스의 92% 를 넘으면 **비례로 한 번 줄인다.** 폭도 자간도 `size` 에 선형이라 한 번이면 정확히 맞는다. 고친 뒤 전부 **91% 안쪽** |
| **한글 이름** | ⚠ Jost 는 라틴만 있다. 폰트 스택을 `"Jost", Pretendard, sans-serif` 로 둬 **한글은 Pretendard 로 떨어진다** (`index.html` 이 이미 받고 있으므로 §6 의 *"시스템 폰트로 때우지 않는다"* 에 안 걸린다). 세로가 라틴 244 vs 한글 278 로 다르지만 **위치는 `glyphFrac` 을 실측하므로 맞는다** |
| 이름의 출처 | `CONFIG.areas[].name` **하나**다. 여기 또 적지 않는다 |

⚠ 짧은 글자는 화면에서 작다 (`A` 10.9% · `우디` 27.5%). 평면 폭이 고정이라 그렇고,
**폭을 채우도록 늘리지 않는다** — 짧은 단어가 거대해져서 오히려 어색하다.

#### 폰트가 바뀌는 경우 — 한 곳은 손으로다

| 무엇 | 어떻게 |
|---|---|
| **다른 웹폰트로 교체** | ⚠⚠ **두 곳을 같이 고친다** — `title.js` 의 `FONT` 상수와 `index.html` 의 구글 폰트 링크. 하나만 고치면 **조용히 폴백으로 구워지고**, 그때도 화면에는 글자가 나오므로 안 들킨다. 두 파일에 주석으로 못 박아 뒀다 |
| 로딩이 늦거나 실패 | 자동. 일단 굽고 **도착하면 한 번 더 굽는다** (§24-2) |
| 자간 | `titleSpacing` 파라미터. 바꾸면 다시 굽는다 |
| **굵기** | 지금 `600` 하드코딩이다. ⚠ 바꾸려면 서브셋 링크의 `wght@600` 도 같이 고쳐야 한다 — 안 고치면 그 굵기가 안 와서 브라우저가 합성한다 |

⭐ 이 셋이 자동으로 맞는 이유는 하나다 — **굽고 나서 실제 픽셀을 재기 때문**이다
(`glyphFrac` · `glyphMid`). 폰트가 무엇이든, 글자가 몇 자든, 어느 언어든 그 측정이
`titleLift` 의 기준을 다시 잡아 준다.
