## 2. 설치해야 하는 것

### 2.1 Node.js — 필수

**22.12.0 이상**이 필요합니다. Vite 8과 TypeScript 6이 이 버전을 요구합니다.

```bash
node -v    # v22.12.0 이상이어야 합니다
npm -v     # 10.9.0 이상
```

버전이 낮거나 설치되어 있지 않다면 [nodejs.org](https://nodejs.org)에서 **LTS 버전**을 설치하세요.
여러 프로젝트를 병행한다면 버전 관리 도구를 쓰는 편이 편합니다.

- Windows: [nvm-windows](https://github.com/coreybutler/nvm-windows)
- macOS / Linux: [nvm](https://github.com/nvm-sh/nvm), [fnm](https://github.com/Schniz/fnm)

### 2.2 Git — 필수

이미 설치되어 있을 것입니다. 사용자 정보가 설정되어 있는지만 확인하세요.

```bash
git config --global user.name
git config --global user.email
```

### 2.3 VS Code 확장 — 권장

에디터는 자유지만, VS Code를 쓴다면 아래 4개를 설치하는 것을 권장합니다.
설치하지 않아도 개발은 되지만, 저장할 때 자동 정리가 안 돼서 `npm run lint`에서 반복해서 걸립니다.

| 확장 | ID | 역할 |
| --- | --- | --- |
| ESLint | `dbaeumer.vscode-eslint` | 코드 규칙 위반을 편집 중에 표시·자동 수정 |
| Prettier | `esbenp.prettier-vscode` | 저장 시 자동 포맷 |
| Tailwind CSS IntelliSense | `bradlc.vscode-tailwindcss` | 클래스 자동완성, 색상 미리보기 |
| EditorConfig | `editorconfig.editorconfig` | 들여쓰기·줄바꿈 규칙 자동 적용 |

설치 후 VS Code 설정(`Ctrl+,` → 우측 상단 파일 아이콘)에 아래를 추가하면 저장할 때마다 포맷과 ESLint 자동 수정이 적용됩니다.

```jsonc
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "eslint.useFlatConfig": true,
  "typescript.tsdk": "node_modules/typescript/lib",
  "files.eol": "\n"
}
```

`files.eol`을 `\n`으로 두는 이유는 Windows 기본값(CRLF)으로 저장하면 **줄바꿈만 바뀐 diff**가 MR에 잔뜩 생기기 때문입니다.

## 3. 처음 시작하기

### Step 1. 저장소 클론 및 브랜치 이동

```bash
git clone https://lab.ssafy.com/s15-bigdata-recom-sub1/S15P21E203.git
cd S15P21E203
git switch develop
git pull origin develop
```

### Step 2. 의존성 설치

```bash
cd frontend
npm ci
```

> **`npm install`이 아니라 `npm ci`입니다.**
> `npm install`은 `package-lock.json`을 갱신해서 사람마다 다른 버전이 설치될 수 있습니다.
> "제 컴퓨터에서는 되는데요"의 가장 흔한 원인입니다.
> 새 패키지를 추가할 때만 `npm install <패키지명>`을 쓰고, **바뀐 `package-lock.json`을 반드시 함께 커밋**하세요.

### Step 3. 환경변수 파일 만들기

```bash
cp .env.example .env.local        # Windows(명령 프롬프트): copy .env.example .env.local
```

`.env.local`은 `.gitignore`에 포함되어 있어 커밋되지 않습니다. **각자 만들어야 합니다.**

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `/api/v1` | API 요청 앞에 붙는 경로 (명세서의 버전 prefix 포함) |
| `VITE_API_PROXY_TARGET` | `http://localhost:8080` | 개발 서버가 요청을 넘겨줄 백엔드 주소 |

이 파일을 만들지 않으면 앱 실행 시 아래 에러가 납니다. 잘못된 값으로 조용히 동작하는 것보다 낫도록 일부러 막아둔 것입니다.

```
환경변수 VITE_API_BASE_URL 가 설정되지 않았습니다.
```

### Step 4. 실행 확인

```bash
npm run dev
```

브라우저에서 <http://localhost:5173> 에 접속해 상단에 "향해" 내비게이션이 보이면 정상입니다.

### Step 5. 검증 명령 확인

```bash
npm run verify
```

포맷 검사 → ESLint → 타입 검사 → 테스트 → 빌드를 순서대로 실행합니다.
**MR을 올리기 전에는 항상 이 명령을 통과시켜 주세요.** 하나라도 실패하면 리뷰어가 받기 전에 먼저 걸립니다.

## 5. 무엇을 왜 이렇게 설정했는가

### 5.1 기술 스택

| 구분 | 선택 | 선택 이유 |
| --- | --- | --- |
| 빌드 도구 | Vite 8 | 개발 서버 기동과 HMR이 빠름 |
| 언어 | TypeScript 6 (strict) | 백엔드 API 응답 형태를 코드로 고정 |
| 라우팅 | React Router 8 | 라우트 단위 코드 스플리팅 지원 |
| 서버 상태 | TanStack Query 5 | 캐싱·로딩·에러·재요청을 직접 구현하지 않음 |
| 전역 상태 | Zustand 5 | 보일러플레이트 없이 세션성 상태만 관리 |
| HTTP | Axios | 인터셉터로 토큰 주입과 에러 처리를 한 곳에서 |
| 스타일 | Tailwind CSS 4 | 반복되는 카드·리스트 UI를 빠르게, 토큰은 CSS에서 관리 |
| 품질 도구 | ESLint 10 + Prettier 3 | 포맷은 Prettier, 코드 규칙은 ESLint로 역할 분리 |

### 5.2 경로 alias

`@`가 `src`를 가리킵니다. `../../../shared/api/http` 같은 경로는 쓰지 않습니다.

```ts
import { http } from '@/shared/api/http' // O
import { http } from '../../../shared/api/http' // X
```

### 5.3 개발 중 CORS가 필요 없는 이유

`VITE_API_BASE_URL=/api/v1`로 두면 Vite 개발 서버가 `/api`로 시작하는 요청을 `VITE_API_PROXY_TARGET`(기본 `http://localhost:8080`)으로 대신 전달합니다.
브라우저 입장에서는 같은 출처(same-origin)라서 **로컬 개발 중에는 백엔드에 CORS 설정이 없어도 동작합니다.**

프록시 규칙은 `vite.config.ts`에서 `/api`로 잡혀 있습니다. Vite 프록시는 경로 앞부분만 비교하므로
`/api/v1/...` 요청도 이 규칙에 걸립니다. 버전이 올라가도 프록시 설정은 고치지 않아도 됩니다.

### 5.4 환경변수를 한 곳에서만 읽는 이유

`import.meta.env`는 `src/shared/config/env.ts`에서만 읽습니다.
코드 전역에 흩어져 있으면 오타나 누락을 실행 중에야 발견하게 되는데, 한 곳에 모으면 앱 시작 시점에 바로 에러로 잡힙니다.

### 5.5 디자인 토큰

Tailwind 4는 CSS의 `@theme` 블록에서 토큰을 정의합니다. 위치는 `src/styles/index.css`입니다.

```
브랜드 색   --color-brand-50 ~ 900   →  bg-brand-500, text-brand-700
텍스트 색   --color-ink, --color-ink-muted
배경 색     --color-surface
모서리      --radius-card            →  rounded-card
```

현재 값은 임시입니다. **디자인 시안이 확정되면 이 블록의 값만 교체**하면 전체 화면에 반영됩니다.
컴포넌트마다 `#3f5337` 같은 색상 코드를 직접 쓰지 말고 토큰 클래스를 사용해 주세요.

### features 슬라이스 작성 방법

한 도메인에 필요한 것을 한 폴더에 모읍니다. **`src/features/perfume/`이 참고 구현입니다. 그대로 따라 하세요.**

```
features/<도메인>/
├── index.ts        공개 API — 밖에서 쓸 것만 여기서 export
├── types.ts        API 요청/응답 타입
├── api.ts          http 호출 함수 (컴포넌트를 몰라도 되는 순수 함수)
├── queries.ts      queryKey + queryOptions / useMutation
├── hooks/          이 도메인 전용 훅
└── components/     이 도메인 전용 컴포넌트
                    테스트는 대상 파일 옆에 둡니다 (Xxx.tsx -> Xxx.test.tsx)
```

> **규칙 하나만 지켜주세요: `features/a`가 `features/b`를 import하지 않기.**
> 두 도메인이 함께 필요하면 공통 부분을 `shared/`로 올리거나, `pages/`에서 조합합니다.
> 서로 물고 물리기 시작하면 나중에 아무도 손을 못 댑니다.

이 규칙은 이제 **ESLint가 강제합니다.** 어기면 `npm run lint`가 실패합니다.
의존 방향은 `app → pages → features → shared` 한 방향이고, 역방향과 도메인 간 교차가 모두 막혀 있습니다.
규칙은 `eslint.config.js`의 `import-x/no-restricted-paths`에 있고,
새 도메인 폴더를 만들면 같은 파일의 `FEATURE_DOMAINS` 배열에도 추가해야 검사가 걸립니다.

도메인은 `index.ts`를 공개 API로 두고, 밖에서는 그것만 import 합니다.

```ts
import { perfumeDetailQuery } from '@/features/perfume' // O
import { perfumeDetailQuery } from '@/features/perfume/queries' // X
```

### 공용 UI 컴포넌트

새로 만들기 전에 `src/shared/ui/`에 있는지 먼저 확인하세요.

| 컴포넌트 | 용도 |
| --- | --- |
| `Button` | `variant` primary·secondary·outline·ghost·danger / `size` sm·md·lg·icon / `isLoading` |
| `Input` | 라벨·에러·hint·접근성 속성 포함 (라벨은 필수 prop) |
| `Card` | 목록에 반복되는 박스. `interactive` 로 호버 효과 |
| `Badge` | 향 계열·상태 같은 짧은 라벨 |
| `Modal` | 네이티브 `<dialog>` 기반. 포커스 가두기·Esc·배경 스크롤 잠금 자동 |
| `Skeleton` | 로딩 중 자리 잡기. 목록에는 스피너보다 이걸 씁니다 |
| `EmptyState` | 결과 0건 화면 |
| `PageFallback` | 라우트 lazy 로딩용 전체 스피너 |

스타일 차이는 새 컴포넌트를 만들지 않고 **variant 를 추가**합니다
(`class-variance-authority` 사용). `PrimaryButton` 같은 파생 컴포넌트는 만들지 않습니다.

공용 컴포넌트에서 `className` 을 받을 때는 반드시 `cn()`(`shared/lib/cn.ts`)으로 합칩니다.
문자열을 이어붙이면 호출하는 쪽이 기본 스타일을 덮어쓸 수 없습니다.

### 공용으로 올리는 시점

**예상해서 미리 `shared/`에 올리지 않습니다.** 처음에는 `features/<도메인>/components/`에 만들고,
다른 도메인에서 같은 것이 실제로 필요해진 그 시점에 옮깁니다.
옮길 때는 도메인 타입 의존을 끊어야 합니다 — `shared/`가 `features/`를 import 하면 ESLint 가 막습니다.

애매하면 항상 도메인 안에 둡니다. 나중에 올리는 건 쉽지만, 잘못 올라간 것을 되돌릴 때는
이미 3명이 그걸 import 한 뒤입니다.

### 화면 하나를 새로 만드는 순서

1. `shared/config/routes.ts`에 경로 상수 추가
2. `pages/`에 화면 컴포넌트 추가 (default export)
3. `app/router/index.tsx`에 lazy 라우트 등록
4. 서버 데이터가 필요하면 `features/<도메인>/`에 `types.ts` → `api.ts` → `queries.ts` 순으로 작성
5. 화면에서 `useQuery(도메인Query(...))`로 사용

`src/pages/PerfumeDetailPage.tsx`가 4~5번까지 이어지는 전체 예시입니다.

| import 경로 | `@/` alias 사용. `../../../` 금지 |
| import 순서 | 외부 → `@/` 내부 → 상대경로. `npm run lint:fix`가 자동 정렬 |
| 타입 import | `import type { X }` 사용 (ESLint가 자동 수정) |
| `any` | 금지. 모르면 `unknown`으로 받고 좁혀서 사용 |
| 서버 데이터 | `useState`에 담지 않고 전부 TanStack Query로 관리 |
| 전역 상태 | Zustand는 로그인 정보, UI 토글 같은 **클라이언트 상태만** |
| `console.log` | 경고 처리. `npm run lint`가 실패하므로 커밋 전 제거 (`console.warn`, `console.error`는 허용) |
| 사용하지 않는 변수 | 에러. 의도적으로 무시할 때만 `_` 로 시작 |

### 서버 통신은 항상 `http` 인스턴스로

`axios`를 직접 import하지 말고 `@/shared/api/http`의 `http`를 사용하세요. 여기에서 아래가 자동으로 처리됩니다.

- 요청에 `Authorization: Bearer <token>` 주입
- 응답 에러를 `ApiError { status, code, message }`로 정규화
- 401 응답 시 인증 상태 초기화(자동 로그아웃)

에러 처리는 `error.message`를 그대로 쓰면 되고, 상태 코드가 필요하면 `isApiError(error)`로 좁혀서 `error.status`를 확인합니다.

## 8. 작업 흐름

팀 Git 컨벤션과 Jira 이슈 관리 규칙을 따릅니다. (`docs/Git_컨벤션_규칙.pdf`, `docs/Jira_이슈_관리_규칙.pdf`)

```
Jira 이슈 확인
  → 최신 develop에서 브랜치 생성
  → 개발 및 확인
  → npm run verify 통과
  → develop으로 MR 생성
  → 리뷰
  → 병합 후 브랜치 삭제
```

```bash
git switch develop
git pull origin develop
git switch -c feature/fe/S15P21E203-00-perfume-map

# 작업 후
cd frontend && npm run verify
git add .
git commit -m "feat: S15P21E203-00 향 지도 화면 구현"
git push -u origin feature/fe/S15P21E203-00-perfume-map
```

| 항목 | 형식 | 예시 |
| --- | --- | --- |
| 브랜치 | `{타입}/fe/{Jira 키}-{기능명}` | `feature/fe/S15P21E203-31-perfume-map` |
| 커밋 | `{타입}: {Jira 키} {작업 내용}` | `feat: S15P21E203-31 향 지도 화면 구현` |
| MR 제목 | `[{Jira 키}][{타입}] {작업 내용}` | `[S15P21E203-31][feat] 향 지도 화면 구현` |

- 커밋 타입: `feat`, `fix`, `refactor`, `design`, `docs`, `test`, `chore`, `remove`
- **1 Jira 이슈 = 1 브랜치 = 1 MR**
- `master`, `develop`에 직접 push하지 않습니다
- MR 본문은 `.gitlab/merge_request_templates/Default.md` 템플릿이 자동으로 채워집니다

## 10. 아직 정해지지 않은 것

작업을 진행하면서 팀과 맞춰야 하는 항목입니다.

### 백엔드와 확정 필요

- **인증 방식** — refresh token을 httpOnly 쿠키로 받는다고 가정하여 `withCredentials: true` 설정.
  401 발생 시 토큰 재발급 로직은 인증 스펙 확정 후 인터셉터에 추가 예정

- **`PerfumeSummary`의 `thumbnailUrl` / `scentFamily`** — 프론트 타입은 **필수**로 선언돼 있지만
  백엔드 COM-05 검색 응답(`PerfumeSummaryResponse`)은 `{ perfumeId, name, brand }`만 내려줍니다.
  두 필드는 각각 `perfume_images`, `perfume_map_points`+`scent_regions` 조인이 필요해서
  해당 기능 이슈에서 추가될 예정입니다.
  → **타입은 통과하는데 런타임엔 `undefined`입니다.** 검색 결과 목록에서 쓸 때 값이 없는 경우를
  먼저 처리하세요. 백엔드에 필드가 추가되면 `features/perfume/types.ts`의 경고 주석을 지우면 됩니다.

- **향 계열(`scentFamily`) 검색 필터** — 백엔드 컨트롤러는 `keyword`만 받습니다.
  `PerfumeSearchParams.scentFamily`를 보내도 **조용히 무시**되고 전체 결과가 내려옵니다.
  필터가 화면에 필요하면 백엔드에 이슈로 요청해야 합니다.
  반대로 백엔드가 지원하는 `sort`는 프론트 타입에 아직 없습니다.

- **DTL-01 향수 상세 조회 (`GET /perfumes/{id}`)** — `features/perfume/api.ts`에 함수는 있지만
  백엔드에 엔드포인트가 아직 없습니다. 호출하면 404입니다.

> 위 세 항목은 백엔드 `feat/be/S15P21E203-95-perfume-search` 브랜치 기준입니다.
> develop에 머지되면 실제 응답을 다시 확인하고 타입을 맞춰주세요.

아래 두 가지는 **확정되었습니다.** 백엔드가 프론트 타입에 맞춰 응답을 감싸주기로 해서
`features/perfume/types.ts` 와 `shared/api/http.ts` 를 고칠 필요가 없습니다.

- **공통 에러 응답 형태** — `{ code, message }` 확정.
  백엔드 `common/ApiErrorResponse.java` (record) ↔ 프론트 `shared/api/http.ts` 의 `ApiErrorResponse`
- **페이지네이션 응답 형태** — `{ content, page, size, totalElements, totalPages }` 확정.
  백엔드 `common/PageResponse.java` ↔ 프론트 `features/perfume/types.ts` 의 `Page<T>`.
  Spring `Page` 를 그대로 직렬화하면 현재 페이지가 `number` 로 나가므로, 백엔드가 `page` 로 감싸줍니다.
  **페이지 번호는 0부터 시작합니다.**

### 팀 논의 필요

- Git hook(husky + lint-staged) 도입 여부 — `frontend/`가 하위 폴더라 루트에서 설정해야 함
- 테스트 도구(Vitest + Testing Library) 도입 시점
- Jenkins 파이프라인에 frontend 빌드 스테이지 추가 (현재는 backend만 빌드)
- 디자인 시안 확정 후 `src/styles/index.css`의 `@theme` 토큰 교체
