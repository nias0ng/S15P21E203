# 9.2(수)
###

기능명세서(62개 기능)와 ERD를 대조하여 설계 결함을 도출하고, 팀 논의를 통해 결정된 사항을 ERD에 반영. 총 35개 테이블 검토.

1. 테이블 삭제

ai_content_review_results 제거

콘텐츠 검수를 하드코딩 금칙어 기반 입력 검증으로 처리하기로 결정
검수 결과가 DB에 저장되지 않으므로(위반 시 업로드 자체가 중단) 이력 테이블이 불필요
기존에 어떤 콘텐츠를 심사한 결과인지 참조 컬럼이 없어 조인이 불가능한 상태였음
2. 컬렉션 공유 구조 확정

공유 방식: 스냅샷 (게시글 독립)

컬렉션을 커뮤니티에 공유할 때 해당 시점의 향수 목록을 게시글에 복사
posts.collection_id 및 관련 FK 삭제 → 게시글이 컬렉션을 참조하지 않음
post_perfumes.display_order 추가 (스냅샷 시 배열 순서 보존)
컬렉션 삭제/수정이 게시글에 영향을 주지 않음

collections.is_public 추가하지 않음

공개 여부는 "해당 컬렉션을 공유한 게시글이 존재하는가"로 파생 가능
별도 컬럼을 두면 게시글 삭제 후에도 공개 상태가 남는 드리프트 발생
3. 향 지도 구조 확정

단일 정사각형 지도 + 4개 향 영역

테이블	변경
scent_regions	map_family 삭제, 경계값 min_x/min_y/max_x/max_y 추가
user_preference_regions	취향 중심 좌표 center_x/center_y 추가
perfume_map_points	map_family → scent_region_id FK로 변경
map_exploration_states	exploration_family 삭제
향족과 영역이 1:1이므로 map_family 문자열이 3개 테이블에 중복되던 것을 scent_regions FK로 통일
좌표 → 영역 판정은 경계값으로 계산
취향 영역 표시는 중심 좌표 기준 원형 렌더링 (반경은 프론트 처리)
4. 향수 데이터 단위 정리

perfumes.volume_ml → perfume_prices.volume_ml 이동

용량은 향에 영향을 주지 않으므로 perfumes에 두면 동일 향수가 용량별로 중복 적재됨
중복 적재 시 향 지도 중복 출현, 유사 향수 목록 오염, 후기 통계 분산 문제 발생
용량별로 달라지는 것은 가격이므로 가격 테이블로 이동
5. 1:1 테이블 대리키 제거

불필요한 대리키를 제거하고 자연키를 PK로 지정하여 유일성을 PK 자체로 보장.

테이블	변경 전	변경 후
perfume_review_summaries	PK(summary_id, perfume_id)	PK(perfume_id)
perfume_map_points	PK(map_point_id)	PK(perfume_id)
map_exploration_states	PK(state_id)	PK(user_id)
기존 복합 PK는 대리키가 이미 유일하여 제약 효과가 없었음 (향수당 요약 여러 개, 향수당 지도 점 여러 개 가능)
6. 취향 테스트 테이블 정리
taste_test_sessions → user_taste_tests (계정당 1회 응시)
status → taste_result (진행 상태가 아닌 테스트 결과를 담는 컬럼이므로 이름 정정)
completed_at NOT NULL — 완료된 세션만 저장, 중도 이탈 시 재시작이므로 미완료 행 불필요
perfume_review_summaries.source_review_count 추가 — 요약 재생성 시점 판단용
7. 삭제 정책 결정
항목	결정
대댓글 기능	없음 → parent_comment_id 추가하지 않음
회원 탈퇴 기능	있음 → 개인 데이터 CASCADE, 커뮤니티 콘텐츠 SET NULL
진열대 해제 시 시향 기록	함께 삭제 (ON DELETE CASCADE) + 사전 경고 모달
컬렉션 삭제 시 게시글	유지 (스냅샷 구조로 자동 해결)
8. 유사 향수 테이블 검토
similarity_score, display_order 추가하지 않음 — 표시 순서 무작위 허용
PK (perfume_id, neighbor_perfume_id), FK 2개 확인 완료
적재 후 역방향 행 채우기로 대칭성 확보 (top-K 데이터는 비대칭이므로)
CHECK (perfume_id <> neighbor_perfume_id) 마이그레이션 SQL에 반영 예정
9. 전수 검증
PK: 35개 테이블 전부 확보 (map_exploration_states 누락분 추가)
FK: 누락분 해소 (perfume_map_points → perfumes)
식별관계/비식별관계 구분 정리 — FK가 PK 구성원인지에 따라 ERDCloud 관계 유형을 다르게 지정
