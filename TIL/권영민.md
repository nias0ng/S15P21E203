### 공통 예외 처리·응답 골자 (S15P21E203-106)

향수 API 9개가 공유할 기반을 먼저 구성. 9개 중 8개가 perfumeId 를 받아 동일한 404 를 내야 하므로
각 컨트롤러에서 개별 처리하면 응답 형태가 어긋남.

1. 에러 코드 소유권을 도메인으로 분리

common/ErrorCode 는 규격만 정의하고, 도메인별로 XxxErrorCode enum 이 구현.
모든 도메인이 하나의 enum 을 공유하면 팀원 전원이 같은 파일 끝부분에 상수를 추가하게 되어
기능적 문제 없이 순전히 파일 구조 때문에 머지 충돌이 반복됨.

enum 은 java.lang.Enum 을 암묵적으로 상속하므로 추상 클래스를 쓸 수 없고, 인터페이스가 유일한 수단.

code() 는 인터페이스 default 로 제공하고 상수 이름(name())을 그대로 반환.
코드 문자열을 별도 필드로 손으로 관리하면 상수명 리팩터링 시 따라오지 않고 값이 중복될 수 있음.

이때 name() 을 인터페이스에 선언하는 것이 핵심. Enum.name() 이 계약을 자동으로 충족하므로 구현이 불필요하고,
enum 이 아닌 클래스가 구현하면 컴파일 에러가 남. this 를 Enum 으로 캐스팅하는 방식은 같은 상황에서
런타임 ClassCastException 이 되므로 채택하지 않음.

남은 약점은 도메인 간 code 문자열 중복을 컴파일러가 막지 못하는 것. PERFUME_ 접두사 규칙을
PerfumeErrorCodeTest 가 values() 전수 검사로 강제.

2. GlobalExceptionHandler 는 ResponseEntityExceptionHandler 를 상속

상속하지 않고 ExceptionHandler(Exception.class) 하나로 받으면 Spring MVC 표준 예외까지 전부 빨려들어가,
405(잘못된 메서드), 400(타입 불일치), 404(없는 URL)처럼 클라이언트 잘못인 4xx 가 500 으로 기록됨.
Loki 에서 status=5 로 장애를 찾는 구조라 노이즈가 됨. 부모가 표준 예외 20종의 상태 코드 매핑을
이미 갖고 있으므로 응답 본문만 변환.

3. RequestIdFilter 와의 로깅 관계

필터는 필터 체인 밖으로 새어나온 예외만 ERROR 로 남김. 핸들러가 처리한 예외는 필터까지 올라가지 않으므로
필터의 ERROR 로그가 찍히지 않음. 따라서 예상하지 못한 예외의 스택트레이스는 핸들러가 직접 남겨야 하고,
이것이 원인 추적의 유일한 근거가 됨. 4xx 는 WARN 한 줄만 남기고 스택트레이스를 생략.
응답 본문에는 고정 문구만 내보내 내부 구조와 사용자 입력이 노출되지 않게 함.

4. PageResponse

Spring 의 Page 를 그대로 직렬화하면 현재 페이지 번호가 number 로 나가지만 프론트엔드는 page 를 읽음.
감싸는 record 를 common 에 두고 모든 목록 API 가 재사용.

### 향수 검색 API (S15P21E203-95)

GET /api/v1/perfumes — 향수명(영문·한글)과 브랜드명 부분 일치 검색.

1. 엔티티 대신 DTO 프로젝션

Page<Perfume> 로 받아 서비스에서 브랜드명을 꺼내면 향수 건수만큼 추가 쿼리가 나가고(N+1),
open-in-view 가 false 라 트랜잭션 밖에서는 지연 로딩 자체가 실패. DTO 프로젝션은 목록·카운트 두 쿼리로 끝남.

brand_id 가 nullable 이므로 LEFT JOIN. INNER JOIN 이면 브랜드가 없는 향수가 검색 결과에서 조용히 사라짐.

2. 검색어 유무를 한 쿼리에서 분기하지 않음

처음에는 keyword IS NULL 로 분기했는데 검색어 없는 요청이 500 으로 실패.
PostgreSQL 이 LIKE 패턴 결합 자리의 null 파라미터 타입을 bytea 로 추론해
lower(bytea) does not exist 가 발생.

검색어가 있는 요청이 먼저 실행되면 준비된 구문의 타입이 varchar 로 고정되어 통과하므로,
전체 테스트 실행에서는 통과하고 단독 실행에서만 실패하는 순서 의존 버그였음.
운영에서는 검색어 없는 첫 요청에 터지는 형태. 메서드를 둘로 나눠 null 바인딩 자체를 제거.

3. 정렬 기본값

ORDER BY 없는 페이징은 행 순서가 보장되지 않아 2페이지에 1페이지 항목이 다시 나오거나
어떤 항목이 아예 조회되지 않을 수 있음. PageableDefault 로 id 정렬을 기본값으로 지정.

4. 기능명세서 재대조로 두 건 수정

구현 후 명세서를 다시 대조해 어긋난 부분을 발견. API 목록의 한 줄만 보고 범위를 좁게 해석한 것이 원인.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 검색어 없음 | 활성 향수 전체 반환 | 조회하지 않고 200 + 빈 목록 |
| 대표 이미지 | 응답에 없음 | thumbnailUrl 추가 |

전체 목록을 돌려주면 검색창을 누르기만 해도 카탈로그 전체를 긁는 요청이 되고, 이름 컬럼에 인덱스가 없어 풀스캔.
400 이 아니라 200 을 쓴 것은 프론트엔드가 빈 화면을 단순하게 그릴 수 있도록 한 결정.

perfume_images 에 대표 여부 컬럼이 없어 display_order 최솟값을 대표로 보고 NULL 은 뒤로 밀며,
값이 같을 때는 image_id 로 순서를 확정. 검색 쿼리에 이미지 조인을 합치지 않은 이유는 이미지가 여러 장이면
행이 중복되고 display_order 가 같거나 NULL 인 경우 어떤 행이 남을지 예측하기 어려워지기 때문.
조회된 페이지의 향수 ID 로 이미지를 한 번 더 조회해 서비스에서 합침.
