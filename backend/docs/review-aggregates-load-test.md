## 3. 무엇이 병목이었는가

50 VU 구간을 항목별로 나누면 이렇습니다.

| 50 VU 기준 | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 화면/s | 255.42 | **745.38** | **+192%** |
| HTTP 요청/s | 1,021.68 | 745.38 | -27% |
| 트랜잭션/s | 1,021.68 | 745.38 | -27% |
| SQL 문/s | 2,554 | **5,218** | +104% |
| 최대 CPU | 212.74% | 166.73% | -21.6% |

**요청 수와 트랜잭션 수는 27% 줄었는데 화면은 2.9배 나왔습니다.** 화면 한 장에 트랜잭션을 넷 열던 것을 하나로 바꾼 결과가 그대로 드러난 수치입니다.

효율로 보면 더 분명합니다.

| | 개선 전 | 개선 후 | 배수 |
| --- | --- | --- | --- |
| CPU 1% 당 화면/s | 1.201 | 4.471 | **3.72배** |
| 화면 한 장의 CPU 비용 | 0.833 | 0.224 | **-73%** |

### 처음 가설 중 틀린 것

최초 분석에서 "이 시스템이 초당 약 2,500 SQL 문에서 막힌 것으로 보인다"고 추정했습니다. **틀렸습니다.** SQL 문 처리량은 5,218/s 까지 두 배 넘게 올라갔고, 그러면서 CPU 는 오히려 내려갔습니다. 막고 있던 것은 SQL 문의 수가 아니라 **요청과 트랜잭션의 개수**였습니다.

### 확정되지 않은 것

CPU 는 개선 전에도 4 vCPU 기준 53% 로 포화가 아니었고 개선 후에는 42% 입니다. 메모리도 전 구간 변동이 15MiB 뿐입니다. **두 자원 모두 병목이 아닙니다.**

남은 유력 후보는 커넥션 풀입니다. `application*.yaml` 에 `maximum-pool-size` 설정이 없어 Spring Boot 기본값 10개가 적용되는데, 두 실행의 트랜잭션 점유 시간을 pool=10 으로 역산하면 개선 전 9.8ms, 개선 후 13.4ms 로 **양쪽 다 커넥션 10개가 꽉 찬 상태와 맞아떨어집니다.** 개선 후 트랜잭션이 길어진 것(SQL 2~3문 → 7문)도 설명됩니다.

다만 **증명은 아닙니다.** `hikaricp_connections_pending` 을 확인해야 확정되고, 그 값은 `/actuator/prometheus` 가 열려야 읽을 수 있습니다. 지금은 nginx 가 `/api/` 로 시작하는 요청만 백엔드로 보내 그 경로가 프론트 SPA 의 `index.html` 을 반환합니다. `performance/ops/nginx-actuator.conf.snippet` 을 적용하면 잴 수 있습니다.

## 4. 남은 일

1. **프론트 이관** — 백엔드만 바뀌었고 화면은 아직 네 번 부릅니다. **실사용자가 받는 응답은 지금도 개선 전 그대로입니다.** 이관 방법은 [통합 안내](review-aggregates-migration.md) 5장에 있습니다.
2. **기존 네 엔드포인트 제거** — 이관 확인 뒤. 제거 범위는 [통합 안내](review-aggregates-migration.md) 8장에 있습니다.
3. **`/actuator/prometheus` 노출** — 커넥션 풀 가설을 판정하려면 필요합니다. 나머지 API 가 공통으로 막힌 900 RPS 대의 상한도 같은 지표로 설명될 수 있습니다.
