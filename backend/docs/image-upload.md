# 이미지 업로드 가이드

올라온 이미지 파일을 서버에 저장하고 주소로 돌려주는 기능입니다. 지금 쓰는 곳은 둘입니다 —
**게시글 이미지**와 **프로필 사진**. 이 문서의 모든 상대 경로는 `backend/`를 기준으로 합니다.

저장 규칙(형식 판별 · 이름 짓기 · 경로 탈출 방어)은 `global/storage/ImageFileStorage` 가
공통으로 갖고 있습니다. **어디에 쌓을지, 얼마까지 받을지, 무엇을 에러로 부를지는 도메인마다
다릅니다.**

## 1. 두 기능의 차이

|  | 게시글 이미지 | 프로필 사진 |
| --- | --- | --- |
| 단계 | 2단계 (올리고 → 글에 담기) | 1단계 (올리면 바로 적용) |
| 장수 | 여러 장, 순서 있음 | 한 장 |
| 저장 자리 | `post_images` 테이블 | `users.profile_image_url` 컬럼 |
| 크기 제한 | 5MB | 1MB |
| 조회 권한 | 로그인 불필요 | 로그인 불필요 |

**게시글만 2단계인 이유는 순서입니다.** 글이 만들어지기 전에 미리보기를 보여줘야 하는데 그
시점에는 이미지를 매달 글이 없습니다. 프로필은 매달 사용자가 이미 있어 나눌 이유가 없고,
나누면 올려 놓고 적용하지 않은 파일만 남습니다.

**프로필 제한이 더 작은 이유**는 아바타가 화면에서 작게 보이고, 글 목록마다 여러 개가 함께
내려가는 자리라 전송량이 곱절로 늘기 때문입니다.

## 2. API

### 게시글 이미지

```
POST /api/v1/posts/images   (multipart/form-data, 파일 자리 이름 file, 로그인 필요)
→ 201 {"imageUrl": "/api/v1/posts/images/2026/09/<uuid>.png"}
```

화면은 이 주소를 글 작성·수정 요청의 `imageUrls` 에 담아 보냅니다. **한 번에 한 장**이고,
여러 장은 이 API 를 여러 번 부릅니다. 그래야 한 장이 실패해도 나머지가 살아남고 어느 장이
실패했는지 화면이 압니다.

| 상태 | 코드 |
| --- | --- |
| 400 | `COMMUNITY_IMAGE_EMPTY` (빈 파일) / `BAD_REQUEST` (`file` 자리 없음) |
| 401 | `COMMUNITY_LOGIN_REQUIRED` |
| 413 | `COMMUNITY_IMAGE_TOO_LARGE` / `PAYLOAD_TOO_LARGE` |
| 415 | `COMMUNITY_IMAGE_TYPE_NOT_ALLOWED` |

### 프로필 사진

```
POST   /api/v1/users/me/profile-image   (multipart/form-data, 파일 자리 이름 file, 로그인 필요)
→ 200 {"profileImageUrl": "/api/v1/users/profile-images/2026/09/<uuid>.png"}

DELETE /api/v1/users/me/profile-image   (로그인 필요)
→ 204
```

**올리는 즉시 계정에 적용되고 쓰던 사진 파일은 지워집니다.** 화면은 응답의 주소로 아바타만
갈아 끼우면 되고, 내 정보를 다시 조회할 필요가 없습니다.

`GET /api/v1/users/me` 응답에 `profileImageUrl` 이 들어 있습니다. **`null` 이면 설정하지 않은
상태**이고 화면이 기본 아바타를 보여줍니다. 서버가 기본 이미지 주소를 넣어 주지 않는 이유는,
기본 이미지를 바꿀 때 이미 저장된 값을 전부 고쳐야 하기 때문입니다.

`DELETE` 는 사진이 없어도 성공합니다. 여러 번 눌러도 결과가 같습니다.

| 상태 | 코드 |
| --- | --- |
| 400 | `USER_PROFILE_IMAGE_EMPTY` / `BAD_REQUEST` |
| 401 | `AUTH_LOGIN_REQUIRED` |
| 413 | `USER_PROFILE_IMAGE_TOO_LARGE` / `PAYLOAD_TOO_LARGE` |
| 415 | `USER_PROFILE_IMAGE_TYPE_NOT_ALLOWED` |

### 413 이 둘인 이유

제한이 두 겹입니다. 안쪽(도메인 제한)이 이유가 있는 에러 코드를 돌려주고, 바깥쪽
(`spring.servlet.multipart.max-file-size`, 8MB)은 요청 본문을 다 읽기 전에 끊는 울타리라 공용
413 만 나갑니다. **바깥쪽을 안쪽보다 작게 두면 도메인 에러 코드가 영영 나가지 않습니다.**

## 3. 형식 판별

파일 이름의 확장자나 `Content-Type` 헤더는 보내는 쪽이 마음대로 적을 수 있어 쓰지 않습니다.
**파일 내용의 앞부분(시그니처)으로 판별하고, 확장자는 거기서 알아낸 형식으로 새로 붙입니다.**

확장자만 믿으면 `.png` 라고 적힌 HTML 파일이 들어오고, 그것을 우리 도메인에서 내주는 순간
저장형 XSS 가 됩니다. SVG 를 받지 않는 이유도 같습니다 — 그림이지만 스크립트를 품을 수 있는
XML 이고, 시그니처가 없어 내용으로 걸러낼 수도 없습니다.

받는 형식은 **JPG · PNG · GIF · WEBP** 넷이고 두 기능이 같습니다.

파일 이름도 우리가 UUID 로 새로 짓습니다. 보낸 이름을 쓰면 같은 이름을 올린 다른 사람의
파일을 덮어쓰고, `../` 가 든 이름으로 저장 위치를 벗어날 수 있습니다.

## 4. 저장 위치와 설정

| 키 | 기본값 |
| --- | --- |
| `hyanghae.community.post-image.directory` | `uploads/posts` |
| `hyanghae.community.post-image.url-path` | `/api/v1/posts/images` |
| `hyanghae.community.post-image.max-size` | `5MB` |
| `hyanghae.user.profile-image.directory` | `uploads/profiles` |
| `hyanghae.user.profile-image.url-path` | `/api/v1/users/profile-images` |
| `hyanghae.user.profile-image.max-size` | `1MB` |
| `spring.servlet.multipart.max-file-size` | `8MB` |

기본값은 각 `*Properties` 에 있습니다. yaml 에는 바꿀 값만 적습니다.

**⚠ 두 저장소의 `directory` 가 겹치면 안 됩니다.** 같은 트리를 둘이 함께 보면 게시글 주소로
프로필 파일을 가리킬 수 있게 되고, 그 글을 지우는 것만으로 남의 프로필 사진이 지워집니다.
`url-path` 도 마찬가지로 겹치면 안 됩니다.

`directory` 가 상대 경로면 프로세스의 작업 디렉터리를 기준으로 풉니다. 컨테이너에서는
`/app/uploads/...`, `./gradlew bootRun` 으로 직접 띄우면 `backend/uploads/...` 입니다
(`.gitignore` 에 있습니다). 시작할 때 이 디렉터리를 만들지 못하면 **애플리케이션이 뜨지
않습니다.** 첫 업로드에서 500 을 보고 알아채는 것보다 배포 시점에 실패하는 편이 낫습니다.

### 주소가 `/api/v1` 아래인 이유

배포 nginx 는 `/api` 만 백엔드로 넘기고 나머지는 정적 파일 디렉터리에서 찾습니다.
`/uploads/...` 같은 주소를 쓰면 nginx 설정을 함께 고치기 전까지 이미지가 404 가 됩니다.
`/api/v1` 아래에 두면 이미 열려 있는 길로 들어오므로 서버 설정을 건드리지 않고 동작하고,
로컬에서 백엔드만 띄웠을 때도 똑같이 동작합니다.

**프로필 사진 주소를 `/api/v1/users/me` 아래에 두면 안 됩니다.** `SecurityConfig` 가 그 경로를
인증 필요로 막고 있어, 남의 글 옆에 붙은 프로필 사진이 비회원에게 깨져 보입니다.

파일을 내주는 것은 컨트롤러가 아니라 리소스 핸들러입니다(`PostImageWebConfig`,
`UserProfileImageWebConfig`). 그래서 Swagger 에는 올리는 쪽만 나옵니다. 받은 주소로 GET 하면
로그인 없이 이미지가 나오고, HEAD 로 크기와 형식만 확인할 수도 있습니다.

## 5. ⚠ 배포 서버에서 해야 하는 일

**저장 디렉터리는 컨테이너 안에 있습니다. 볼륨을 붙이지 않으면 다음 배포에서 그동안 올라온
이미지가 전부 사라지고 게시글과 프로필에는 깨진 주소만 남습니다.**

배포 디렉터리(`/home/ubuntu/hyanghae`)의 `compose.yaml` 은 저장소에 없으므로 서버에서
직접 고쳐야 합니다. backend 서비스에 볼륨을 붙입니다.

```yaml
services:
  backend:
    volumes:
      - uploaded-images:/app/uploads

volumes:
  uploaded-images:
```

두 기능이 `/app/uploads` 아래의 서로 다른 하위 디렉터리를 쓰므로 **볼륨은 하나면 됩니다.**

적용은 평소 배포와 같습니다.

```bash
cd /home/ubuntu/hyanghae
docker compose -f compose.yaml up -d
```

`compose.manual-test.yaml` 에는 같은 볼륨이 이미 들어 있습니다. nginx 는 건드릴 필요 없습니다.

### 디스크

쓰이지 않게 된 파일은 지워지지만(§6) 게시글에 올려 놓고 글을 쓰지 않은 파일은 쌓입니다(§7).
배포 서버의 여유 공간을 한 번은 확인해 두는 편이 좋습니다.

```bash
df -h /var/lib/docker
docker system df -v | grep uploaded-images
```

## 6. 파일을 지우는 규칙

| 언제 | 게시글 이미지 | 프로필 사진 |
| --- | --- | --- |
| 교체 | 빠진 주소의 파일 삭제 | 쓰던 파일 삭제 |
| 삭제 | 글을 지우면 그 파일들 삭제 | 내리면 파일 삭제 |
| 탈퇴 | — | 쓰던 파일 삭제 |

공통으로 지키는 것들입니다.

- **커밋된 뒤에 지웁니다.** 트랜잭션 안에서 지우면 뒤늦게 롤백됐을 때 행은 살아 있는데 파일만
  없어져 깨집니다. 커밋 뒤에 지우면 최악이라도 파일이 남을 뿐이고, 남은 파일은 나중에 치울
  수 있습니다. 되돌릴 수 없는 쪽을 피하는 것입니다.
- **우리가 만들지 않은 주소는 건드리지 않습니다.** 그 저장소의 `url-path` 로 시작하고 저장
  루트 안으로 풀리는 주소만 지웁니다. 외부 주소나 `../` 가 섞인 주소는 조용히 지나갑니다.
- **지우기에 실패해도 요청은 성공입니다.** 사용자가 요청한 일은 이미 커밋됐고, 파일 정리가
  안 됐다고 그것을 되돌릴 수는 없습니다. 실패는 로그로만 남습니다.

**게시글만 참조 수를 셉니다.** 주소는 문자열이라 남의 글에 있는 주소를 복사해 자기 글에 붙일
수 있어, 세어 보지 않고 지우면 자기 글을 지우는 것만으로 남의 글 이미지를 깨뜨릴 수 있습니다.
프로필은 주소가 컬럼 하나에만 들어가고 그 값을 정하는 것이 서버라 그런 일이 없습니다.

## 7. 알려진 한계

- **버려진 게시글 이미지**: 올리기만 하고 글을 쓰지 않으면 파일이 남습니다. 글에 한 번도
  걸리지 않아 지울 근거가 생기지 않습니다. 보존 기간(예: 24시간)을 두고 아무 글도 참조하지
  않는 파일을 치우는 배치로 해결할 수 있지만, 실제로 얼마나 쌓이는지 보고 주기와 보존 기간을
  정하는 편이 낫다고 보아 별도 이슈로 남겼습니다. **프로필은 올리는 즉시 적용되므로 정상
  흐름에서는 이 문제가 없습니다.**
- **롤백된 프로필 업로드**: 파일을 저장한 뒤 트랜잭션이 롤백되면 그 파일만 남습니다. 컬럼은
  옛 주소 그대로이고 쓰던 사진도 지워지지 않으므로 **화면은 멀쩡합니다.** 파일이 남는 것은
  나중에 치울 수 있지만 쓰던 사진이 사라지는 것은 되돌릴 수 없어, 되돌릴 수 있는 쪽을 택한
  결과입니다.
- **저장소를 넘나드는 주소**: 프로필 사진 주소를 게시글의 `imageUrls` 에 붙여 넣은 뒤 프로필을
  바꾸면 그 글의 이미지가 깨집니다. 반대 방향도 같습니다. 막으려면 두 도메인이 서로의
  테이블을 알아야 해서 그대로 두었습니다. 자기 사진을 자기 글에 붙인 경우라 피해 범위가
  자신에게 그칩니다.
- **빈 디렉터리**: 파일을 지워도 날짜 디렉터리는 남습니다. 개수가 달마다 하나씩 늘 뿐이라
  그대로 둡니다.
- **서버가 하나라는 전제**: 파일이 그 서버의 디스크에 있으므로 백엔드를 여러 대로 늘리면
  A 에 올린 이미지를 B 가 내주지 못합니다. 늘릴 때는 저장소를 먼저 옮겨야 합니다.
- **리사이징이 없습니다**: 올린 원본을 그대로 저장합니다. 넣으려면 이미지를 디코딩해야 하는데
  표준 `ImageIO` 는 WebP 를 못 읽어, WebP 를 포기하거나 라이브러리를 추가해야 합니다.

## 8. 나중에 옮길 때

- **nginx 가 직접 내주게 하기**: 같은 경로를 nginx 가 디스크에서 바로 내주도록 가로챕니다.
  저장된 주소는 그대로 두고 앞단만 바뀌므로 데이터는 손댈 필요가 없습니다.
- **S3 같은 외부 저장소로 옮기기**: `ImageFileStorage` 의 저장 부분과 `url-path` 만 바꾸면
  두 기능이 함께 옮겨집니다. `PostService` 와 `User` 는 주소 문자열만 알고 있어 바뀌지
  않습니다. **이미 저장된 주소는 옛 경로 그대로이므로, 옮긴 뒤에도 그 주소가 계속 닿는지
  확인해야 합니다.**
