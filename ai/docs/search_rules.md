# 자연어 향수 추천 — 검색 규칙

`nlr_reference.py` 가 실제로 하는 일을 글로 옮긴 것입니다. **둘이 어긋나면 코드가 맞습니다.**

## 표기 규약

- **[측정]** — 실제 데이터에서 확인한 값입니다. 여기에 맞지 않게 만들면 결과가 달라집니다.
- **[제안]** — 저희 판단입니다. **참고만 하시고 담당자분이 정하시면 됩니다.**

---

## 전체 흐름

```
사용자 문장
   │
   ▼
① 조건 추출        한국어 표현 -> accord 이름              [측정]
   │               (LLM 구조화가 있으면 같이 씀)
   ▼
② 검색             그 accord 를 전부 가진 향수를 찾음        [측정]
   │
   ▼
③ 정렬             strength 합 -> 평가자 수 -> id           [측정]+[제안]
   │
   ▼
④ 완화             3개 미만이면 조건을 단계적으로 풀음        [제안]
   │
   ▼
향수 5개 + 각 향수가 어느 조건에 어떻게 맞았는지
```

## ① 조건 추출

`domain_lexicon_v1_14.csv` 63행에서 **문장에 들어 있는 표현**을 찾습니다.

```
"빨래 냄새 나는 향수 찾고 있어"
   └ '빨래' 발견  ->  soapy (core) + fresh (core)
```

**[측정] 규칙 3가지**

| | 규칙 | 근거 |
|---|---|---|
| 1 | `required` 가 `core` 인 행만 조건으로 씁니다 | `optional` 은 점수용이며 아직 검증 전 |
| 2 | `target_field` 가 `NO_MAPPING` 인 행은 **건너뜁니다** | 매핑 근거가 없다고 판정된 표현 |
| 3 | `match_condition` 이 `query_contains:a,b,c` 면 그 단어가 문장에 있을 때만 적용 | 뜻이 갈리는 표현 (`깨끗한` = 비누냐 물이냐) |

### `scent_preference` 의 노트 이름 — 노트 브리지

①단계 LLM 이 `scent_preference` 에 accord 이름이 아니라 **노트(향 원료) 이름**을 넣는 일이
잦습니다. 예전에는 알아듣지 못해 버렸고, 지금은 `note_accord_bridge.csv` 로 바꿉니다.

```
scent_preference: ["mint"]   ->   aromatic · fresh spicy · green
scent_preference: ["lemon"]  ->   aromatic · citrus
scent_preference: ["flower"] ->   (표에 없습니다. 노트가 아니라 형용사입니다)
```

**[측정] 문턱 2가지 — 다만 지금 실제로 거르는 것은 `lift` 뿐입니다**

| | 문턱 | 이 파일에서 거르는 행 | 근거 |
|---|---|---:|---|
| 1 | `p >= 0.5` — 그 노트를 가진 향수의 **절반 이상**이 그 accord 를 가질 때만 | **0행** | 배포 CSV 를 만들 때 이미 `p >= 0.5` 로 걸러 넣었습니다(`p` 최솟값이 정확히 `0.5000`). **재생성 대비 방어**로 남겨 둔 것이지 지금 일하지 않습니다 |
| 2 | `lift >= 1.4` — 그 비율이 accord 기저율의 **1.4배 이상**일 때만 | **987행** | `woody` 는 전체 향수의 **63.1%** 가 가지고 있어 `p` 만 보면 아무 노트에나 붙습니다. `peony → woody` 는 `p` 0.536 인데 `lift` 0.87 로 **오히려 덜 나온다**는 뜻입니다 |

2,925행 중 1,938행이 통과합니다 [측정].

문턱 `1.4` 는 `DECISIONS.md` N4 의 통제군 값입니다.
`load_index(bridge_p_min=, bridge_lift_min=)` 으로 바꿀 수 있습니다.

> **`p` 문턱을 내려 실험하려면 이 파일로는 안 됩니다.** `p < 0.5` 인 행이 들어 있지
> 않습니다. 분석용 원본 `EDA/analysis_outputs/10_note_accord_bridge.csv`(5,806행 ·
> `p` 최솟값 0.0027 · `p < 0.5` 가 2,881행)를 써야 합니다.

합성 600문장에서 조건을 뽑는 비율이 **87.5% → 88.8%** 로 오르고, 조건이 하나뿐인
`SINGLE_BROAD` 가 **89 → 73** 으로 줍니다 (`DECISIONS.md` N14 · 사전 v1.14 기준).

**`ai/data/note_accord_bridge.csv` 가 없으면** 기동 로그에 경고가 남고 이 단계를
건너뜁니다. 서버는 정상으로 돕니다.

**[측정] 한글 accord 표기 10종**도 직접 잡습니다 — `바닐라`·`스위트`·`시트러스`·`아로마틱`·`앰버`·`우디`·`파우더리`·`프레시`·`프루티`·`플로럴`. 합성 평가셋 600건에서 80건이 여기 걸립니다(대부분 `바닐라`).

### LLM 구조화는 선택입니다

LLM이 `scent_preference` 를 뽑아주면 함께 씁니다. **없어도 돌아갑니다.**

| | 결과가 나오는 비율 (600건) |
|---|---|
| LLM + 사전 | **77.7%** (갈래A 88.7% · 갈래B 66.7%) |
| **사전만** | **35.7%** (갈래A 39.7% · 갈래B 31.7%) |

**[측정] LLM이 커버리지의 절반을 만듭니다.** 그래도 사전만으로 장면 쿼리 4개는 돌아가므로, **API가 죽어도 서비스는 살려두십시오.**

## ② 검색 — 하드 AND

**core accord 를 전부 가진 향수만** 통과합니다.

```sql
-- [제안] SQL 로 옮기면 이런 모양입니다
SELECT p.id
FROM perfumes p
WHERE EXISTS (SELECT 1 FROM perfume_accords a
              WHERE a.perfume_id = p.id AND a.accord = 'soapy')
  AND EXISTS (SELECT 1 FROM perfume_accords a
              WHERE a.perfume_id = p.id AND a.accord = 'fresh')
  AND NOT EXISTS (SELECT 1 FROM perfume_accords a          -- avoid
                  WHERE a.perfume_id = p.id AND a.accord = ANY(:avoid))
  AND p.people >= 10
```

**[측정] core 가 2개 미만이면 AND 를 쓰지 않습니다.** accord 하나로는 순위가 안 나옵니다 — `citrus` 단독은 **17,736개가 똑같이 강도 100** 이라 상위 5개가 제비뽑기가 됩니다. 근거는 `DECISIONS.md` N2.

**[측정] `people >= 10` 문턱.** 평가자가 없는 향수를 거릅니다. 커버리지 손실은 **0.3%p** (58.3% → 58.0%) 입니다.

> `people` 은 그 향수의 평가에 참여한 총 사용자 수입니다. 전체 131,930개 중 **16,578개(12.6%)가 0명이거나 결측**입니다.

## ③ 정렬 — 여기가 제일 중요합니다

```
1순위  strength 합 내림차순     ← 향 조건이 순위를 정합니다
2순위  평가자 수 내림차순       ← 동점일 때만 개입합니다
3순위  향수 id 오름차순         ← 재현성 장치. 의미 있는 순서가 아닙니다
그리고 브랜드당 최대 1개
```

**조건이 accord 하나뿐이면 `stage` 가 `SINGLE_BROAD` 입니다.** AND 와 OR 이 같은 집합이라
넓힐 것이 없는데, 예전에는 `RELAXED_OR` 로 떨어져 *"조건을 넓혀 찾았습니다"* 가 떴습니다.
넓힌 적이 없으므로 거짓이었고 600문장 중 **91건**이 그렇게 표시됐습니다.

그렇다고 `AND` 로 적을 수도 없습니다. 넓은 accord 하나로는 향 조건이 순위를 정하지 못하고
**인기도가 정합니다**(`citrus` 단독은 5위 동점 17,736개). 사용자에게 알려야 할 상태입니다.

그래서 단계를 따로 뒀습니다. **`status` 는 `OK_RELAXED` 그대로**라 연동 형식은 바뀌지 않고,
`diagnostics.relaxed` 에 *"향 조건이 accord 하나뿐이라 순위를 정하지 못한다"* 가 들어갑니다.

| | 전 | 후 |
|---|---:|---:|
| `AND` | 391 | 391 |
| `SINGLE_BROAD` | — | **91** |
| `RELAXED_OR` | 129 | **38** (진짜 완화만) |
| `NO_CONDITION` | 80 | 80 |

`DECISIONS.md` N2 가 직역 대응(`나무`=woody)의 단독 매핑을 허용하면서 **이 표시를 조건으로
달았습니다.** 추천 결과는 바뀌지 않습니다 — NDCG@5 0.4688 로 동일합니다.

### [측정] 2순위를 넣은 이유

원래는 1순위만 있고 동점을 id 순으로 깼습니다. 그랬더니 **평가자 0명짜리 향수가 1위**로 올라왔습니다.

```
"이불 같은 포근한 향"
  전:  White Cotton Hair & Body Mist (평가자 0명, 평점 0.0)   <- 1위
  후:  Hair Salon Grooming (40명) / Enigma Blend (80명) /
       Clean Vibes (25명) / Invictus Parfum (3,141명) / Samia Intense (26명)
```

동점이 클 때(완화가 걸린 경우) 차이가 큽니다.

```
"시트러스" 한 조건만 남았을 때 — 동점 8,704개
  전:  Orange Tonic (95명)
  후:  Light Blue (35,695명) / Coco Mademoiselle (32,839명) / Terre d'Hermès (27,711명)
```

**[측정]** 합성 600건에서 상위 5개에 든 평가자 0명 향수가 **249개 → 165개** 로 줄고, 평가자 중앙값이 **9명 → 15명** 이 됩니다.

> **왜 인기도를 점수에 곱하지 않았는가** — `strength 합 × log(평가자 수)` 를 재봤더니 **인기가 향 조건을 이겼습니다.** `이불` 검색에 `soapy=13` 짜리 향수가 4위로 올라옵니다. 그러면 추천 이유 칸에 *"soapy 13 이 맞았습니다"* 라고 써야 합니다. 그래서 **동점일 때만** 개입하게 두었습니다.
>
> 평점(`rating_avg`)은 **쓰면 안 됩니다.** 평점 5.00 인 향수 8,410개 중 **99.8%가 평가자 10명 이하**입니다. 평점을 더하면 평가자 1명짜리가 1위가 됩니다.

### [측정] 3순위(id)는 순위를 정하는 규칙이 아닙니다

*"id 오름차순으로 추천한다는 게 말이 되나"* 는 당연한 의문입니다. **맞습니다. 순서에 의미는 없습니다.**
1·2순위로도 갈리지 않을 때 **아무거나 고르지 않기 위한 장치**입니다. 빼면 같은 문장에 다른 향수가
나올 수 있고, 회귀 테스트도 버그 재현도 불가능해집니다.

**얼마나 개입하는지 셌습니다.** 합성 600건의 상위 5개 자리를 전부 검사했습니다.

```
검사한 자리       2,196개   (조건을 뽑은 문장 × 상위 5)
3순위가 정한 자리     11개   (0.5%)  — 전부 4·5위. 1~3위는 한 번도 없음
동점 묶음 크기        전부 2개  — "8,704개 중 아무거나" 가 아닙니다
```

1순위만 같은 경우는 흔하지만(5위 동점 중앙값 8,704개), **평가자 수가 0~35,695 로 넓어 2순위가
거의 다 갈라냅니다.** 세기 합과 평가자 수가 **둘 다** 같아야 3순위까지 내려옵니다.

#### id 는 무작위가 아니지만, 그게 3순위를 정당화하지는 않습니다

| id 구간 | 향수 수 | 평가자 수 중앙값 |
|---|---:|---:|
| 1분위 `1 ~ 33,986` | 32,290 | **42명** |
| 2분위 `33,986 ~ 67,686` | 32,290 | 19명 |
| 3분위 `67,686 ~ 101,025` | 32,290 | 11명 |
| 4분위 `101,025 ~ 134,530` | 32,291 | **2명** |

단조 감소합니다. **작은 id 가 더 알려진 향수입니다.** 먼저 등록된 향수라서입니다.

**그런데 3순위 상황에서는 이 사실이 쓸모없습니다.** 3순위는 평가자 수가 **이미 같을 때만**
발동하는데, 위 관계는 **평가자 수를 통해서만** 성립하기 때문입니다. 실제로 발동한 11묶음은
**전부 평가자 수가 같았고**, `id 작은 쪽의 평가자 수가 더 많은 경우는 0개`였습니다.

평가자 수를 고정하고 보면 id 는 아무것도 예측하지 못합니다.

```
평가자  0명 향수 15,561개 — id 와 평점의 상관 -0.044
평가자  1명 향수 10,902개 — id 와 평점의 상관 +0.089
평가자  2명 향수  7,558개 — id 와 평점의 상관 +0.099
평가자 10명 향수  2,129개 — id 와 평점의 상관 +0.087
```

#### [보류] 3순위를 평점으로 바꾸는 안

평가자 수가 이미 같은 상태라 **위 블록쿼트의 "평점 5.00 · 평가자 1명" 문제가 생기지 않습니다.**
`Alga(평점 4.80)` 가 `Bronze Goddess(4.20)` 를 이기는 것이 id 로 이기는 것보다 설명하기 쉽습니다.

**그래도 지금 바꾸지 않습니다.** 실제 동점 묶음이 **2종류뿐**이라 판단 근거가 부족합니다.
표본 2개로 규칙을 바꾸는 것은 `DECISIONS.md` N4 가 금지한 방식입니다. 그리고 11묶음 중
`Coconut Sand(3.97)` 가 `Desejo por Coco e Baunilha(4.09)` 를 이긴 사례가 있어 방향도 일정하지 않습니다.

미매칭 로그와 실사용 기록이 쌓이면 다시 봅니다.

### [제안] 브랜드당 1개

```
"휴양지에서 쓸 향수"
  전:  Victoria's Secret x3 + 2개    -> 브랜드 3종, 평가자 중앙 7명
  후:  브랜드 5종, 평가자 중앙 83명
```

숫자는 담당자분이 정하셔도 됩니다. 2개까지 허용해도 동작합니다.

## ④ 완화 — 결과가 3개 미만일 때

`spec.md` §3 의 완화 사다리 중 **4단계와 5단계만** 구현돼 있습니다.

| 순서 | 하는 일 | 상태 |
|---|---|---|
| 4 | **core accord 를 AND 에서 OR 로** | 구현됨 |
| 5 | **평가자 문턱 해제** | 구현됨 |
| 1~3 | optional 제거 / context 제거 / performance 제거 | **미구현** — 그 조건들을 아직 안 쓰기 때문 |
| — | **`avoid` 는 어느 단계에서도 완화하지 않습니다** | 사용자가 명시적으로 거부한 것 |

**[측정] 완화를 켜면 58.3% → 77.7%** 로 오릅니다. 조건이 하나라도 있으면 **결과 없음이 0건**입니다.

**[측정] 대가** — 완화로 넘어간 쿼리는 5위 동점이 **중앙값 3,204개**입니다. 향 조건이 순위를 거의 못 정하고 평가자 수가 정합니다. 응답의 `diagnostics.stage` 가 `RELAXED_OR` 면 **사용자에게 "조건을 넓혀서 찾았다"고 알려주십시오.**

### "3개 미만" 의 기준은 요청한 개수를 넘지 않습니다

```python
min_results = min(min_results, top_k)
```

`top_k` 가 3보다 작으면 AND 가 다 찾아도 3개를 못 채워 **무조건 완화로 떨어졌습니다.**
`topK=2` 로 부르면 `OK` 가 나올 수 없고 평가자 2명짜리 향수가 1위로 올라왔습니다.
부른 쪽이 원한 개수보다 많이 요구할 수는 없으므로 작은 쪽으로 맞춥니다.

기본값(`top_k=5`)에서는 `min(3, 5) = 3` 이라 **동작이 바뀌지 않습니다.** 합성 평가셋
600건 재측정에서 NDCG@5 가 0.4110 으로 수정 전과 같았습니다.

## ⑤ 결과를 못 내는 경우 — 22.3%가 여기 걸립니다

| `status` | 뜻 | 화면에서 할 일 |
|---|---|---|
| `OK` | 조건을 다 만족하는 결과 | 그대로 보여줍니다 |
| `OK_RELAXED` | 조건을 넓혀서 찾음 | **"조건을 넓혀 찾았다"고 알립니다** |
| `NO_CONDITION` | **향 조건을 하나도 못 뽑음** | 다시 입력 요청 + 미매칭 로그 기록 |
| `NO_RESULT` | 조건은 있는데 결과가 없음 | 현재 발생하지 않습니다 |

**[측정] `NO_CONDITION` 이 600건 중 134건(22.3%)** 입니다. 사전에 없는 표현이거나 향과 무관한 입력입니다.

**[제안] 이때 인기 향수를 대신 보여주지 마십시오.** 추천처럼 보이지만 근거가 없습니다. *"어떤 향을 원하시는지 좀 더 알려주세요"* 쪽이 정직합니다.

**[제안] 미매칭 로그를 1일차부터 켜 주십시오.** 어떤 표현이 몇 번 막혔는지가 사전을 키울 유일한 단서입니다. 필요한 것은 `원문 · 정규화 키 · 시각` 세 칸입니다.

```json
{
  "status": "OK",
  "query": "빨래 냄새 나는 향수 찾고 있어",
  "conditions": {
    "core": ["fresh", "soapy"],
    "avoid": [],
    "matched_expressions": ["빨래"],
    "source": "lexicon_only"
  },
  "results": [
    {
      "perfume_id": 73368,
      "name": "Laundry",
      "brand": "Ostrikov Beauty Publishing",
      "people": 29,
      "rating": 4.17,
      "score": 193,
      "matched": [
        { "accord": "soapy", "strength": 100, "from": "빨래",
          "tier": "TEAM",
          "rationale": "팀 문서의 생활 비유에 '햇빛에 바싹 말린 빨래'가 있다..." }
      ],
      "avoid_confirmed": []
    }
  ],
  "diagnostics": {
    "stage": "AND", "candidate_count": 518, "tie_at_last": 1,
    "relaxed": [], "unmatched_hint": null
  }

```

**`matched[].rationale` 이 추천 이유의 재료입니다** (요구사항 NLR-07). 문장화는 LLM이 하되 **이 근거만 주고** 향수의 다른 정보는 주지 마십시오 — 없는 내용을 지어낼 재료 자체를 주지 않는 것이 방법입니다.

**`tier` 는 사용자에게 노출하지 마십시오.** 내부 기록입니다.
